# 架构演进与取舍深度解析

> 本文档以「演进时间线」为主线，把 25 条 ADR 串成一条有因果链的叙事：**每到一个阶段遇到什么问题 → 有哪些候选方案 → 为什么选这个 → 付出的代价是什么**。
> 与《ADR-架构决策记录》的关系：ADR 是「决策的归档」（结论先行），本文是「决策的推理」（过程展开）。
> 视角：客观中立，聚焦技术事实与取舍逻辑。

---

## 阅读指引：三条主线

整个系统的架构演进，本质上是三条主线在推进：

1. **能力主线**：从「能对话」到「能编排多个 Agent 并行干活」（Multi-Agent 工作流）
2. **可靠性主线**：从「能跑」到「挂了不丢消息、坏了自动降级、慢了能熔断」（消息可靠性 + 熔断 + 对账）
3. **工程化主线**：从「单体脚本」到「微服务 + 配置中心 + 服务发现 + 可观测」（架构治理）

下面按时间线展开，每个阶段标注「问题 → 方案 → 取舍」。

---

## 阶段一：从单体到多服务（ADR-019 / ADR-001~005 铺垫）

### 遇到的问题

系统最初是单体应用：前端、AI 编排、LLM 接入、游戏、多模态挤在一个服务里。上线后暴露两个问题：

1. **内存压力**：单服务器承载全部组件，实测可用内存仅 822Mi，频繁 OOM
2. **故障域不分**：改一个功能要整体重启，一个模块挂了全站瘫

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 继续单体 + 加内存 | 简单 | 治标不治本，故障域不分 |
| B. 按技术栈微服务拆分 | 彻底解耦 | 过度设计，运维成本高 |
| C. **按「变更频率 + 资源边界」拆分** | 贴合实际 | 需想清楚边界 |

### 决策：方案 C，拆成 6 个服务

- `chat-core`：AI 编排（**变更最频繁**，独立部署）
- `chat-llm`：LLM 接入 + RAG + 知识图谱（**要独立扩容**）
- `chat-web`：HTTP/WS 接入层（**要扛并发**）
- `chat-games` / `chat-media`：独立业务域
- `chat-common`：公共库

**取舍代价**：拆服务带来分布式复杂度（跨服务调用、配置同步、部署编排），这些代价在阶段二~五逐步用「配置中心、服务发现、消息队列」来偿还。

> 关键判断：**不是按代码量切，是按变更频率和资源边界切**。这是「会不会过度设计」这一追问的根本答案。

## 阶段二：配置治理与模型接入（ADR-014 / ADR-012 / ADR-011）

### 遇到的问题

1. **配置三源分立**：`model_configs` 表（运行时源）+ `llm_*` 表（管理面源）+ Nacos YAML（兜底），改配置不知道改哪，直接导致过一次「豆包 404」事故（path 拼接重叠）
2. **模型厂商硬编码**：加一家新模型要改业务代码
3. **工具/存储硬编码**：工具启停、存储替换都要改代码发布

### 决策

1. **配置归一**：`model_configs` 退役，运行时统一读 `llm_*` 表，YAML 仅兜底（ADR-014）；后续演进为「DB 是 provider key 唯一真相源 + chat-core/chat-llm 双端每 60 秒定时刷新」，改 key 无需重启
2. **SPI 工厂**：`LLMProvider` 统一接口 + Spring 自动收集实现，加新厂商 = 加一个实现类（ADR-012 同范式推广到存储）
3. **工具平台化**：`ToolDefinition` 元数据 + DB 覆盖，工具启停零发布（ADR-011）

**取舍代价**：元数据「双源」（代码 + DB）需维护一致性，决策约定「DB 优先」。

> 这阶段的主题是「**把变化点抽象成可配置**」：厂商、工具、存储都是变化点，抽象后变化不再触碰核心链路。

## 阶段三：RAG 与意图识别（ADR-013 / ADR-015）

### 遇到的问题

1. **RAG 双体系并存**：legacy RAG（生产中在用）+ 新版多数据源 RAG（无调用方），维护成本翻倍
2. **意图识别慢**：单一 LLM 分类 200-1000ms，贵且慢

### 决策

1. **RAG 二选一**：保留 legacy，下线新版（ADR-013）——**敢于做减法**
2. **意图三层漏斗**（ADR-015）：L1 规则（0-1ms）→ L2 语义（30-80ms）→ L3 LLM（200-1000ms）串行降级，高置信结果回灌 L1/L2 自增强

**取舍代价**：L1/L2 冷启动依赖 ~420 条种子预加载。

> 关键判断：**「敢删」比「敢加」更难**。新版 RAG 代码看似先进，但无调用方就是死代码，留着只会增加心智负担和出 bug 面。

## 阶段四：Multi-Agent 工作流（ADR-016 / ADR-017 / ADR-018）— 最大亮点

### 遇到的问题

超长/跨域请求单 Agent 串行处理，耗时且输出冗长；且双实例下并发控制缺失。

### 决策（三层递进）

1. **树状辩论混合编排**（ADR-016）：LLM 动态拆视角 → Java `CompletableFuture` 并行 → 每视角一个 LangGraph 子图（含 Reflection）→ LLM 汇总
2. **Multi-Agent 并行工作流**（ADR-017）：`TaskPlanner` 拆 ≤9 子任务 → RabbitMQ 分发 → 双实例 `SubAgentWorker`×10 并行 → Redis 幂等聚合 → 收敛压缩 ≤1000 字
3. **可靠性加固**（ADR-018）：Reconciler ZSet 索引（O(N)→O(logN)）+ Worker DLX 死信指数退避重试

**取舍代价**：工作流状态依赖 Redis（AOF + DB 对账列为后续加固项）。

> 这三条 ADR 是「从能用到可靠」的典型演进：先有编排能力，再补并发控制，最后补对账和重试兜底。

## 阶段五：可观测性（ADR-008 / ADR-021 / ADR-022）

### 遇到的问题

Prometheus 告警只有系统层（宕机/内存/磁盘），业务运行质量（意图命中率、工作流降级、LLM 成本）无指标可查。

### 决策

1. 系统层告警（ADR-008）：Prometheus + Alertmanager + 钉钉
2. 业务指标（ADR-021）：`CoreBusinessMetrics` 埋点意图漏斗 + 工作流
3. **切面化**（ADR-022）：手写埋点 → AOP 切面，业务类零侵入

**取舍代价**：AOP 仅拦截外部 Bean 调用，同类自调用会绕代理（需保证切点跨类）。

> 关键判断：**可观测性代码不应该污染业务代码**。埋点从「手写」演进到「切面」，本质是把横切关注点从业务逻辑里剥离。

## 阶段六：安全加固（2026-08-16，对应 ADR-026）— 从「能用」到「可信」

### 遇到的问题

代码走查发现多处「文档承诺了、代码没做」的硬伤：

1. **方法级鉴权全缺失**：`@EnableMethodSecurity` 被注释，管理接口用明文 `String.equals` 比密码（存在时序侧信道）
2. **WebSocket 无鉴权**：握手只读 `userId` 不验 JWT，任何人可伪造 userId 订阅他人私有消息
3. **日志无脱敏**：JWT、OSS 签名 URL、密钥直接打进日志
4. **硬编码默认密码**：DB/中间件默认口令写死在配置里
5. **文件上传无类型校验**：可上传任意脚本/可执行文件
6. **内容安全 fail-open**：检测服务异常时放行，且只检输入不检输出

### 决策

1. **恢复方法级鉴权**：`@EnableMethodSecurity(prePostEnabled=true)` + 管理密码改 `MessageDigest.isEqual` 常量时间比较
2. **WebSocket 双层鉴权**：握手验 JWT（宽容匿名）+ 私有 topic 订阅级鉴权（`ChannelInterceptor`）
3. **日志脱敏**：logback 自定义 `MaskingMessageConverter`，`%msg` → `%maskedMsg`
4. **删默认密码**：改环境变量注入 + 移除 gitleaks 对 docker-compose 的豁免
5. **上传类型白名单 + OSS SSRF 防护**：扩展名白名单 + 内网地址拦截（含 DNS 重绑定）
6. **内容安全 fail-close + 输出检测**：异常不再放行，LLM 输出侧检测 + 命中跳过缓存/记忆写入

**取舍代价**：
- WebSocket 鉴权采用「宽容握手 + 订阅级鉴权」而非「强制握手」，是为了**不破坏首页在线人数、监控面板的匿名订阅**——这是「安全」与「可用性」的权衡，最终选择在订阅层堵漏洞而非握手层一刀切
- 输出检测不阻断流式内容（流式已实时推送），而是作用于缓存/记忆等复用链路——承认流式架构的固有特性

## 阶段七：弹性伸缩与服务发现（2026-08-16，对应 ADR-027）— 从「静态配置」到「动态拓扑」

### 遇到的问题

web 实例数写死在 Nginx `upstream`（`ip_hash` + 固定 8081/8082），core 双实例靠 web 侧手动配 `base-urls`。想扩缩容必须改配置 + 手动 reload，且发现「health-check.sh 还在守护已废弃的 8082」导致幽灵实例。

### 决策

1. **Nacos 服务发现**（已引入，正式启用）：每个服务实例启动自动注册、心跳超时自动摘除
2. **动态 upstream 同步器**（`nacos-upstream-sync.sh`）：周期拉取 Nacos 健康实例 → 生成 Nginx upstream → 有变化才 reload
3. **负载均衡策略 `ip_hash` → `least_conn`**：放弃粘性，改用最小连接数（长连接 WebSocket 场景更均衡）
4. **弹性扩缩容控制器**（`web-scale.sh` + health-check 标记机制）：想 1 个实例就 1 个，压力大了 `scale-up` 一键扩容

### 关键取舍：为什么放弃粘性（ip_hash）？

- `ip_hash` 的本意是「同一用户始终连同一台 web」，避免 WebSocket 连接漂移
- 但 `ip_hash` 与「动态增减节点」**天然冲突**：节点增减时哈希环变化，已有连接会漂移
- 更根本的原因：**本项目已有跨节点广播机制**（`BroadcastService` + RabbitMQ `cross-node` 交换机 + `_nodeId` 标识），结果无论在哪个节点生成，都能推回真正持有用户连接的节点——所以「粘性」不是必需的
- 因此选 `least_conn`：纯轮询 + 最小连接，动态扩缩容最简单、负载最均衡

> 关键判断：**粘性（sticky）是「没有跨节点通信能力时的权宜之计」**。一旦有了跨节点广播，粘性反而成为动态扩容的障碍。

## 演进规律总结

回看这七个阶段，能抽象出几条贯穿始终的设计原则：

1. **变化点要抽象**：厂商、工具、存储、配置，凡是会变的，都抽象成可配置/可插拔
2. **可靠性靠「兜底」而非「假设不出错」**：对账、死信重试、熔断、fail-close，都是「默认会出错」的设计
3. **可观测性不污染业务**：埋点切面化，横切关注点剥离
4. **「敢删」与「敢加」同样重要**：死代码要删（ADR-013），该补的兜底要补（ADR-018）
5. **权衡要显式化**：安全 vs 可用性（宽容握手）、粘性 vs 动态（least_conn），每个取舍都记录代价
