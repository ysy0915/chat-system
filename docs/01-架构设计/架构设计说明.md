## 2. LLM 调用架构

### 2.1 策略模式

```
                    ┌──────────────────┐
                    │  LLMClient        │  ← Fluent Builder API
                    │  (场景化调用)       │
                    └───────┬──────────┘
                            │ 委托
                    ┌───────▼──────────┐
                    │  LLMInvoker       │  ← 熔断 / 自愈 / 链路追踪
                    └───────┬──────────┘
                            │ 调用
          ┌─────────────────▼─────────────────┐
          │ LlmBundleClient / DirectLLMClient │  ← 统一多模型入口 / 降级直连
          └─────────────────┬─────────────────┘
                            │ 可路由至
          ┌─────────────────▼─────────────────┐
          │ chat-llm 独立服务 多 Provider      │  ← OpenAI 兼容 / OpenAI SDK / 豆包
          │ OpenAICompatProvider · OpenAISdk…  │
          └───────────────────────────────────┘
```

### 2.2 调用层次

| 组件 | 职责 | 使用者 |
|------|------|--------|
| `LLMClient` | Fluent Builder、场景配置预设 | 业务层 |
| `LLMInvoker` | 熔断、链路追踪、自愈重试 | LLMClient |
| `LlmBundleClient` | 统一多模型调用入口（对接 chat-llm 独立服务） | LLMInvoker |
| `DirectLLMClient` | 降级 HTTP 直连调用（未注入/熔断时） | LLMInvoker |
| chat-llm Provider | OpenAI 兼容 / OpenAI SDK / 豆包 多 Provider 注册 | LlmBundleClient |

### 2.3 动态配置（Nacos）

`LLMClientConfig` 通过 `@RefreshScope` 支持运行时调整：
- 重试次数 / 退避间隔
- 超时时间
- 各场景的 temperature / max_tokens / top_p
- 修改 Nacos 配置后无需重启，刷新间隔内自动生效

chat-llm 模块的弹性参数（`invoke-timeout-seconds` / `max-retries` / `retry-backoff-millis`）与 Resilience4j 熔断/重试/限流/超时配置均可在 Nacos 共享配置中调整。

### 2.4 chat-llm 独立 LLM 服务

#### 模块定位

chat-llm 是独立的 LLM 微服务（REST :9095 / gRPC :9195），承接全部 LLM 能力，与 chat-core 解耦：

| 能力 | 实现 | 说明 |
|------|------|------|
| 多 Provider 调用 | `LLMProviderRegistry` + `OpenAICompatProvider` / `OpenAISdkProvider` | REST (OpenAI 兼容) 与 OpenAI SDK 两种接入方式，支持 DeepSeek / 千问 / 豆包 |
| 图执行引擎 | `GraphExecuteService` | 自研 LangGraph 风格引擎：逻辑节点、并行分支、状态写入、重试自愈、流式事件；条件路由支持数值比较（`gt/gte/lt/lte/ne/eq`）+ 模板变量（`{{state.xxx}}`），节点索引 O(1) 查找 + 环告警 |
| RAG 检索增强 | `RagService` + Milvus/Pinecone 适配 | 多数据源路由、Embedding、文档分块、结果融合 |
| 模型管理面 | `LlmProviderAdminService` + `LlmRoutingRepository` / `InMemoryLlmRoutingRepository` | `/api/v1/llm/admin/providers` 增删改查：DB 三表（生产）或纯内存（standalone）实现 |
| 对话记忆 | `ConversationMemoryService` + `MemoryKVStore`（Redis / `InMemoryMemoryKVStore`） | 短期/长期记忆，`/internal/rag/memory/*` |
| 用户画像记忆 | `UserFactMemoryService` + `FactExtractor` | LLM 抽取用户事实，Milvus 或内存召回 |
| 知识图谱 | `KnowledgeGraphService`（Neo4j）+ `InMemoryKnowledgeGraphService` | 三元组抽取 + 图谱查询，`/internal/graph/*` |
| gRPC 服务 | `LlmLangGraphGrpcService` / `RagGrpcService` | 图执行与 RAG 的 gRPC 接口（:9195） |
| 弹性能力 | Resilience4j 熔断/重试/限流/超时 | 按 Provider 维度隔离 |
| 可观测性 | `LlmMetrics` + `TracingGrpcInterceptor` | Prometheus 指标 + gRPC TraceId 透传 |

#### Standalone 纯内存模式（2026-08-14）

`--spring.profiles.active=standalone` 时，chat-llm 可**零外部依赖直接启动**（无需 MySQL/Redis/Neo4j/Milvus），四大能力全部走纯内存实现，数据重启即清空：

| 能力 | 内存实现 | 配置开关 |
|------|---------|---------|
| 模型管理面 | `InMemoryLlmRoutingRepository` | `app.llm.admin.memory=true`（`app.mapper-scan.enabled=false` 关 MyBatis） |
| RAG 检索 | `InMemoryVectorStoreService` + `InMemoryRAGRepository`（余弦相似度 TopK） | `app.rag.enabled=true` + `app.rag.backend=memory` |
| 对话记忆 | `InMemoryMemoryKVStore`（短/长期）+ `InMemoryUserFactMemoryService`（画像） | `app.rag.backend=memory` |
| 知识图谱 | `InMemoryKnowledgeGraphService` | `app.knowledge-graph.backend=memory` |

启动方式：`java -jar chat-llm-0.0.1-SNAPSHOT.jar --spring.profiles.active=standalone --server.port=9095`。API Key 经环境变量注入（`DEEPSEEK_API_KEY` / `QWEN_API_KEY` / `DOUBAO_API_KEY`，standalone 向量化缺省回退 `QWEN_API_KEY`，可单独配 `EMBEDDING_API_KEY`），或启动后经模型管理面 API 动态添加。生产环境请保持默认 `milvus` / `neo4j` backend 并接入 MySQL——**生产下 provider key 的唯一真相源是 DB `llm_provider_props` 表**（chat-llm / chat-core 均从 DB 加载并每 60 秒定时刷新，改 key 无需重启；`.env` 的 `*_API_KEY` 仅作 standalone/DB 故障兜底；`DASHSCOPE_API_KEY` 例外，用于 RAG 向量化 embedding 不走 DB）。详见 `chat-llm/STANDALONE.md`。

#### 与 chat-core 的协作

```
chat-core (业务编排)
  ├── LlmBundleClient ── HTTP REST (SSE) ──▶ chat-llm (:9095)
  │     ├── POST /api/v1/chain/invoke        非流式调用
  │     ├── POST /api/v1/chain/stream        SSE 流式 (逐 token)
  │     └── POST /api/v1/chain/graph/stream  图执行流式
  │                                              ├── Provider 调用 (同步/SSE 流式)
  │                                              ├── 图执行 (LangGraph 风格)
  │                                              └── RAG 检索生成 (gRPC :9195 亦开放)
  │
  └── RagClient (Java 11 HttpClient) ──▶ chat-llm (:9095)
        ├── POST /internal/rag/search        知识库向量检索 (legacy kbId 模型)
        ├── POST /internal/rag/embed         文本向量化 (1024 维)
        ├── POST /internal/rag/memory/*      对话记忆存取
        └── POST /internal/rag/invoke(-stream)  RAG 回答 (SSE 流式)
```

- chat-core 负责业务编排（辩论、树洞、意图识别），通过 `LlmBundleClient`（HTTP）调用 chat-llm，chat-llm 专注 LLM 协议适配、provider 路由与熔断/重试/限流弹性
- chat-llm 的 baseUrl 由 `BundleLlmProperties` 配置（`--app.bundle.base-url`），本机指向 `http://127.0.0.1:9095`
- gRPC (:9195) 为 chat-llm 对外开放的图执行 / RAG / 管理通道
- 降级路径：chat-llm 不可用时 chat-core 内 `DirectLLMClient` 直连兜底
- **RAG / 知识图谱运行时（2026-08 迁移）**：旧版 RAG 代码已从 chat-core 迁至 chat-llm（`rag/legacy` 包，兼容 kbId 模型与 1024 维向量），chat-core 经 `RagClient` 跨进程调用；chat-web 的知识库管理 API（`/api/v1/rag/*`）由 `CoreClient` 代理到 chat-llm，地址由 `app.llm-service.base-url` 配置（本机 `http://127.0.0.1:9095`）
- **两套 Embedding 并存**：新版 `EmbeddingService`（text-embedding-3-small / 1536 维）服务新版多数据源 RAG；`LegacyEmbeddingService` / `IntentEmbeddingService`（1024 维）分别服务旧知识库与意图识别 L2 语义匹配，维度互不兼容故独立实现
- **对话自动 RAG（2026-08）**：个人对话 / 群聊经 `ChatProcessor.shouldAutoRag` 三层判定（① 开关配置 `app.rag.chat.enabled` + `kb-id>0` → ② 意图 `KNOWLEDGE_QA`/`TASK_EXECUTION` → ③ 排除实时/个人数据查询），命中后经 `RagClient.search` 检索默认知识库（top-k 3、相似度 ≥0.3、≤2000 字符），【参考资料】注入 system prompt 增强生成；知识库为空 / 未命中 / 检索失败自动降级普通回答
- **树洞用户画像（2026-08）**：`/internal/rag/memory/save` 保存对话后异步调用 LLM（qwen/qwen-plus）提炼情景/情绪/偏好，Redis `user_profile:{scene}:{userId}` TTL 30 天增量合并；`buildMemoryContext` 注入【用户画像】段落，回答贴合用户偏好

## 3. 意图识别 — 三层漏斗

```
用户输入
  │
  ▼
┌──────────────────────────┐
│  IntentFunnelEngine      │ 编排器，串行降级
└───────────┬──────────────┘
            │
┌───────────▼──────────────┐  命中率 15-25%  ·  0-1ms
│ L1: RuleBasedMatcher     │  规则引擎
│   · Trie 关键词扫描       │  33 条规则 (10 类意图全覆概率)
│   · Regex 预编译匹配      │  CREATIVE_WRITING / KNOWLEDGE_QA
│   · 状态机 (多轮命令流)   │  EMOTIONAL_SUPPORT 等已补齐
│   · batchAddRules 热追加  │  种子池关键词实时注入
└───────────┬──────────────┘
            │ 未命中 ↓
┌───────────▼──────────────┐  命中率 80-90%  ·  30-80ms
│ L2: ContextMatcher       │  上下文语义匹配
│   · Embedding → k-NN     │  「接住九成常规意图」
│   · ~421 条种子预加载     │  intent-seeds.json 启动时灌入
│   · 动态阈值滑动窗口     │  每意图 HIT_RATE → ±0.02 自适应
│   · 增强上下文消歧       │  多轮同主题 / 代码场景 / 情绪连续性
│   · nprobe 动态自适应     │  小集合32 / 中等16 / 大集合8
└───────────┬──────────────┘
            │ 未命中 ↓
┌───────────▼──────────────┐  命中率 < 10%  ·  200-1000ms
│ L3: ToolIntentMatcher    │  深度语义层
│   · LLM 分类 (qwen-turbo)│  「意图 → 执行」打通
│   · MCP 工具执行 (预留)   │  兜底 UNKNOWN
└──────┬───────────────────┘
       │ 高置信 (≥0.80)
┌──────▼───────────────────┐  反馈闭环 (异步)
│ SeedPool                 │  积累 100条 / 每10分钟
│   ├→ Milvus (强化 L2)     │  写入 intent_examples
│   └→ Trie  (强化 L1)     │  提取关键词 → 规则引擎
└──────────────────────────┘
```

### 3.1 设计要点

| 设计 | 说明 |
|------|------|
| 规则全意图覆盖 | 33 条规则覆盖 10 类意图，L1 命中率 15-25% |
| 种子预加载 | `intent-seeds.json` ~421 条启动时自动灌入 Milvus，解决冷启动 |
| 动态阈值调优 | 滑动窗口 (1000条) 追踪每意图命中率，自动 ±0.02 调节阈值 |
| 增强上下文消歧 | 多轮同主题 (+0.05) / 代码场景降权 (-0.03) / 情绪连续性 (+0.03) |
| nprobe 自适应 | 集合 <1000→nprobe=32, <5000→16, ≥5000→8 |
| 反馈闭环 | L3 高置信结果 → SeedPool → 定时灌入 L2 (Milvus) + L1 (Trie) |
| 质量监控 | 每意图命中率 / 动态阈值快照 / 种子池队列 / 冷启动率 |
| 多级 TF-IDF | 阈值从 tf>0.2 降为三级 (0.05/0.08/0.15)，规则挖掘量提升 5× |
| 意图→参数路由 | `IntentRoutingHelper` 按意图动态调整 temperature |
| 三层容错 | 每层失败自动降级到下一层，不阻塞主流程 |

```

```

### 4.2 多实例就绪探针

`ReadinessHealthIndicator` 暴露 `/actuator/health/readiness`：
- 验证 Redis 读写能力
- 确认 Session 追踪器可正常工作
- Kubernetes / 负载均衡可根据此探针判断实例是否就绪

### 4.3 水平扩展能力

| 组件 | 状态管理 | 多实例安全 |
|------|---------|-----------|
| chat-web | Session → Redis Hash | ✅ 生产弹性伸缩（8081 默认 + Nacos 动态 upstream） |
| chat-core | 无本地缓存 | ✅ 生产双实例 (9090/9092) |
| chat-llm | 无状态任务（弹性能力按 Provider 隔离） | ✅ |
| chat-games | 游戏状态 → Redis | ✅ |
| chat-media | 无状态任务 | ✅ |

### 4.4 双 core 部署要点（生产 9090 + 9092）

| 要点 | 实现 | 说明 |
|------|------|------|
| web 轮询 | `--app.core.base-urls=http://127.0.0.1:9090,http://127.0.0.1:9092` | `CoreClient` 启动时解析逗号分隔列表并入 `coreUrls`，普通请求轮询 |
| stop 广播 | `CoreClient.broadcast(path, payload)` | stop 需命中承载该 reqId 的实例，广播到所有 core，任一成功即成功、全失败才抛异常 |
| autoChat 主实例 | `ModelAutoChatService` 校验 `server.port == "9090"` | 定时自动问答仅主实例执行，避免双实例重复广播、重复入库 |
| nodeId 固定 | `CrossNodeConfig.nodeId()` 返回 `node-{serverPort}` | 重启后 RabbitMQ 队列名不变（`cross-node-{nodeId}`），杜绝每次重启生成带 UUID 新队列导致队列堆积 |
| 精确重启 | `restart-core.sh [9090|9092|all]` | 按 `server.port` 精确 pkill，不误杀另一实例 |
| 内存分配 | 主 9090 `-Xmx768m`，从 9092 `-Xmx512m` | 9091 被 milvus-standalone 容器占用不可用，Prometheus UI 用 9094 |

> **Session 失忆修复（"回答完就断开"）**：根因是 `ChatHistoryBuilder.buildGroup` 不加载历史对话，导致多轮会话跨实例后上下文丢失。已修复为复用 `buildFromRecent` 加载近期消息，个人对话/树洞恢复上下文记忆。

## 5. 思考链展示 (Thinking Chain Display)

### 5.1 架构位置

思考链位于 LLM 流式输出管道中，在 ChatProcessor / TreeHoleService 与 WebSocket 之间：

```
LLM (流式输出)
    │
    ▼
ThinkingStreamParser (状态机分离 <thinking> 标签)
    │
    ├── thinking_token  →  WebSocket → 前端灰色展示
    └── stream_token    →  WebSocket → 前端正常展示
    └── answerCollector →  DB 存储（纯回答，不含思考链）
```

### 5.2 ThinkingStreamParser 状态机

逐 token 解析的三态状态机，核心代码位于 `chat-core/.../intent/funnel/ThinkingStreamParser.java`：

| 状态 | 行为 |
|------|------|
| `NORMAL` | feed token → 缓冲并 emit answer token；遇到 `<thinking>` 切换 |
| `IN_TAG` | feed token → 缓冲并 emit thinking token；遇到 `</thinking>` 切换 |
| `TAG_CLOSED` | feed token → 直接 emit answer token |

**关键设计**：
- `emitSafe()` 只缓冲最后 11 个字符（`</thinking>` 长度），其余即时 flush → 零延迟
- 300 字符安全阈值：LLM 未输出 `<thinking>` 时自动切非思考模式
- `markAsNonThinking()` 手动降级接口

## 6. LangGraph4j 辩论编排

### 6.1 概述

依赖 `org.bsc.langgraph4j:langgraph4j-core-jdk8:1.0-beta1` 实现 LLM 辩论的有向无环图编排，替代硬编码的循环逻辑。分两种辩论模式：

| 模式 | 实现 | 图类型 |
|------|------|--------|
| 标准辩论 | `DebateGraphService` + `DebateState` | 单一 `StateGraph`，N 轮循环（默认 3，可选 1~10） |
| 树状辩论 | `TreePerspectiveGraphService` + `TreePerspectiveState` | **混合模式**：Java 上层并行 + 每视角一个 LangGraph 子图 |

### 6.2 标准辩论图（多模型组队 + Reflection 反思循环）

```
START → debate(N 方并行) → reflect(N 方批判性反思) → shouldContinue ─┬─ true → debate（下一轮）
                                                                     └─ false → summary → END
```

- 模型数由前端 `model_count` 参数透传（`DebateProcessor.resolveDebateModels`，默认 3，限 3~6）：从已配置 chat 模型随机抽取 N 个，动态分配参与者 id 0..N-1，整合模型 id=N；树状模式固定 3 个且排除本地 Ollama 慢模型
- 轮数由前端 `rounds` 参数透传（`DebateGraphService.execute(reqId, userId, topic, rounds)`，限 1~10，默认 3），`maxSteps` 与 `state.maxRounds` 随之动态化
- **Reflection 反思节点**：每轮辩论后 N 方各自审视「自己观点 + 对方观点」，输出「1) 我被反驳得有道理的点 2) 是否修正 3) 修正后的立场」，写入 `proReflections / conReflections / neutralReflections`
- **裁决式汇总**：`summary` 基于反思后的最终立场（`{{state.proReflections[-1]}}` 等）输出【正方强调 / 反方强调 / 中立评价 / 关键分歧 / 共识结论】，替代原先的机械归纳
- **模型名中文展示**：`ModelRouter.modelDisplayName(provider, model)`（豆包/千问/DeepSeek/Kimi/自研 hermes3 等），`round_start` 事件携带 `model_ids` 供前端渲染
- **提示词增强（2026-08-15）**：debate 分支 prompt 注入「对方上一轮反思立场」`{{state.conReflections[-1]}}`（反方/中立类推）与「历史辩论记忆」`{{state.historySummary}}`，reflect 分支新增"对方立场是否影响我的判断"自我审视；仅取 `[-1]` 负索引、窗口定长 ≤200 字，零 token 增长
- **Redis 外存记忆（2026-08-15）**：`debate:memory:{userId}:{topicHash}`（TTL 7 天）JSON 定长窗口跨会话保存各方最后一条反思立场，同话题二次辩论首轮即注入 `historySummary`；无 Redis 时静默降级不 NPE
- **reflect 事件可见（2026-08-15）**：reflect 节点 `branch_start`/`branch_end` 广播 `reflecting` WS 事件，前端展示反思提示，消除「第二轮启动慢」静默期

- `DebateState`：topic、round、history、summary
- `DebateGraphService`：节点内联构建（debateNode N 方并行 / shouldContinue 条件路由 / summaryNode）→ `compile()` → `invoke()`
  > 节点逻辑已内联到服务内，`DebateNodes` 类已废弃删除

### 6.3 树状辩论 — Plan-and-Execute 混合图

树状辩论因视角数量由 LLM 运行时动态决定，无法用单一 `StateGraph` 表达。采用 **Plan-and-Execute 混合模式**：先由 LLM 生成执行计划（拆解视角），再并行执行各子任务（视角辩论），最后汇总执行结果。

```
DebateTreeProcessor.runTreeDebate()
  ├── decompose()  ← Plan：Java: LLM 拆解 → 2-3 视角（生成执行计划）
  ├── 并行视角 (CompletableFuture)  ← Execute：并行执行各子任务
  │   for each perspective:
  │     TreePerspectiveGraphService.execute()    ← LangGraph 子图 (节点内联)
  │       ├── debateNode            ← N 方并行
  │       ├── reflectNode           ← N 方批判性反思（Reflection 循环）
  │       ├── shouldContinue        ← 条件路由
  │       └── summaryNode           ← 视角总结（基于反思后立场）
  └── aggregate()                    ← Java: 各视角结论 → LLM 汇总（汇总执行结果）
```

**为什么不全图**：LangGraph4j 的 `StateGraph` 节点编译时固化，但视角数量运行时决定，全图需要预定义 3 条并行分支 + 条件跳过，灵活性和可维护性不如混合模式。

```
├── TreePerspectiveState.java     # 树状单视角状态
```

## 7. Multi-Agent 并行工作流（2026-08 新增）

超长/跨域请求不再单 Agent 串行处理，而是 **TaskPlanner → RabbitMQ → 双实例 Worker 并行 → 收敛** 的编排链路，将一次 LLM 长回答拆解为 N 个独立子任务并行执行，大幅压缩复杂任务耗时与输出。

```
请求 (chat-core)
  ├── TaskPlanner.shouldDecompose()   ← 判定：长度 ≥ min-length 且可拆解（否则普通流程）
  ├── tryAcquirePermit()              ← Redis Lua 原子限流：全局并行工作流 ≤ max-concurrent=8
  │     超限 → 降级普通流程（不排队、不拒绝）
  ├── TaskPlanner.buildPlan()         ← LLM 拆解 2-9 个子任务（每任务独立极短上下文）
  ├── startWorkflow()                 ← 计划/meta/total 写入 Redis + 前端推送 PLAN_START
  ├── RabbitMQ 分发 (agent.subtask.exchange)  ← 逐个子任务入队
  │     ┌───────────────────────────────────────────────┐
  │     │  双实例 Worker (SubAgentWorker, 各 10 并发)     │
  │     │  manual ack + prefetch=1 → 按真实能力公平分发    │
  │     │  执行 → 回传 SubAgentResult 到结果队列            │
  └─────┴───────────────────────────────────────────────┘
             ↓
  SubTaskResultCollector  ← 结果 hash 幂等聚合 + received INCR + 进度推送
  ├── received ≥ total → SETNX 收敛锁（双实例只收敛一次）
  └── AgentWorkflowOrchestrator.converge()  ← 主 Agent 汇总 → 压缩输出 ≤ 1000 字 → 完整收尾
```

### 关键机制

| 机制 | 说明 |
|------|------|
| **Redis Lua 原子限流** | `agent:workflow:active` 用 INCR/DECR Lua 脚本原子计数，双实例合计不超过 `max-concurrent=8`；超限自动降级普通流程。修复了早期 Semaphore 跨实例 acquire/release 错配（9092 释放 9090 的许可导致计数异常） |
| **manual ack + prefetch=1** | Worker 忙时不 ack 不拉新消息、空闲即拉，天然按真实能力均衡分发（避免预取模式下快实例空等）；子任务执行中挂掉由 RabbitMQ requeue 自动重投，不丢失 |
| **Redis 结果聚合** | 结果按 `taskId` 幂等覆盖写 `agent:subtask:result:{planId}` hash；`received` INCR 原子计数；SETNX 锁保证双实例只收敛一次 |
| **WorkflowReconciler 对账** | 每 30s 扫描 Redis 中"结果已齐但收敛未完成"的 plan 并重新触发收敛，兜底"收敛中途崩溃重启后卡死"的盲区；以 `converged` 标记 + DB 状态双重去重 |
| **失败语义** | Worker 执行失败回传失败结果 + `basicNack(requeue=false)`（防无限重试重复计数）；Collector 处理失败 `requeue=true`（结果丢失会导致收敛永远等不到） |
| **输出压缩** | 收敛调用轻量模型（qwen-turbo）汇总，`converge-max-chars` 硬截断兜底，最终回答 ≤ 1000 字 |

### 代码位置

