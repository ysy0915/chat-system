## P2 场景来源：问题从哪来

**现实观察**：
- 大模型越来越聪明，但用户只能听到"一个 AI"的回答，存在立场单一、推理黑盒、参数僵化的问题
- 真实决策场景（投资、选题、争议性话题、职业规划）需要**多角度、可验证、可追问**的论证
- 现有产品把聊天、绘画、视频、游戏割裂在不同 App，用户需要在多个平台之间复制粘贴
- 模型调用不稳定，高峰期经常超时 / 限流，直接影响线上服务体验

**场景来源**：
- 来源于对现有 AI 助手类产品"单声道输出"的反思
- 来源于对群体决策、辩论式学习、创意发散等场景的真实需求
- 来源于 AIGC 时代用户对"AI 可解释、可协作、可娱乐"的一站式诉求

## P3 用户痛点：6 大核心问题

| 痛点 | 用户感受 | 造成的后果 |
|------|---------|-----------|
| **单一模型偏见** | "AI 总是站在一个角度说话" | 观点片面，容易形成确认偏误 |
| **推理黑盒** | "它为什么这么说我不知道" | 无法判断结论可信度 |
| **意图识别粗暴** | "简单闲聊和复杂问题用一样的语气" | 响应慢、参数不匹配、体验差 |
| **能力孤岛** | "聊天、画画、做视频要在不同 App 完成" | 数据不互通、操作成本高 |
| **稳定性焦虑** | "生成到一半卡住了" | 用户流失、信任下降 |
| **安全与体验失衡** | "防刷太严影响正常用，不防又被滥用" | 运营压力大 |

## P4 核心洞察：为什么是「多模型辩论」

**一句话讲清价值**：
> 单一 AI 会犯错、会偏执、会被「一本正经地胡说八道」蒙混过去。
> 但当 6 个不同厂商、不同立场的 AI 围绕同一个问题互相质疑、反驳、修正时，
> **偏见被对冲，错误被暴露，结论更接近真相。**

**这解决了大模型最根本的三个问题**：
| 单一模型的缺陷 | 多模型辩论的对策 |
|--------------|----------------|
| 立场单一 → 确认偏误 | 正/反/中立多立场对冲 |
| 推理黑盒 → 无法验证 | 观点互相质疑、逐条反驳 |
| 幻觉 → 无从察觉 | 一个模型的幻觉会被另一个模型当场戳穿 |

**为什么这比「更好的单个模型」更可行**：
- 不用训练更贵的大模型，而是**用现有的多模型组合出超越单模型的效果**
- 成本可控（模型池灵活配置），效果可解释（每个观点都有出处和反驳）

## P5 解决方案：产品定位与核心思路

**产品定位**：
博思AI智能体是一个「多模型智能协作平台」，核心理念是：
> 不只一个 AI 回答你，而是一群 AI 一起帮你。

**解决思路（以辩论为主线，其他能力为支撑）**：
1. **多模型辩论（核心）**：从已配置 chat 模型随机抽取 3~6 个模型（模型数可自选）组队，分别扮演正方/反方/中立等立场，展开多轮辩论
2. **问题动态拆解**：对复杂问题自动拆成 2-3 个分析视角，形成树状论证网络（让辩论有结构、有深度）
3. **意图分级识别**：快速判断用户意图，按场景调参，复杂问题才走 LLM 深度链路（支撑辩论的快速响应）
4. **思考链透明化**：把 AI 的推理过程实时展示给用户（让「AI 为什么这么说」可见）
5. **AI 错误自愈**：模型故障时自动切换/重试/降级，保证服务可用（支撑多模型调度的稳定性）
6. **一站式能力整合**：聊天、辩论、创作、游戏统一入口（辩论的配套生态）

## P6 产品形态：一站式 AI 平台

**前端形态**：Web SPA（React + Vite）
- 13 个功能页面：首页、观点辩论场、知识脉络图、个人对话空间、情绪树洞、AI 伙伴群聊、图片与视频、3D 模型生成、AI 多人游戏、问答列表、个人信息、模型管理、知识库
- 响应式布局，支持桌面端与移动端双指缩放

**后端形态**：6 个微服务 + 1 个前端
- `chat-core`：AI 核心引擎（辩论、意图识别、思考链、RAG、Agent 工具）
- `chat-web`：Web 接入层（认证、限流、WebSocket、路由）
- `chat-llm`：独立 LLM 服务（多 Provider、自研图执行引擎、RAG、gRPC）
- `chat-games`：AI 多人游戏
- `chat-media`：多模态生成（图/视频/3D）

**部署形态**：Docker + Docker Compose + 双服务器架构
- 主服务器：Nginx + Redis + RabbitMQ
- Milvus 服务器：Java 服务 + Nacos

## P7 核心流程：从用户输入到多模型输出

### 流程一：普通 AI 对话

```
用户输入
  │
  ▼
[意图识别三层漏斗]
  L1 规则匹配（0-1ms）
  L2 语义匹配（30-80ms，Milvus k-NN）
  L3 LLM 分类（200-1000ms，兜底）
  │
  ▼
[按意图路由]
  闲聊 → 低 temperature
  代码 → temperature 0.2
  创意 → temperature 0.95
  推理 → 开启思考链
  │
  ▼
[LLM 调用 + 工具调用]
  实时流式输出
  错误自愈（换模型/重试/降级）
  │
  ▼
前端展示：answer_token / thinking_token
```

### 流程二：树状辩论

```
用户输入
  │
  ▼
[LLM 语义拆解]
  复杂问题 → 2-3 个分析视角
  │
  ▼
[视角并行]
  视角A（豆包×DeepSeek×千问，3轮辩论 + 每轮反思修正）
  视角B（豆包×DeepSeek×千问，3轮辩论 + 每轮反思修正）
  视角C（豆包×DeepSeek×千问，3轮辩论 + 每轮反思修正）
  │
  ▼
[LLM 综合汇总]
  形成最终结论 + 理由 + 建议
  │
  ▼
前端展示：可拖拽 DAG 树图 + 节点连线 + 结论面板
```

## P8 Agent 能力：博思AI 能做什么

### 7.1 多模型 Agent 群聊

- 多个 AI 模型同时参与公开聊天室
- 每个模型有自己的角色设定和人格参数
- 用户 @ 某个模型或让模型自由讨论

### 7.2 辩论 Agent

- **标准辩论**：多模型随机组队（3~6 个可选，默认 3），场次可选（默认 3 轮，1~10）
- **树状辩论**：Plan-and-Execute 范式 —— LLM 拆解视角（计划）→ 每视角 3 个快模型独立辩论（执行）→ 综合汇总
- 立场角色动态分配、模型数/轮次可调、结论可解释

### 7.3 工具调用 Agent（ReAct 范式）

内置四类工具，LLM 根据意图自主决定是否调用（思考 → 行动 → 观察 循环，即 ReAct / function calling）：

| 工具 | 用途 |
|------|------|
| Calculator | 数值计算 |
| Weather | 天气查询 |
| Time | 时间查询 |
| KnowledgeSearch | 知识库检索增强 |

### 7.4 创作 Agent

- 文生图 / 文生视频 / 图生 3D
- 多模态生成服务独立部署，按需扩容

### 7.5 游戏 Agent

- 城堡围攻：AI 领主积分 + 兵力招募 + 实时对战
- 蛇王争霸：多人贪吃蛇
- AI 乒乓球：与 AI 对战

## P9 工具 / 数据 / 模型使用方式

### 8.1 模型使用

| 用途 | 模型 | Provider |
|------|------|----------|
| 通用对话、知识问答 | 千问 (qwen-turbo / qwen-plus) | 阿里云 |
| 辩论场模型池（随机组队） | 已配置 chat 模型：豆包 / DeepSeek / 千问 / 自研 Ollama 等 | 多厂商 |
| 代码推理 | DeepSeek-V3 / DeepSeek-R1 | DeepSeek |
| 创意生成 | 豆包 | 火山引擎 |
| Embedding 语义检索 | text-embedding-v3 | 阿里云 |
| 多模态生成 | 文生图/视频/3D 专用模型 | 对应厂商 API |

**路由策略**：
- chat-llm 多 Provider 注册（`OpenAICompatProvider` / `OpenAISdkProvider`）
- 支持 OpenAI 兼容格式与豆包专用格式
- 通过 Nacos 动态配置 temperature / maxTokens / persona

### 8.2 数据使用

| 数据类型 | 来源 | 用途 |
|----------|------|------|
| 用户对话历史 | MySQL | 查询历史记录、生成摘要 |
| 用户短期/长期记忆 | Redis + Milvus | 24h 短期对话 + 长期向量记忆 + 用户画像（情景/情绪/偏好） |
| 知识库文档 | 用户上传 PDF/Word/TXT | Milvus 向量检索增强 |
| 意图示例 | 历史对话 + 自动挖掘 | Milvus intent_examples 集合 |
| 限流/拉黑记录 | Redis | 安全策略计数 |

### 8.3 工具使用（ReAct 循环）

```
Agent 决策 → 调用 ToolDispatcher → 执行工具 → 观察结果 → LLM 再决策（最多 3 轮）→ 最终回答
```

- 工具描述注入 prompt，LLM 自主判断是否需要调用（ReAct：Reasoning + Acting 交替）
- 工具结果以 `tool` 角色消息回填上下文，送入下一轮生成，直到 LLM 不再请求工具或达到 `maxToolCalls`

## P10 合规边界

### 9.1 内容安全

- 两道防线：通用闸门（本地敏感词库 + 阿里云内容安全 Green API，fail-close）+ 大模型自检（chat-llm native guardrail 可插拔 SPI）
- 发消息前输入侧检测 + LLM 生成后输出侧检测
- 色情、暴力、政治敏感、违禁内容自动拦截
- 情绪树洞等模块额外做情感极性保护

### 9.2 数据与隐私

- JWT 认证 + 用户级会话隔离
- 个人对话内容不跨用户共享
- 思考链仅实时展示，不持久化存储
- 用户上传知识库文档按用户空间隔离

### 9.3 安全防护

| 策略 | 说明 |
|------|------|
| IP 限流 | 600 次/分钟 |
| 用户限流 | 20 次/分钟、200 次/小时 |
| 自动拉黑 | 1000 次/60s 触发，封禁 10 分钟 |
| UA 过滤 | 拦截 curl/wget/scrapy 等爬虫 |
| CORS 白名单 | 仅允许指定域名访问 |
| CSP 头 | 防 XSS 攻击 |
| Fail-open | Redis 异常时放行，不阻塞正常业务 |

### 9.4 模型使用合规

- 不直接传播第三方模型输出用于商业二次训练
- 所有模型调用均通过官方 API
- 保留调用日志用于问题追溯

## P11 后续落地计划

### 第一阶段：完善现有能力（1-2 个月）

- 树状辩论增加更多可视化主题和导出功能（PDF / 图片）
- 意图识别漏斗持续补充规则与示例，提升 L1/L2 命中率
- 思考链扩展支持 Markdown 公式、代码块渲染
- 多模态生成接入更高质量模型，缩短等待时间

### 第二阶段：平台化扩展（3-6 个月）

- 上线自定义 Agent 广场：用户可创建自己的多模型 Agent 团队
- 引入 RAG 知识库市场：分享和复用优质知识库
-  debates 模板市场：覆盖职场、投资、教育、公共政策等垂直场景
- 开放 API： debates / chat / media 能力以 API 形式对外提供

### 第三阶段：商业化与生态（6-12 个月）

- SaaS 订阅：按调用量、模型数量、存储空间计费
- 企业私有化部署：支持本地 LLM、本地知识库、本地用户管理
- 教育 / 政府 / 金融等行业解决方案
- 开源部分核心组件（LLM Client、意图漏斗、LangGraph 混合编排）
