# 项目原创性与技术贡献说明

> 本文档面向大赛评审，诚实说明本项目的开发方式、原创性边界与技术贡献，作为提交材料的补充。

## 一、开发方式说明（诚实披露）

本项目在开发过程中使用了 **AI 辅助编码工具**（代码补全、模板生成、代码 review 等），用于**提高编码效率**。AI 辅助的范围与边界如下：

| 环节 | 是否使用 AI 辅助 | 说明 |
|------|:---:|------|
| 编码实现（样板代码、CRUD、工具函数） | ✅ 使用 | AI 辅助生成基础代码框架，人工修改与验证 |
| 架构设计与模块拆分 | ❌ 独立完成 | 见 ADR-001 ~ ADR-005 |
| 技术选型与性能方案 | ❌ 独立完成 | 见 ADR-006 ~ ADR-025 |
| 可靠性方案（限流/重试/对账） | ❌ 独立完成 | 基于真实线上故障复盘设计 |
| 安全加固方案 | ❌ 独立完成 | 见安全合规文档 |
| 测试用例与验收 | ✅ 部分辅助 + 人工验证 | 895 用例全量通过 |

**核心判断**：AI 工具是「编码效率放大器」，但本项目的**架构判断、技术决策、故障复盘、方案权衡**均为独立完成，并沉淀为 25 条 ADR 架构决策记录（见下文）。

## 三、原创性亮点：Multi-Agent 并行工作流可靠性闭环

这是本项目**最具原创性、也最难被 AI 直接生成**的部分——它不是「调用一个 LLM」，而是一套完整的分布式可靠性方案：

```
TaskPlanner 拆分 → RabbitMQ 公平分发 → 双实例 Worker 并行执行
     ↓                                              ↓
Redis Lua 原子限流（防过载）           MANUAL ack + DLX 死信指数退避重试
     ↓                                              ↓
SubTaskResultCollector 收敛（SETNX 锁防重复）  ←  Reconciler ZSet 索引对账兜底
```

**这套方案中的关键判断（AI 无法替代）：**

1. **为什么用 MANUAL ack 而非 auto ack** —— 因为结果丢失会导致收敛永久等待，必须 ack 前置到结果落库后
2. **为什么 DLX 重试用指数退避（1s→60s）** —— 避免瞬时故障下重试风暴击穿下游
3. **为什么 Reconciler 用 ZSet 索引而非全量 keys 扫描** —— O(log n) 检索 vs O(n) 扫描的性能权衡
4. **为什么收敛锁 TTL 要 5min 对齐** —— 收敛调 LLM 流式总结可能超时，锁过期会导致重复收敛（真实踩坑后修复）

以上每一条都对应一个真实的故障场景或性能瓶颈，是**反复验证后的工程判断**。

## 四、技术贡献清单（自研部分）

| 技术点 | 说明 |
|--------|------|
| 意图识别三层漏斗 | 精确匹配 → 规则 → 语义兜底 + SeedPool 自增强的多级路由架构 |

| 可靠性闭环 | Lua 原子限流 + MANUAL ack + DLX 死信重试 + Reconciler 对账 |

| 模型 Provider SPI | 策略工厂 + 动态注册 + 模型自助管理面 |
| 存储 SPI 热插拔 | StorageRegistry 抽象，支持多存储后端切换 |
| 安全加固体系 | 三层限流 + UA 校验 + 验证码 + 登录锁定 + 敏感词词边界 |
| 可观测性 | Prometheus 全链路 + 业务级指标 + 钉钉告警 |

## 六、结语

本项目**不回避使用 AI 辅助工具**——在 AI 时代，善用 AI 提高效率本身是能力的一部分。但本项目的核心竞争力——**架构判断力、故障复盘能力、可靠性方案设计**——均来自独立的技术思考，并沉淀为 27 条可追溯的 ADR 决策记录与 895 个通过测试的用例。

我们相信：**AI 能帮你写代码，但「为什么这么写」的判断，才是工程师不可替代的价值。**
