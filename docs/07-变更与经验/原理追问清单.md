# 项目原理追问清单（答辩版）

> 用途：开源/面试/答辩前自查，覆盖本项目最可能被追问的原理点。
> 每个点含：**追问** → **人话版回答** → **一句话总结**（临场开场白）。
> 更新：2026-08-14

---

## 一、架构与部署

### Q1：为什么拆成 5 个微服务？不会过度设计吗？

按"变更频率"和"资源需求"分离：chat-core 管 AI 编排（变更最频繁）、chat-llm 管 LLM 接入（要独立扩容）、chat-web 管 HTTP/WS 接入（要扛并发）、chat-games/media 是独立业务域。这样改 AI 逻辑不重启接入层，LLM 出问题不影响聊天主链路。

> **一句话**：按变更频率和资源边界切，不是按代码量切。

### Q2：为什么 core 要跑双实例？9091 为什么不能用？

单实例挂了全站 AI 服务就瘫了；双实例一主一从，一个挂了另一个顶上。9091 被服务器上的 milvus-standalone 容器占用了，所以双实例用 9090/9092。

> **一句话**：高可用需要冗余，端口被别的服务占了就换。

### Q3：web 怎么在两个 core 之间选？stop 为什么要广播？

web 配置了 base-urls 列表（9090,9092），请求轮流发（轮询），一个不通自动切另一个。stop（停止 AI 回复）必须广播：同一场对话的请求可能被分到不同实例，只通知一个实例的话另一个还在继续生成。

> **一句话**：多实例下"发通知"必须全量广播，否则有实例收不到。

### Q4：nodeId 防堆积是什么？

多实例同时消费同一个任务队列时，同一子任务可能被两个实例重复处理。每个 worker 带唯一 nodeId，处理前先占坑（Redis 去重），防止重复执行和消息堆积。

> **一句话**：多实例抢活，先登记再干活，避免重复。

### Q5：Nacos 是干嘛的？为什么不用 application.yml 直接配？

配置中心。环境变量、DB 密码、LLM 参数集中管理，改配置不用重新打包重启（动态刷新）。多实例共享同一份配置，不会"改了 A 忘改 B"。

> **一句话**：配置集中管 + 动态刷新，多实例不用逐个改。

## 二、Multi-Agent 工作流（最大亮点，最可能被深挖）

### Q6：为什么要把任务拆解成子任务？

超长/跨域请求一次调用，模型容易上下文超限或答得笼统。拆成 ≤9 个独立子任务并行处理，每个专注一件事，再合并，质量和速度都更好。

> **一句话**：单打独斗不如分工协作。

### Q7：Redis Lua 限流 vs Java Semaphore？

Java 的锁只能锁单进程，双实例是两个进程，锁不住对方。Redis Lua 脚本原子执行，两个实例抢同一个 Redis 计数，全局生效——像两个收银台共用一个号牌机。

> **一句话**：跨进程的并发控制，得上"共享的号牌机"。

### Q8：prefetch=1 + manual ack 是干嘛的？

队列默认会把消息批量推给消费者。prefetch=1 = 一次只派一个活，干完再领下一个，忙的实例不会被塞爆（按真实能力分发）。manual ack = 干完才从队列删；实例中途挂了没 ack，RabbitMQ 会自动重投给别的实例，消息不丢。

> **一句话**：按能力派活 + 干完才算数，防塞爆防丢失。

### Q9：DLX 死信重试是什么？

普通队列处理失败的消息会"消失"。死信队列 = 失败消息先转进专门队列，按 1s→2s→4s→60s 指数退避重试，超过 5 次才判定真失败。防止"坏消息反复卡死主队列、拖垮所有消费者"。

> **一句话**：失败先隔离、退避重试，而不是原地反复死磕。

### Q10：WorkflowReconciler 对账是干嘛的？

兜底机制。正常流程：子任务全做完 → 触发收敛。但万一收敛步骤因服务器重启/异常没触发，整个流程就"卡住"了。Reconciler 每 30s 扫一遍，发现"结果齐了但没收敛"的流程，自动补触发收敛。

> **一句话**：正常链路之外加个"定时查漏"，防流程卡死。

### Q11：为什么收敛要用轻量模型 + 压缩到 1000 字？

收敛就是把 N 个子任务结果汇总成最终答案。用轻量模型（qwen-turbo）是为了快和便宜——汇总不需要很强的推理。压到 1000 字是控制输出长度，避免答案又臭又长。

> **一句话**：重活让强模型干，汇总这种轻活用便宜模型干。

## 三、LLM 接入层

### Q12：多 Provider 是怎么抽象的？SPI 工厂是什么？

定义了统一的 `LLMProvider` 接口（调用模型、计费、错误格式都一样），OpenAI/DeepSeek/豆包各写一个实现。SPI 工厂 = 通过 Spring 自动收集所有实现，注册到注册中心，新增一家模型只要加一个实现类，业务代码零改动。

> **一句话**：接口统一 + 工厂自动注册，加新模型不碰业务代码。

### Q13：动态路由是什么？

注册中心里按模型优先级/默认模型配置路由；模型不可用时自动切换备用模型（降级）。路由规则存在数据库，改配置即时生效，不用重启。

> **一句话**：根据配置和可用性自动选模型，坏了自动换。

### Q14：熔断器怎么工作的？

某模型连续失败达到阈值 → 熔断器打开，一段时间内不再调用它（快速失败）→ 半开状态放少量试探请求 → 恢复成功则闭合。防止"已挂的模型反复拖慢请求"。

> **一句话**：发现下游坏了就"先别打它"，过会儿试探再放量。

### Q15：为什么 RAG/知识图谱要下沉到 chat-llm？

知识检索、向量化、图谱抽取都是"LLM 周边能力"，和 core 的业务编排解耦。core 通过内部 API 跨进程调用 llm 服务。好处：知识模块的变更不影响业务主链路，llm 服务可独立扩容。

> **一句话**：LLM 生态的能力归一个服务管，业务编排只管调度。

## 四、RAG 与知识库

### Q16：RAG 完整流程？

用户提问 → 意图判定（是不是知识类问题）→ 问题转成向量 → Milvus 里找最相似的文档片段（相似度 ≥0.3 才算命中）→ 把原文片段 + 对话记忆一起拼进提示词 → AI 基于原文回答。知识库为空或没命中 → 自动降级为普通回答。

> **一句话**：先检索原文再让 AI 基于原文答，不瞎编有出处。

### Q17：为什么有两套 Embedding（1024 维和 1536 维）并存？

老知识库用的是旧模型（legacy，1024 维），新 RAG 用的是新版模型（1536 维）。历史数据已经按老维度存了，为了兼容存量数据不能直接切，只能两套并存、按库区分。后续可平滑迁移到新维度。

> **一句话**：存量数据迁移成本高，新旧并存过渡，逐步收敛。

### Q18：可查性三层判定是什么？

解决"该不该触发 RAG"的问题：① 配置开关（全局是否开启）→ ② 意图判定（是不是知识问答/任务执行类）→ ③ 排除法（天气、时间、新闻、行情、订单这些实时/个人数据不检索，因为知识库根本没有）。避免"问了天气也去库里白搜一遍"。

> **一句话**：三层过滤，只在"该查的时候查"，不做无效检索。

### Q19：知识图谱和 RAG 什么区别？

RAG = 找原文片段拼给 AI（像查资料）。知识图谱 = 抽取实体和关系存 Neo4j（像画关系网），回答"谁和谁什么关系"类问题。RAG 适合"找依据"，图谱适合"讲关联"。

> **一句话**：一个查资料，一个画关系网，场景不同。

## 五、前端与实时通信

### Q20：流式输出（打字机效果）怎么做的？

后端 AI 生成时是"边生成边返回"（SSE/WebSocket 分块推送 token），前端收到一个 token 追加一个到界面上，看起来就像实时打字。不是等全部生成完才一次性返回。

> **一句话**：边生成边推送，前端边收边渲染。

### Q21：前后端完全分离怎么部署？

前端 `npm run build` 出静态文件，部署到 Nginx；后端是独立 jar。前端通过 Nginx 反代 `/api/` 和 `/ws/` 到后端 chat-web。好处：前端更新不用重启后端，静态文件走 Nginx 高性能。

> **一句话**：静态资源归 Nginx，接口反代到后端，互不干扰。

## 六、安全与可观测性

### Q22：三层限流是哪三层？

IP 层（每 IP 每分钟次数）+ 用户层（登录锁定：登录失败 15 分钟锁定 / 媒体生成用户级限流）+ 接口层（上传限制 10MB、SQL 执行台每分钟 30 次等）。纵深防御，单层被绕过还有下一层。

> **一句话**：IP → 用户 → 接口，三层拦截。

### Q23：JWT 弱密钥校验是什么？

启动时检查 JWT 签名密钥强度（≥32 字节），太弱直接拒绝启动。防止"密钥太短被暴力破解 → 攻击者伪造任意用户 token"。

> **一句话**：启动自检，弱密钥直接不让上线。

### Q24：调用链追踪怎么做的？

Micrometer Tracing + Brave + Zipkin。每个请求生成 traceId，贯穿"web → core → llm → 数据库"，每跳记录耗时。出问题时按 traceId 串起整条链路，定位慢在哪个环节。

> **一句话**：给每个请求发"追踪编号"，一路记流水账，出问题按号查。

### Q25：Prometheus 告警体系？

各服务通过 micrometer 暴露 /actuator/prometheus 指标 → Prometheus 定时抓取 → 按规则判断（系统 8 条：宕机/内存/磁盘/JVM/CPU/负载/延迟/错误率；业务 4 条：漏斗命中率/工作流降级率/收敛失败/token 激增）→ 触发告警 → Alertmanager → 钉钉 webhook 推送。业务指标用 AOP 切面采集，业务代码零侵入。

> **一句话**：指标自动采集 + 规则判定 + 钉钉告警，替代人工巡检。

## 答辩心态建议

1. **被问到不会的**：大方说"这个点我了解不深，但我的理解是……，我回去再确认一下"。诚实比装懂更加分。
2. **先讲"一句话"，再展开**：上面的"一句话"就是开场白，再展开讲细节。
3. **讲取舍比讲实现重要**：最想听的是"为什么这么做"而不是"怎么写的"。
