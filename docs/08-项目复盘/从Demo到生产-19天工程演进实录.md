# 从 Demo 到生产：一个 AI 系统的 19 天工程演进实录

> 这不是一篇"我做了什么"的流水账，而是一份"一个 AI 系统如何从能跑，到能扛"的工程决策记录。
> 每一个决策，我都写下：**问题 → 方案 → 取舍 → 代价**。
> 如果你也在用 AI 做一个产品，希望这份实录能帮你少走一些我踩过的坑。

---

## 背景

2026 年 7 月 30 日，我把一个"多模型 AI 智能协作平台"部署到了两台云服务器上：

- **主服务器**：2 核 4G（Nginx + Redis + RabbitMQ）
- **Milvus 服务器**：4 核 8G（所有 Java 服务 + Milvus 向量库）

19 天后（8 月 17 日），它已经是一个 6 微服务、双实例高可用、带完整可观测性和安全加固的生产级系统。

这篇文章，记录这 19 天里，我做对的、做错的、以及每一个"为什么"。

---

## 第一阶段：先让它跑起来，但别让它裸奔（7/30 ~ 8/2）

### 第一天做了什么

第一天我没有急着堆功能，而是先跑通一条**最小闭环**：

```
前端页面 → HTTP → 后端 → LLM → WebSocket 流式返回
```

7 月 30 日 16:55，这条链路第一次全通——前端加载、WebSocket 实时对话、移动端兼容，全部验证完毕。

### 一个关键认知：demo 也要"预留骨架"

很多人做 demo 是"能跑就行，架构以后再说"。但我一开始就在单体里**预留了这些边界**：

- 分层设计（Controller / Service / Repository 清晰分离）
- 缓存、限流、降级的**位置**提前留好（哪怕一开始是空实现）
- 统一的模型接入抽象（哪怕一开始只有 DeepSeek 一个模型）

> **为什么？** 因为我知道，如果 demo 阶段不预留这些边界，等需求爆发后再补，代价是"重构"，而不是"填充"。
> AI 写代码时，它会顺着你的骨架走；如果你给它的是一坨，它还你一坨。

---

## 第二阶段：业务稳定了，才开始抽象（8/3 ~ 8/6）

### 一个反直觉的决策：不急着建"领域模型"

很多教程会教你"先设计好领域模型再写代码"。但我的经验是：

> **业务形态没定型时，实体是抽象不出来的。**

一开始，一个接口就 6、7 个参数，硬去抽象成 Model，只会得到一个"为了抽象而抽象"的四不像。

我的做法是：

1. 先让功能跑起来，用**真实的用户反馈**（我先找了身边朋友试用）去收敛需求
2. 当某个功能**稳定了、不再变了**，才把它抽象成 Model
3. 抽象的时候，顺带做数据字典的微调

> **关键判断**：抽象的最佳时机，不是"你觉得自己懂了"，而是"功能已经不再变化了"。过早抽象是债，过晚抽象是痛。

### 8 月 5 日，树洞功能上线

这一天，`tree_hole_messages` 表建起来，情绪树洞功能上线。这是我"功能稳定 → 再抽象"这条原则的一个具体体现。

## 第三阶段：单体太慢了，拆成微服务（8/9 ~ 8/12）

### 触发点：单体启动太慢

随着功能越来越多，单体应用启动越来越慢。改一个 bug，重启一次要几十秒到一两分钟——这期间用户是**完全不可用**的。

> 如果这是金融级系统，这就是 P0 故障。

### 拆分的决策链（这是我最想分享的部分）

我没有拍脑袋"拆成 6 个服务"，而是列了这几个判断维度：

| 维度 | 我的判断 |
|------|---------|
| **变更频率** | AI 编排逻辑改得最频繁 → 独立成 `chat-core` |
| **资源边界** | LLM 调用要独立扩容 → 独立成 `chat-llm` |
| **故障域** | 一个模块挂了不能全站瘫 → 按业务域隔离 |
| **并发压力** | HTTP/WS 接入要扛并发 → 独立成 `chat-web` |
| **服务器资源** | 4 核 8G 的机器，能跑几个实例？→ 决定起几个实例 |
| **未来增长** | 游戏、多模态会持续加 → 预留独立服务位 |

最终拆成 6 个服务：

```
chat-common  公共库
chat-core    AI 编排（变更最频繁）
chat-llm     LLM 接入 + RAG + 知识图谱（要独立扩容）
chat-web     HTTP/WS 接入层（要扛并发）
chat-games   游戏
chat-media   多模态
```

### 拆完之后的"连锁思考"

拆服务不是终点，而是**新问题的起点**：

- **挂了怎么办？** → core 起双实例（9090 主 + 9092 从），web 轮询负载
- **一个实例挂了，消息丢了吗？** → 消息队列 + 死信重试
- **怎么知道它挂了？** → Prometheus + Alertmanager + 钉钉告警

> **这才是"拆微服务"真正的价值**：它逼你把"故障"当成一个必须回答的问题，而不是侥幸地假设"它不会挂"。

### 8 月 12 日，两个关键升级

1. **模型接入 SPI 化**：从"注册中心硬编码 if-else"，升级为 SPI 策略工厂。新增一个模型厂商，不再改核心代码，只加一个实现类。

2. **LLM 独立服务化**：把 LLM 调用从 chat-core 里拆出来，独立成 chat-llm 服务（REST + gRPC 双协议）。这是后来抽离出 llm-gateway 的雏形。

## 第四阶段：从"能跑"到"扛得住"（8/13 ~ 8/15）

这一阶段，我开始做一件很多 AI 应用团队都忽略的事：**给 LLM 调用上"生产级底线"**。

### 性能：11 秒 → 1-3 秒的根因追踪

用户反馈"响应太慢，11 秒"。我做了逐层定位，揪出两个**隐蔽根因**：

1. **`tool_call_id` 字段缺失**：工具调度时，`ToolDispatcher` 构造消息漏传了 `tool_call_id`，DeepSeek 严格校验直接返回 400，触发重试和熔断连锁——单次工具调度耗时 11.5 秒。

2. **豆包默认开启"深度思考"**：`doubao-seed-2-0` 系列默认输出大量 reasoning token（实测 149 个），导致首 token 延迟 4~18 秒。修复方式是在调用时显式透传 `thinking:{type:disabled}`。

> **这两个 bug 的共同点**：都是"文档没明说、默认值坑人"的隐性坑。AI 写代码不会告诉你"这里有个默认参数会拖慢 10 秒"，只有真实压测和逐层排查才能发现。

### 可靠性：默认"它会出错"

我给 LLM 调用叠了四层保护：

```
限流 RateLimiter → 熔断 CircuitBreaker → 超时 TimeLimiter → 重试 Retry
```

外加：
- 缓存 key 双写（修掉"读写 key 不一致导致缓存永远失效"的 bug）
- 流式 token 合并广播（30ms 窗口，MQ 消息量降一个数量级）
- 死信队列指数退避重试

> **核心原则**：可靠性靠"兜底"，不靠"假设不出错"。默认每个组件都会挂，然后为每个"会挂"设计恢复路径。

### 安全：AK 泄露事故的真实复盘

这是我最想诚实记录的一次事故。

**发生了什么**：早期开发时，我把模型的 API Key **误提交到了 Git 仓库**。

**怎么发现的**：在做依赖漏洞扫描和密钥检查（gitleaks）时，发现仓库里残留了明文 AK。

**怎么处理的**：
1. 立即吊销所有泄露的 AK，重新生成
2. **归档重建整个仓库**——这是最彻底的方案，代价是**丢了 8 月 14 号之前的所有 Git 提交历史**
3. 建立密钥治理规范：AK 存数据库（加密），环境变量只做兜底，代码里绝不出现明文

**教训**：
- AK 泄露不是"会不会"的问题，是"什么时候"的问题
- 一旦泄露，**必须吊销重建，不能只删掉那一行**（历史记录里还在）
- 代价是真实的：我丢了 15 天的 Git 历史，后来只能用服务器日志一点点还原

> 这也是为什么我现在写这篇文章——**把踩过的坑写下来，比把"我很厉害"写下来，更有价值。**

### 8 月 15 日，安全加固 V4-V8 上线

连续 8 个版本的安全加固：
- 方法级鉴权恢复 + 常量时间密码比较
- WebSocket 双层鉴权（握手 + 订阅级）
- 日志脱敏（JWT、签名 URL、密钥全部遮蔽）
- 删除硬编码默认密码
- 上传类型白名单 + SSRF 防护
- 内容安全 fail-close + 输出检测

同时把 Dependabot 的 12 项漏洞告警（含 1 critical、2 high）全部清零。

## 第五阶段：抽象出"可复用的底座"（8/16 ~ 8/17）

### 深度思考，做成"用户可配置"

豆包的"深度思考"（reasoning）又快又慢——开着深入但慢，关着快但浅。我没有替用户决定，而是做成了**用户可选的开关**：

- 个人对话、群聊、辩论，都加"🧠 深度思考"按钮
- 默认普通模式（快），需要深度时用户自己开

> **这个决策的本质**：把"快 vs 深"的权衡，交给真正做权衡的人——用户。工程师不该替用户做这种主观选择。

### 抽离 llm-gateway

19 天做到最后，我做了一个最重要的决定：

**把 chat-llm 里的"通用 LLM 能力"，抽离成一个独立的 llm-gateway 项目。**

为什么？因为我意识到，这套东西——多模型路由、统一调用、流式、熔断、RAG、知识图谱——**跟"聊天"没有任何关系，它是所有 AI 应用的通用底座**。

把通用能力从业务里剥离出来，它才能被复用、被传播、被更多人受益。

---

## 最后：AI 时代，什么还值得工程师亲手做

19 天，我全程用 AI 辅助 coding。但回头看，**真正决定系统质量的，从来不是 AI 写了多少代码**，而是这几个 AI 替代不了的东西：

1. **抽象能力**：什么时候该抽象、抽象到什么粒度，AI 给不了答案
2. **权衡能力**：快 vs 深、安全 vs 可用、粘性 vs 动态，每个都是业务场景决定的
3. **根因追踪**：11 秒的慢、缓存不命中、AK 泄露，AI 不会主动告诉你"这里有个默认参数坑"
4. **工程判断**：拆几个服务、起几个实例、预留多少扩展空间

**AI 放大了我的执行速度，但方向盘一直是我自己。**
