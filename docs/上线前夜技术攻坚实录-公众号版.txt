从下午两点到凌晨四点，14 个小时，我们集中解决了 15 类问题。
这篇文章不是 changelog，而是一个真实的项目上线前夜，记录我们踩过的坑、做的决策、和那些只有深夜写代码才会想到的边界情况。

一、需求改造：让三个大模型好好辩论


----------------------------------------------------------------
1. 整合模型从智谱换成千问

观点辩论场是这个项目的核心功能之一：三个大模型围绕用户的问题展开三轮辩论，最后由第四个模型整合结论。

原来的设计是让智谱 GLM 做最后的整合者。但业务方提出新要求：全程不出现智谱，豆包调豆包、千问调千问、DeepSeek 调 DeepSeek，最后让千问整合。

问题出在哪？后端 DebateProcessor.java 里硬编码了"找 zhipu provider 作为汇总模型"的逻辑，而且辩论模型是用 priority 排序取前 N 的模糊策略——这意味着模型组合不可控。

修复方案：
- 整合模型改为通过 model_type="chat" + provider="qwen" 精确匹配
- 辩论模型按 provider 固定取 doubao / qwen / deepseek 三个 chat 模型
- 加三级回退兜底：qwen+chat → 任意 qwen → 任意 chat
- 前端所有"智谱整合"文案同步改为"千问整合"

反思：模型选择逻辑不应该硬编码在后端代码里。更好的做法是把"辩论模型组合"做成配置项存到数据库，运营可以动态调整，不用改代码重新发布。

二、用户体验：让页面切换不丢状态


----------------------------------------------------------------
2. 跨页面状态保持

这是个看起来简单、做起来一堆坑的需求。

现象：用户在观点辩论场发起了一场辩论，切到个人对话空间看一下，再切回来——辩论状态全没了，页面回到初始态。TreeHole、PersonalChat、Chat 都有同样的问题。

根因：React Router 的 <Routes> + <Route> 在切换路由时会卸载旧组件。所有 state、WebSocket 连接、定时器全部销毁。再切回来时，组件重新挂载，一切从零开始。

方案：自研 KeepAliveRoute 组件，所有页面常驻 DOM，用 display: none/block 切换显示。这样切换路由只是改变可见性，组件不卸载，状态全部保留。

function KeepAliveRoute({ pathname, matchPath, children }) {
    const visible = pathname === matchPath
    return (
        <div style={{
            display: visible ? 'flex' : 'none',
            flex: 1, minHeight: 0, overflow: 'hidden',
            flexDirection: 'column'
        }}>
            {children}
        </div>
    )
}

踩坑：第一版用 display: block，导致手机端首页直接无法滚动（详见后文第四节）。后台页面如 Monitor 不应该常驻 DOM，否则敏感结构会暴露在页面源码里——改为条件渲染，仅访问时挂载。

反思：KeepAlive 用空间换时间，适合页面数量可控的中后台。如果页面很多，建议结合 LRU 策略，只保留最近访问的 N 个页面常驻。

三、合规先行：内测版本必须做的几件事


----------------------------------------------------------------
3. 内测版本公告弹窗

作为内部测试版本，只通过 IP 地址向受邀用户开放，没有正式 ICP 备案，不能让用户产生"这是正式服务"的误解。

我们做了一个会话级的公告弹窗：
- 用户首次访问立即弹出（无延迟）
- 倒计时 3 秒按钮"我已了解并同意"，倒计时期间禁用
- 用户必须点按钮才能关闭，点遮罩无效
- 用 sessionStorage 而非 localStorage：关闭浏览器后会话结束，再次访问重新弹窗
- 导航栏常驻公告入口（电脑版+手机版都显示）

为什么用 sessionStorage 而不是 localStorage？因为内测期间用户每次访问都应该重新确认声明，但同一会话内刷新页面不应该反复弹。sessionStorage 完美满足这个需求。


----------------------------------------------------------------
4. AI 生成内容必须标注

合规要求所有 AI 生成内容必须标注"AI生成"标识。听起来简单，做起来涉及 6 个文件、10 处位置：

  Chat.jsx           自动问答、回答他人、当前用户 AI 回答（3处）
  PersonalChat.jsx   私聊 AI 回答
  TreeHole.jsx       树洞 AI 回应
  Debate.jsx         各方辩论回复、最终整合结论（2处）
  MediaGen.jsx       图片/视频生成结果
  History.jsx        历史问答
  KnowledgeGraph.jsx 图谱节点悬浮提示

定义全局样式 .ai-generated-tag，在每处 AI 回答的内容末尾追加这个标识。灰色小标签，11px 字号，半透明背景，不抢眼但清晰可见。

反思：标识应该作为后端响应的一部分统一返回，而不是前端逐个页面手动加。后续可在 Message 实体里加 generatedByAI 字段，前端统一渲染。

四、移动端的暗坑：flex 嵌套滚动


----------------------------------------------------------------
5. 手机端首页滚动失效

这是 KeepAliveRoute 改造后出现的 bug，排查了一个多小时。

现象：电脑端正常，手机端首页（Landing）无法上下滚动，页面像被钉住了一样。

根因：第一版 KeepAliveRoute 的外层 div 用 display: block。而 .app-layout 是 height: 100vh; overflow: hidden 的 flex 容器。这个 div 没有 flex: 1，没有限制高度，导致内部 .landing 的 flex: 1; overflow-y: auto 完全失效——外层 div 高度被内容无限撑开，但父容器把溢出全裁剪了。

方案：把 KeepAliveRoute 的 div 改为 flex 容器：

    display: visible ? 'flex' : 'none',
    flex: 1, minHeight: 0, overflow: 'hidden',
    flexDirection: 'column'

反思：flex 布局的滚动容器嵌套是前端最常见的坑之一。关键三要素缺一不可：
① 父容器固定高度 + overflow: hidden
② 中间层 flex: 1 + min-height: 0（这个 min-height: 0 是最容易被忽略的）
③ 滚动层 flex: 1 + overflow-y: auto

很多人只知道前两条，忽略了 min-height: 0，结果就是 flex 子项不会被压缩到内容尺寸以下，滚动失效。

五、安全加固：从配置化到二次验证


----------------------------------------------------------------
6. SQL 执行器二次验证

SQL 执行器原本只有一道密码登录，登录后可以执行任意 SQL。但写操作（DROP、DELETE、TRUNCATE）一旦误执行就是灾难。

方案：执行前弹窗二次确认，按 SQL 类型分级处理：

  读操作（SELECT/SHOW/DESC/EXPLAIN）
    → 绿色标签，点"确认执行"即可

  写操作（INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE 等）
    → 红色危险标签，必须重新输入管理密码

  未知类型
    → 黄色警告，需确认

写操作的密码通过后端接口校验，弹窗还显示 SQL 内容预览（最多 300 字符），让用户三思而后行。

反思：二次验证应考虑加请求签名或时间戳防重放，避免密码被中间人截获。生产环境建议叠加 IP 白名单。


----------------------------------------------------------------
7. 敏感页面后台化

Monitor 页面（在线人数监控）原本和普通页面一样常驻 DOM。但这个页面包含敏感的在线数据，不应该让任何访问者都能在页面源码里看到监控结构。

方案：
- 从 KeepAliveRoute 常驻列表中移除
- 改为条件渲染：仅当 URL 是 /monitor 时才挂载，离开立即卸载
- 不显示在任何导航菜单中
- 访问需要密码登录


----------------------------------------------------------------
8. 密码配置化：从前端搬到后端

Monitor 页面的登录密码原本硬编码在前端 JSX 里（19641025），任何查看浏览器源码的人都能看到。

方案：
- 后端 MonitorController 新增 POST /api/v1/monitor/login 接口
- 密码从 application.yml 读取，支持环境变量覆盖
- 前端改为调接口校验，源码中不再暴露任何密码

这是个低级但常见的安全问题。任何密码都不应该出现在前端代码里，哪怕是被混淆过。


----------------------------------------------------------------
9. 注册表单：昵称改为可选

注册时强制要求昵称，影响转化率。改为用户名和密码必填，昵称可选——不填时后端自动用 username 作为默认昵称。

六、最难的一个 Bug：在线人数只增不减


----------------------------------------------------------------
10. 竞态条件导致在线人数虚高

这是个花了两个小时才定位到的并发 bug。

现象：Monitor 页面显示其他模块在线人数只增不减。用户从首页切到个人对话空间，首页在线人数不下降，个人对话空间 +1，总在线人数虚高。

根因：用户切换页面时，前端发两条 STOMP 消息——先发 unregister（旧 page），再发 register（新 page）。但 STOMP 消息是异步的，两条消息到达后端的顺序不保证。

如果 register 先到：
  步骤1：registerUser 执行，localSessions 更新为新 page
  步骤2：unregister 后到，localSessions.remove() 返回新 page（已被步骤1更新）
  步骤3：从新 page 的 set 里移除自己——把刚注册的给删了！

更糟的是，如果 STOMP 连接未就绪，unregister 消息直接被跳过不发，旧 page 的 sessionId 永远留在 Redis set 里。

方案（三层修复）：

第一层：unregisterUser 优先用传入的 page 参数
不信任 localSessions.remove() 的返回值，因为那可能已经被 register 提前更新了。

第二层：registerUser 兜底扫描所有 page
每次 register 时，主动扫描所有已知 page，把该 sessionId 从非当前 page 中移除。即使 unregister 消息丢失，下次 register 也会自动清理残留。

第三层：前端串行发送
确保 unregister 在 register 之前发送，且同 page 不重复发。

反思：跨进程状态同步（Redis + 内存 Map）的竞态问题极易被忽略。最佳实践是：
① 核心清理逻辑做幂等
② 不依赖消息顺序
③ 有兜底全量扫描机制

如果用 Redis Hash（sessionId → page）替代多个 Set，可以原子化操作，避免扫描。这是后续优化的方向。

七、资源回收：5 分钟无操作自动断开


----------------------------------------------------------------
11. 闲置连接自动断开

WebSocket 连接是宝贵资源。用户打开页面后离开不关闭，连接会一直占用服务器资源。Redis 里的在线计数也会虚高。

方案：前端 + 后端双保险。

前端：
- 监听 mousemove / keydown / click / scroll / touchstart 五种事件
- 5 分钟无任何操作，主动发 unregister 并断开 STOMP 连接
- 顶部显示红色提示条："您已 5 分钟无操作，连接已断开"
- 用户恢复操作时自动重连

后端兜底：
- 每次 register 时记录心跳时间到 Redis
- 定时任务每 60 秒扫描一次，超过 5 分钟无心跳的 session 自动清理
- 防止浏览器崩溃、手机杀进程等导致僵尸 session

为什么需要双保险？因为前端不能保证 100% 执行清理逻辑。浏览器崩溃、网络断开、手机系统杀后台，都不会触发前端的 cleanup。后端定时任务是最后的安全网。

八、防爬虫与接口保护


----------------------------------------------------------------
12. 五层防护体系

项目暴露在公网 IP 上，没有任何防护的话，一个晚上就能被各种爬虫扫穿。

方案：基于 Redis 的 IP 限流 + 黑名单 + UA 过滤。

第一层：IP 全局限流
单 IP 每分钟最多 60 次请求，覆盖所有 /api/** 接口。

第二层：敏感接口限流
登录、注册、SQL 登录、Monitor 登录等接口，每分钟最多 5 次。防止暴力破解密码。

第三层：自动拉黑
60 秒内超过 100 次请求的 IP，自动拉黑 10 分钟。

第四层：UA 过滤
拦截无 User-Agent 或已知爬虫工具的 UA：scrapy、curl、wget、python-requests、headless、selenium 等。
放行 Google、Baidu、Bing 等搜索引擎爬虫。

第五层：管理员手动管控
提供 API 让管理员手动拉黑/解封 IP，查看限流状态。

容错策略：Redis 异常时 fail-open（放行），避免 Redis 故障导致全站不可用。这是有意为之的权衡——可用性优先于安全性。

与现有防护的关系：
  已有：用户级限流（按 userId，防登录用户刷接口）
  新增：IP 级限流（按 IP，防匿名爬虫）
  多层防护才能覆盖各种攻击场景

九、其他


----------------------------------------------------------------
13. 数据库变更：兼容低版本 MySQL

需要给 model_configs 表加 model_type 字段，但生产 MySQL 版本低于 8.0.29，不支持 ADD COLUMN IF NOT EXISTS 语法。

方案：用存储过程做幂等 DDL，通过 information_schema 检查列是否存在，不存在才 ALTER。数据用 ON DUPLICATE KEY UPDATE 实现 upsert，可重复执行。


----------------------------------------------------------------
14. 删除不需要的页面

内测版本不需要展示制作人个人信息，直接删除 About.jsx 和 about.css，清理所有引用。代码越精简，维护成本越低。


----------------------------------------------------------------
15. 汉堡菜单加文字

手机端右上角的汉堡按钮只有三条横线，不够直观。改为"三条横线 + 菜单"二字，降低用户认知成本。

总结


这一夜共解决 15 类问题，涉及前端 8 个文件、后端 7 个文件、配置 2 个文件、数据库 1 张表。

核心经验：

  架构
    KeepAlive 适合中后台，但要注意 flex 嵌套滚动和后台页面隔离

  安全
    密码必须配置化，AI 内容必须标注，敏感页面需二次验证 + 后台化

  稳定性
    跨进程状态同步要做幂等 + 兜底全量扫描，不依赖消息顺序

  合规
    内测声明需会话级弹窗，不收集敏感信息，AI 生成内容标识

  移动端
    flex 滚动容器三要素：父固定高+overflow hidden、中间 flex:1+min-height:0、子 flex:1+overflow auto

  防护
    多层防护才能覆盖各种攻击场景，可用性优先于安全性（fail-open）


后续待办：

  - 模型选择逻辑配置化（避免硬编码 provider）
  - AI 生成标识改为后端字段统一返回
  - 在线人数改用 Redis Hash 原子化操作
  - SQL 二次验证加请求签名防重放
  - 接入 Nginx limit_req 做网关层限流
  - 加滑块验证码防自动化脚本


写这篇文章不是为了炫技，而是希望这些踩坑经验能帮到同样在做 AI 应用的开发者。

很多问题看起来是"小问题"——一个 flex 滚动失效、一个竞态条件、一个密码硬编码——但在真实项目中，这些小问题累积起来就是线上事故。

深夜写代码的好处是安静，坏处是容易忽略边界情况。希望这篇文章能帮你少踩几个坑。
