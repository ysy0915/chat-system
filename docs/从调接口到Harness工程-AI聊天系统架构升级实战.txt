从调接口到 Harness 工程：AI 聊天系统的架构升级实战


一、背景：当"调接口"不够用了

大多数 AI 应用的起点都很简单：前端发一个问题，后端调一下大模型 API，把回答返回给前端。一个 HTTP 请求，几十行代码，就能跑起来。

但当你真正把 AI 聊天系统做下去，问题会接踵而至：

  - 用户说"我上周跟你说过的那个项目"，AI 完全不记得——没有记忆
  - 用户问业务相关问题，AI 一本正经地编造——没有知识库
  - 4 个业务模块各自复制了一套 LLM 调用代码，改一个地方要改 4 遍——没有抽象
  - 想加个"调用统计"功能，不知道在哪里加——没有统一入口
  - 想换个模型底座，要改一堆 if-else——没有策略隔离

这些问题指向同一个结论：你需要的不只是"调接口"，而是一个 Harness 工程——AI 应用的编排层。

本文记录了一个真实的 Spring Boot + React AI 聊天系统，如何在一夜之间从"调接口"升级为"Harness 工程"，完成设计模式重构、RAG 知识库、对话记忆、多模态增强四大改造。

各层职责：

  - 策略层：封装不同模型供应商的调用差异（接口格式、响应解析、流式处理）
  - 外观层：统一调用入口，收敛 baseUrl/apiKey/统计/日志等横切逻辑
  - Harness 层：在 LLM 调用之上编排"检索-记忆-生成"的完整流程
  - 业务层：只关心业务逻辑，通过 Harness 层间接使用 LLM 能力

三、设计模式重构：策略 + 工厂 + 外观

这是整个升级的基础。重构前，4 个业务模块各自实现了 callLLM/callLLMStream/resolveBaseUrl，累计约 740 行重复代码。

3.1 策略模式：隔离供应商差异

定义统一接口：

    public interface LLMStrategy {
        String invoke(String baseUrl, String apiKey, String model,
                      List<Map<String, Object>> messages, double temperature) throws Exception;

        String invokeStream(String baseUrl, String apiKey, String model,
                            List<Map<String, Object>> messages, double temperature,
                            Consumer<String> callback) throws Exception;

        default boolean supportsStream() { return true; }
    }

两个实现：
  - OpenAICompatStrategy：覆盖千问/DeepSeek/豆包，走 /chat/completions
  - DoubaoStrategy：走 /responses 接口（备用），supportsStream=false 时伪流式降级

关键设计：流式回调用 Consumer<String>，策略层只管"从 HTTP 响应里挤出 token"，不关心 token 最终去哪（WebSocket 推前端还是攒成完整回答）。


3.2 工厂模式：路由策略

    @Component
    public class LLMStrategyFactory {
        public LLMStrategy getStrategy(String provider) {
            switch (provider.toLowerCase()) {
                case "doubao_responses": return doubaoStrategy;
                default: return openAICompatStrategy; // 默认走 OpenAI 兼容
            }
        }
    }

默认走 OpenAICompatStrategy——大多数供应商都在向 OpenAI 兼容靠拢，新增供应商时如果兼容，连工厂都不用改。


3.3 外观模式：收敛横切逻辑

LLMInvoker 统一处理：baseUrl 解析、API Key 选择、调用统计、日志记录：

    public String invoke(ModelConfig config, List<Map<String, Object>> messages,
                         double temperature, String scene, ...) throws Exception {
        LLMStrategy strategy = strategyFactory.getStrategy(config.provider);
        String baseUrl = baseUrlResolver.resolve(config, defaultBaseUrl);
        String apiKey = selectApiKey(config, defaultApiKey);
        try {
            String answer = strategy.invoke(baseUrl, apiKey, config.model, messages, temperature);
            callRecorder.record(provider, model, scene, true, latency, answer.length());
            return answer;
        } catch (Exception e) {
            callRecorder.record(provider, model, scene, false, latency, 0);
            throw e;
        }
    }


3.4 重构收益

  模块                改造前    改造后    减少
  ChatProcessor       1038     560      -46%
  DebateProcessor     426      280      -34%
  TreeHoleService     518      400      -23%
  合计                1982     1240     -37%

  重复代码消除：~740 行
  LLM 调用入口：4 个 -> 1 个
  新增供应商成本：改 4 个文件 -> 加 1 个策略类

四、RAG 知识库：让 AI 先查资料再回答

4.1 问题：AI 不知道你的业务数据

大模型的训练数据有截止日期，也不知道你的业务文档。用户问"公司的请假流程是什么"，AI 只能编造。

RAG（Retrieval-Augmented Generation）的思路很简单：先检索相关文档，把检索结果拼到 prompt 里，再让 AI 回答。


4.2 技术选型

  组件         选型                    理由
  向量数据库   Milvus 2.3.4            生产级、支持 HNSW 索引、Docker 部署
  Embedding    阿里云 text-embedding-v3 1024 维，中文效果好，复用现有千问 API Key
  部署方式     独立 ECS（8G 内存）      与应用服务器分离，互不影响


4.3 数据流

  上传文档 → 解析(PDF/Word/TXT) → 分片(500字/片, 50字重叠) → 向量化 → 存入 Milvus

  用户提问 → 问题向量化 → Milvus 检索 top5 → 拼入 system prompt → 调 LLM → 回答


4.4 核心组件

(1) EmbeddingService：文本转向量

(4) RAGService：编排层核心

    public String invokeWithRAG(ModelConfig config, Long kbId, String question,
                                List<Map<String, Object>> messages, ...) throws Exception {
        // 1. 检索相关文档
        String context = retrieveContext(kbId, question);
        // 2. 拼入 system prompt
        if (context != null) {
            messages.add(0, Map.of("role", "system", "content",
                "你是知识库问答助手。根据以下资料回答：\n" + context));
        }
        // 3. 委托 LLMInvoker 调用
        return llmInvoker.invoke(config, messages, temperature, scene + ":rag", ...);
    }


4.5 零侵入接入

RAG 所有组件用 @ConditionalOnProperty 控制：

    @ConditionalOnProperty(name = "app.rag.enabled", havingValue = "true")

  - app.rag.enabled=false（默认）：所有 RAG Bean 不注册，项目行为完全不变
  - app.rag.enabled=true：自动激活，业务层 @Autowired(required=false) 注入

业务层接入只需 3 行：

    if (ragService != null && kbId > 0) {
        answer = ragService.invokeWithRAG(config, kbId, question, messages, ...);
    } else {
        answer = llmInvoker.invoke(config, messages, ...);  // 降级
    }

五、对话记忆：让 AI 记住用户说过的话

5.1 问题：AI 是"金鱼记忆"

原来的系统只有 10 分钟内的对话历史（MySQL 查询），超过 10 分钟 AI 就完全"失忆"了。用户说"我上周跟你聊的那个项目"，AI 一脸茫然。

5.2 两层记忆架构

  ┌──────────────────────────────────────────────────┐
  │  短期记忆（Redis）                                 │
  │  - 最近 5 轮对话，完整保留                          │
  │  - key: memory:{scene}:{userId}                  │
  │  - TTL: 24 小时                                   │
  │  - 读取速度：< 1ms                                │
  └──────────────────────────────────────────────────┘
  ┌──────────────────────────────────────────────────┐
  │  长期记忆（Milvus）                                │
  │  - 所有历史对话向量化存储                           │
  │  - 每轮对话（问+答）作为一个向量                     │
  │  - 检索 top 3 条相关历史                           │
  │  - 相似度 > 0.5 才纳入                            │
  │  - 永久保存                                       │
  └──────────────────────────────────────────────────┘

5.3 核心流程

保存对话时：

    public void saveConversation(String scene, Long userId, String question, String answer) {
        saveToShortTerm(scene, userId, question, answer);  // Redis List, trim 最近 5 轮
        saveToLongTerm(scene, userId, question, answer);   // Milvus 向量化存储
    }

构建上下文时：

    public String buildMemoryContext(String scene, Long userId, String currentQuestion) {
        List<ConversationEntry> shortTerm = getShortTerm(scene, userId);     // Redis 读最近 5 轮
        List<ConversationEntry> longTerm = getLongTerm(scene, userId, query); // Milvus 检索 top3

        // 拼接为：
        // 【最近对话】
        // 用户: xxx
        // AI: xxx
        // 【相关历史记忆】
        // 用户(3天前): xxx
        // AI: xxx
    }

5.4 业务接入

在 TreeHoleService 和 ChatProcessor 中：

    // 构建消息时，把记忆拼入 system prompt
    String systemPrompt = SYSTEM_PROMPT;
    if (memoryService != null) {
        String memory = memoryService.buildMemoryContext("treehole", userId, question);
        if (memory != null) systemPrompt += "\n\n" + memory;
    }
    messages.add(Map.of("role", "system", "content", systemPrompt));

    // 回答完成后保存记忆
    if (memoryService != null) {
        memoryService.saveConversation("treehole", userId, question, answer);
    }

5.5 效果

  - 10 分钟内的对话：完整保留在短期记忆（Redis）
  - 上周/上月的对话：通过向量检索找到相关的，加入上下文
  - 超过 24 小时的 Redis 过期，但 Milvus 里的长期记忆永久保存
  - AI 能"记住"用户一个月前说过的话

6.1 图片拖拽上传

个人对话空间的输入区支持拖拽图片，AI 自动识别图片内容（调用 qwen-vl-max）。

    <form onDrop={handleDrop} onDragOver={e => e.preventDefault()}>
      // 拖拽时显示高亮边框
    </form>

6.2 语音输入

使用浏览器原生 Web Speech API：

    const SR = window.SpeechRecognition || window.webkitSpeechRecognition;
    const rec = new SR();
    rec.lang = 'zh-CN';
    rec.continuous = false;          // iOS 必须为 false
    rec.interimResults = !isIOS;     // iOS 关闭中间结果（不稳定）
    rec.onresult = (e) => { /* 追加到输入框 */ };

iOS 兼容性处理：
  - 检测 iPad/iPhone/iPod（含 iPad 桌面模式）
  - iOS 14.5+ 才支持 webkitSpeechRecognition
  - iOS 必须 HTTPS 才能用（非 HTTPS 时隐藏麦克风按钮）
  - no-speech 错误静默处理（iOS 频繁触发）

6.3 AI 回答语音朗读

    const utterance = new SpeechSynthesisUtterance(text);
    utterance.lang = 'zh-CN';
    utterance.rate = 1.0;
    window.speechSynthesis.speak(utterance);

封装为可复用的 useSpeechSynthesis hook：
  - speak(id, text)：开始朗读
  - stop()：停止
  - speakingId：当前朗读的消息 ID
  - 自动清理 Markdown 符号（```、`、*、# 等）

七、体验增强：重新生成、停止、对话摘要

7.1 重新生成

AI 回答不满意时，点击"重新生成"按钮：

后端：
    public void regenerate(String oldReqId, Long userId) {
        Message old = messageRepository.findByReqId(oldReqId);
        String newReqId = "regen-" + UUID.randomUUID();
        // 插入新消息记录，复用 process() 流式逻辑
    }

前端：新回答作为新 AI 消息追加（不替换原回答），用户可以对比两个版本。


7.2 停止生成

流式输出时，发送按钮变为"停止"按钮：

后端：
    private final ConcurrentHashMap<String, AtomicBoolean> stopFlags = new ConcurrentHashMap<>();

    // 流式回调中检查
    token -> {
        if (stopFlags.getOrDefault(reqId, new AtomicBoolean(false)).get()) {
            return; // 已停止，不再推送 token
        }
        broadcastService.broadcast("/topic/user." + userId, ...);
    }

前端：点击停止后调用 POST /api/v1/messages/stop，本地立即标记最后一条消息为 stopped。

设计说明：LLM 流式调用本身无法中断（invokeStream 是阻塞的），停止后后端仍会继续接收 LLM 输出但不再推送给前端，完成后推送 stopped 消息保存已生成内容。


7.3 对话摘要

每次对话完成后，异步生成 15 字摘要：

    @Async
    public void summarizeAsync(Long messageId, String question, String answer) {
        String summary = llmInvoker.invoke(config,
            "请用15个字以内概括以下对话的主题：\n问：" + question + "\n答：" + answer,
            0.3, "summary", ...);
        messageRepository.updateSummary(messageId, summary);
    }

历史列表优先显示摘要作为主标题，question 作为副标题。旧数据（无摘要）保持原样。

关键设计：
  - @Async 异步执行，不阻塞主流程
  - 失败仅打日志，不影响用户正常对话
  - temperature=0.3（摘要需要确定性输出）
  - 走统一的 LLMInvoker 入口，scene=summary 便于统计

八、基础设施升级

8.1 数据库迁移到阿里云 RDS

  - 原服务器 MySQL（1.6G 内存）迁移到阿里云 RDS
  - VPC 内网连接，延迟 < 1ms
  - 应用服务器释放 ~180MB 内存（MySQL 进程关闭）
  - RDS 自带备份、监控、高可用

8.2 Milvus 独立部署

  - 新购 8G ECS 专门跑 Milvus
  - 与应用服务器同一 VPC，内网延迟 2ms
  - Docker Compose 部署：milvus-standalone + minio + etcd
  - HNSW 索引 + COSINE 度量，1024 维向量

8.3 Spring Profile 环境隔离

  - application.yml：默认本地配置（MySQL localhost）
  - application-prod.yml：生产配置（RDS + Milvus）
  - 服务器启动加 --spring.profiles.active=prod

8.4 在线人数优化

  - 首页/Chat/PersonalChat：展示虚拟随机数（0-300），各页面之和=总数
  - 监控页面：展示真实 WebSocket 连接数
  - 每 60 秒刷新一次，按真实连接数比例分配

九、架构思考：为什么这些功能要一起做

回顾这次升级，看似是 4 个独立的功能（设计模式重构、RAG、记忆、多模态），但它们有内在的逻辑关系：

  设计模式重构（策略+工厂+外观）
        │
        │ 提供了统一的 LLMInvoker 入口
        ▼
  RAG 知识库
        │
        │ 在 LLMInvoker 之上加检索层
        ▼
  对话记忆
        │
        │ 复用 Embedding + Milvus 基础设施
        ▼
  多模态 + 体验增强
        │
        │ 在业务层增加交互能力

如果先做 RAG 而不做设计模式重构，RAG 代码会和业务逻辑纠缠在一起，无法复用。
如果先做记忆而不做 RAG，Embedding 和 Milvus 基础设施要从头搭。
如果先做多模态而不做记忆，用户体验是割裂的——AI 能看图但记不住昨天的话。

这就是 Harness 工程的核心思想：在 LLM 和业务之间建立一个编排层，让所有 AI 能力（检索、记忆、生成、多模态）都在这个层里编排，业务层只负责调用。

十二、结语

AI 应用的竞争，已经不是"谁的模型更强"，而是"谁的工程化做得更好"。

模型是通用的，但你的数据、你的业务逻辑、你的用户体验是独特的。Harness 工程的作用，就是把这些独特性编织进 AI 的能力中，让通用的模型变成"懂你业务的专属 AI"。

从"调接口"到"Harness 工程"，不是一次性的重构，而是持续演进的过程。今晚做的 8 项功能只是开始，后续还有 Agent、路由、微调等着落地。

但最重要的是：架构的底子打好了，后续的每一步都会更快、更稳。
