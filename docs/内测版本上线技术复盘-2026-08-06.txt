博思AI智能体 · 内测版本上线技术复盘（2026-08-06）

本文记录了博思AI智能体内测版本上线前夜（2026年8月5日—6日）集中解决的一系列功能、安全与体验问题，涵盖前端架构、后端逻辑、数据库变更、跨端适配、安全鉴权、状态保持等多个维度。每个问题都给出"现象 → 根因 → 方案 → 反思"，供后续迭代参考。

一、功能迭代

----------------------------------------------------------------
1.1 观点辩论场：整合模型改为千问 chat

现象：原辩论场最终整合结论由智谱 GLM 模型生成，业务方希望改用千问 chat 模型，且全程不出现智谱。

根因：DebateProcessor.java 中硬编码了"找 zhipu provider 作为汇总模型"的逻辑，且辩论模型用 priority 取前 N 的模糊策略。

方案：
- 整合模型改为通过 findAllEnabledByType("chat") + provider="qwen" 精确匹配
- 辩论模型改为按 provider 固定取 doubao / qwen / deepseek 三个 chat 模型
- 加三级回退：qwen+chat → 任意 qwen → 任意 chat
- 前端文案"由智谱整合结论"同步改为"由千问整合结论"

反思：模型选择逻辑应避免硬编码 provider，更好的做法是把"辩论模型组合"和"整合模型"做成可配置项，存到 model_configs 或独立配置表中。

----------------------------------------------------------------
1.2 跨页面状态保持

现象：用户在观点辩论场发起辩论后切到个人对话空间，再切回来时辩论状态丢失，页面回到初始态。其他页面（PersonalChat、TreeHole 等）同理。

根因：原路由用 <Routes> + <Route>，切换路由时旧页面组件卸载，所有 React state、WebSocket 连接、定时器全部销毁。

方案：自研 KeepAliveRoute 组件，所有页面常驻 DOM，用 display:none/block 切换显示：

function KeepAliveRoute({ pathname, matchPath, children }) {
    const visible = pathname === matchPath
    return (
        <div style={{
            display: visible ? 'flex' : 'none',
            flex: 1, minHeight: 0, overflow: 'hidden',
            flexDirection: 'column'
        }} aria-hidden={!visible}>
            {children}
        </div>
    )
}

踩坑：
1. 第一版用 display: block，导致手机端首页无法滚动（见 3.1）
2. 后台页面（Monitor）不应常驻，改为条件渲染单独挂载

反思：KeepAlive 方案用空间换时间，适合页面数量可控的中后台应用。如果页面很多，建议结合虚拟滚动或 LRU 策略，只保留最近访问的 N 个页面。

二、安全与合规

----------------------------------------------------------------
2.1 内测版本公告弹窗

现象：内测版本需向用户声明"仅通过 IP 向受邀用户开放、未正式上线、不收集敏感信息、AI生成内容已标注"等合规说明。

方案：
- 新增 AnnouncementModal 组件，首次访问立即弹出（sessionStorage 判重）
- 关闭浏览器/标签页后会话结束，再次访问重新弹窗
- 弹窗含 3 秒倒计时按钮"我已了解并同意"，倒计时期间禁用
- 导航栏增加 公告入口（电脑版+手机版均显示）

关键细节：
- 用 sessionStorage 而非 localStorage：保证会话级一次，关闭浏览器重新弹
- 倒计时按钮防止用户盲点跳过声明
- 弹窗遮罩 onClick 不关闭，必须按按钮才能关闭

----------------------------------------------------------------
2.2 AI 生成内容标识

现象：合规要求所有 AI 生成内容必须标注"AI生成"标识。

方案：定义全局样式 .ai-generated-tag，在所有展示 AI 回答的位置末尾追加标识。共涉及 6 个文件、10 处位置：

  Chat.jsx         自动问答、回答他人、当前用户 AI 回答
  PersonalChat.jsx 私聊 AI 回答
  TreeHole.jsx     树洞 AI 回应
  Debate.jsx       各方辩论回复、最终整合结论
  MediaGen.jsx     图片/视频生成结果
  History.jsx      历史问答
  KnowledgeGraph.jsx 图谱节点悬浮提示

反思：标识应该作为后端响应的一部分统一返回，而不是前端逐个页面手动加。后续可在 Message 实体里加 generatedByAI 字段，前端统一渲染。

----------------------------------------------------------------
2.3 SQL 执行器二次验证

现象：SQL 执行器已有一道密码登录，但执行 SQL（特别是写操作）时缺少二次确认，存在误操作风险。

方案：
- 执行前用 classifySql() 分析 SQL 类型：
  - 读操作（SELECT/SHOW/DESC/EXPLAIN）→ 绿色标签，点"确认执行"即可
  - 写操作（INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE/GRANT/REVOKE/SHUTDOWN）→ 红色危险标签，必须重新输入管理密码
  - 未知类型 → 黄色警告，需确认
- 写操作密码通过 /api/v1/sql/login 接口校验
- 弹窗显示 SQL 内容预览（最多 300 字符）

反思：二次验证应考虑加请求签名或时间戳防重放，避免密码被中间人截获。生产环境建议叠加 IP 白名单。

----------------------------------------------------------------
2.4 在线人数监控页面后台化

现象：Monitor 页面原本和普通页面一样常驻 DOM，存在安全隐患（未授权用户可在页面源码看到监控结构）。

方案：
- 从 KeepAliveRoute 常驻列表中移除 /monitor
- 改为条件渲染：仅当 location.pathname === '/monitor' 时挂载，离开即卸载
- 不显示在任何导航菜单中
- 访问需密码登录（sessionStorage.monitor_authed）

----------------------------------------------------------------
2.5 监控页面密码配置化

现象：Monitor 登录密码硬编码在前端 JSX 里（19641025），任何查看前端源码的人都能看到。

方案：
- 后端 MonitorController 新增 POST /api/v1/monitor/login 接口
- 密码从 application.yml 读取：monitor.password: ${MONITOR_PASSWORD:19641025}
- 前端改为调接口校验，源码中不再暴露密码
- 支持环境变量 MONITOR_PASSWORD 覆盖

----------------------------------------------------------------
2.6 注册表单：昵称改为可选

现象：注册时强制要求昵称，影响转化率。

方案：
- 前端昵称字段去掉 required，placeholder 改为"选填，不填则默认使用用户名"
- 后端移除"昵称不能为空"校验，昵称为空时用 username 作为默认值

三、移动端适配

----------------------------------------------------------------
3.1 手机端首页滚动失效

现象：KeepAliveRoute 改造后，手机端首页（Landing）无法上下滚动。

根因：第一版 KeepAliveRoute 的 div 用 display: block，作为 .app-layout（height: 100vh; overflow: hidden）的子项，没有 flex: 1 也没有限制高度，导致内部 .landing 的 flex: 1; overflow-y: auto 失效——外层 div 高度被内容无限撑开，但父容器裁剪了溢出。

方案：把 KeepAliveRoute 的 div 改为 flex 容器：

    display: visible ? 'flex' : 'none',
    flex: 1, minHeight: 0, overflow: 'hidden',
    flexDirection: 'column'

- flex: 1; min-height: 0：在父 flex 容器中获得剩余高度并允许收缩
- display: flex; flexDirection: column：让子页面能用 flex: 1; overflow-y: auto 正确滚动

反思：flex 布局的滚动容器嵌套是前端常见坑。关键三点：①父容器固定高度 + overflow: hidden；②中间层 flex: 1; min-height: 0；③滚动层 flex: 1; overflow-y: auto。缺一不可。

----------------------------------------------------------------
3.2 汉堡菜单加"菜单"文字

现象：手机端右上角汉堡按钮只有三条横线，不够直观。

方案：
- 按钮改为横向布局：三条横线 + "菜单"二字
- 新增 .navbar-hamburger-label 样式（13px、accent 色）

四、后端稳定性

----------------------------------------------------------------
4.1 在线人数只增不减（竞态 Bug）

现象：Monitor 页面显示其他模块在线人数只增不减，切换页面后旧 page 计数不下降。

根因：切换页面时前端发两条 STOMP 消息——unregister（旧 page）+ register（新 page）。但存在两个问题：

1. 消息乱序：STOMP 消息异步，register 可能先于 unregister 到达。registerUser 执行后 localSessions 更新为新 page，随后 unregister 到达时 localSessions.remove() 返回新 page，把刚注册的新 page 给移除了。

2. unregister 消息丢失：如果 STOMP 连接未就绪（client.connected === false），publishPresence 直接 return，unregister 消息没发出，旧 page 的 sessionId 永远留在 Redis set。

3. 进程重启后 localSessions 内存丢失：但 Redis 里的 sessionId 还在，registerUser 找不到 previousPage，无法清理残留。

方案（三层修复）：

第一层：unregisterUser 优先用传入的 page

    String pageKey = (page != null && !page.isBlank()) 
        ? normalizePage(page) 
        : localSessions.get(sessionId);

不信任 localSessions.remove() 的返回值，避免被 register 提前更新导致误删。

第二层：registerUser 兜底扫描所有 page

    Set<String> knownPages = redisTemplate.opsForSet().members(KNOWN_PAGES_KEY);
    if (knownPages != null) {
        for (String p : knownPages) {
            if (!p.equals(pageKey)) {
                redisTemplate.opsForSet().remove(SESSION_PAGE_PREFIX + p, sessionId);
            }
        }
    }

每次 register 时主动扫描所有 page，把该 sessionId 从非当前 page 中移除。即使 unregister 消息丢失，下次 register 也会自动清理。

第三层：前端串行发送

    if (active && active.page !== desired.page) {
        publishPresence('/app/online.unregister', active)
    }
    publishPresence('/app/online.register', desired)

确保 unregister 在 register 之前，且同 page 不重复发。

反思：跨进程状态同步（Redis + 内存 Map）的竞态问题极易被忽略。最佳实践是：①核心清理逻辑做幂等；②不依赖消息顺序；③有兜底全量扫描机制。如果用 Redis Hash（sessionId → page）替代多个 Set，可以原子化操作，避免扫描。

五、数据库变更

----------------------------------------------------------------
5.1 model_configs 表结构升级

现象：需要新增 model_type 字段区分 chat/image/video/text_parse/image_parse，但生产 MySQL 版本 < 8.0.29，不支持 ADD COLUMN IF NOT EXISTS。

方案：用存储过程做幂等 DDL：

    DROP PROCEDURE IF EXISTS _mc_alter;
    DELIMITER //
    CREATE PROCEDURE _mc_alter()
    BEGIN
        IF NOT EXISTS (SELECT 1 FROM information_schema.COLUMNS
                       WHERE TABLE_SCHEMA = DATABASE()
                         AND TABLE_NAME = 'model_configs'
                         AND COLUMN_NAME = 'model_type') THEN
            ALTER TABLE model_configs ADD COLUMN model_type VARCHAR(20) NOT NULL DEFAULT 'chat';
        END IF;
        -- ... updated_at、索引同理
    END //
    DELIMITER ;
    CALL _mc_alter();
    DROP PROCEDURE _mc_alter;

数据用 ON DUPLICATE KEY UPDATE upsert，可重复执行，且不覆盖 api_key_encrypted（避免覆盖生产密钥）。

总结

今晚共解决 12 类问题，涉及前端 8 个文件、后端 5 个文件、配置 2 个文件、数据库 1 张表。核心经验：

  架构    KeepAlive 适合中后台，但要注意 flex 嵌套滚动和后台页面隔离
  安全    密码必须配置化，AI 内容必须标注，敏感页面需二次验证 + 后台化
  稳定性  跨进程状态同步要做幂等 + 兜底全量扫描，不依赖消息顺序
  合规    内测声明需会话级弹窗，不收集敏感信息，AI生成内容标识
  移动端  flex 滚动容器三要素：父固定高+overflow hidden、中间 flex:1+min-height:0、子 flex:1+overflow auto
