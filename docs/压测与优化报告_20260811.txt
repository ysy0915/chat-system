二、意图识别系统 — 三层漏斗架构
================================================================================

2.1 漏斗整体设计
--------------------------------------------------------------------------------

设计一个三级漏斗，逐层降级，确保高命中率 + 低延迟 + 低成本。

       用户输入 "写一个Python快速排序"
           │
           ▼
   ┌─────────────────────────────────────┐
   │ L1: RuleBasedMatcher  规则引擎      │
   │ 延迟: 0-1ms  命中率: 5-15%         │
   │ Trie关键词扫描 + 正则 + 状态机      │
   └──────────────┬──────────────────────┘
       命中?──────┼──────未命中──┐
        │                      ▼
   CODE_GENERATION   ┌─────────────────────────────────────┐
                     │ L2: ContextMatcher  语义匹配        │
                     │ 延迟: 30-80ms  命中率: 70-85%      │
                     │ Embedding 向量化 + Milvus k-NN 检索 │
                     └──────────────┬──────────────────────┘
                         命中?──────┼──────未命中──┐
                          │                      ▼
                    CODE_GENERATION  ┌─────────────────────────────────────┐
                                    │ L3: ToolIntentMatcher  LLM 分类     │
                                    │ 延迟: 200-1000ms  命中率: <10%       │
                                    │ qwen-turbo 轻量模型 + MCP(预留)      │
                                    └──────────────┬──────────────────────┘
                                        未命中?
                                           ▼
                                      UNKNOWN

关键设计原则：
  - 每层失败自动降级，不阻塞主流程
  - 无论哪层命中都返回 FunnelRecognizeResult（含 source 标记命中层）
  - L3 仅有 <10% 流量经过 LLM，成本极低


2.2 L1 规则层 — RuleBasedMatcher
--------------------------------------------------------------------------------

三种匹配引擎按优先级并行执行：

  ┌───────────────┬──────────────────────────────────────┐
  │ 引擎          │ 说明                                  │
  ├───────────────┼──────────────────────────────────────┤
  │ 状态机匹配    │ 最高优先级，用于多轮命令流             │
  │ (STATE_TRANS) │ 如“帮我写代码→继续→优化”              │
  ├───────────────┼──────────────────────────────────────┤
  │ Trie 关键词    │ 滑动窗口 + 最长匹配优先 + 优先级加权   │
  │ (KEYWORD)     │ 如“排序”→CODE_GENERATION              │
  ├───────────────┼──────────────────────────────────────┤
  │ 正则匹配      │ Pattern 预编译缓存，支持复杂模式       │
  │ (REGEX)       │ 如“翻译.*英文”→TRANSLATION             │
  └───────────────┴──────────────────────────────────────┘

规则来源：
  - 手动配置：intent-rules.json（含 9 条规则，覆盖代码生成/翻译/摘要/问候/推理）
  - 自动挖掘：IntentDataExtractor 用 TF-IDF 从历史对话中提取高频关键词


2.3 L2 语义层 — ContextMatcher
--------------------------------------------------------------------------------

启用条件：app.rag.enabled=true

流程：
  1. 用 EmbeddingService 将用户输入向量化（1024 维）
  2. 在 Milvus intent_examples 集合中做 Cosine k-NN 检索（默认 topK=5）
  3. 按意图类别投票，取最高分
  4. 上下文消歧：最近 1-2 轮相同意图 → +0.02~0.05 加分
  5. 分数 >= 阈值 → 命中

类别专属阈值（降低泛化类别的门槛）：
  GENERAL_CHAT:     0.72
  EMOTIONAL_SUPPORT: 0.70
  TRANSLATION:       0.80 (提高精确类别的门槛)
  CODE_GENERATION:   0.80


2.4 L3 LLM 层 — ToolIntentMatcher + IntentRecognitionService
--------------------------------------------------------------------------------

ToolIntentMatcher 委托给 IntentRecognitionService：

  - 模型：qwen-turbo（轻量快速，由 app.intent.model 配置）
  - 温度：0.1（极低，保证分类稳定）
  - 超时：3 秒
  - 缓存：本地 LRU 缓存 500 条，10 秒过期
  - 置信度阈值：0.5，低于此值降级为 UNKNOWN

LLM 输出 JSON：{"category":"CODE_GENERATION","confidence":0.85,"reasoning":"...","entities":""}
JSON 解析有模糊匹配容错机制。

MCP 工具执行预留了扩展点：当意图为 TASK_EXECUTION 时可调用 MCP Server 工具。


2.5 10 种意图分类
--------------------------------------------------------------------------------

  ┌────────────────────┬──────────────┬──────────┬──────────────┐
  │ 枚举值              │ 含义         │ Temp     │ 是否复杂     │
  ├────────────────────┼──────────────┼──────────┼──────────────┤
  │ GENERAL_CHAT        │ 日常闲聊     │ 0.70     │ ❌           │
  │ KNOWLEDGE_QA        │ 知识问答     │ 0.30     │ ✅ 复杂      │
  │ CODE_GENERATION     │ 代码生成     │ 0.20     │ ✅ 复杂      │
  │ CREATIVE_WRITING    │ 创意写作     │ 0.95     │ ❌           │
  │ REASONING           │ 逻辑推理     │ 0.20     │ ✅ 复杂      │
  │ SUMMARIZATION       │ 摘要总结     │ 0.10     │ ❌           │
  │ EMOTIONAL_SUPPORT   │ 情感支持     │ 0.85     │ ❌           │
  │ TASK_EXECUTION      │ 任务执行     │ 0.30     │ ✅ 复杂      │
  │ TRANSLATION         │ 翻译         │ 0.10     │ ❌           │
  │ UNKNOWN             │ 未知/兜底    │ 0.70     │ ❌           │
  └────────────────────┴──────────────┴──────────┴──────────────┘

4 种复杂意图（REASONING / CODE_GENERATION / KNOWLEDGE_QA / TASK_EXECUTION）
会触发思考链模式，LLM 用 <thinking>...</thinking> 标签包裹推理过程。


2.6 意图 → 路由映射 (IntentRoutingHelper)
--------------------------------------------------------------------------------

识别出意图后，三个维度映射：

  1. Temperature：0.1（摘要/翻译）~ 0.95（创意写作）
  2. 工具启用：仅 TASK_EXECUTION 和 CODE_GENERATION 启用 Function Calling
  3. 中文标签：闲聊/问答/代码/创作/推理/摘要/情感/任务/翻译/未知


2.7 自动挖掘 (IntentDataExtractor)
--------------------------------------------------------------------------------

从历史对话中自动学习，定期产出两类数据：

  KEYWORD 规则  → TF-IDF 提取高频关键词 → 刷新到 L1 RuleBasedMatcher
  意图示例      → 每个意图 top-3 条    → 推入 Milvus → 增强 L2 ContextMatcher

两种模式：
  - extract(labeledData)：已有标签数据直接提取
  - autoLabelAndExtract(questions, scene)：先用 LLM 打标签再提取

调度：每天凌晨 3 点自动执行（${INTENT_EXTRACT_CRON:0 0 3 * * ?}）


2.8 配置与环境变量
--------------------------------------------------------------------------------

  app.intent.enabled:              true           # 总开关
  app.intent.model:                qwen-turbo     # L3 分类模型
  app.intent.min-confidence:       0.5            # LLM 置信度阈值
  app.intent.timeout-seconds:      3              # LLM 超时
  app.intent.temperature:          0.1            # 低温度分类
  app.intent.funnel.context.top-k: 5              # L2 k-NN 检索数量
  app.intent.funnel.context.match-threshold: 0.75 # L2 相似度阈值

三、思考链展示 — 实时推理可视化
================================================================================

3.1 设计目标
--------------------------------------------------------------------------------

让 LLM 的推理过程实时可见（灰色字），增强用户信任和可解释性。

  - 个人对话：意图驱动，仅 4 种复杂意图启用
  - 情绪树洞：始终启用，不依赖意图判定


3.2 核心组件：ThinkingStreamParser 状态机
--------------------------------------------------------------------------------

位置：chat-core/.../intent/funnel/ThinkingStreamParser.java

三态状态机，逐 token 解析 XML <thinking> 标签：

                  ┌──────────────────┐
                  │ AWAIT_THINKING    │ 等待 <thinking> 标签
                  └────────┬─────────┘
          检测到 <thinking>  │  300 字符未检测到 → nonThinkingMode
                           ▼
                  ┌──────────────────┐
                  │ IN_THINKING       │ 在思考标签内部
                  │ (灰色字)          │ onThinking 回调
                  └────────┬─────────┘
          检测到 </thinking>│
                           ▼
                  ┌──────────────────┐
                  │ IN_ANSWER         │ 在回答部分
                  │ (黑色字)          │ onAnswer 回调
                  └──────────────────┘

关键设计：
  - emitSafe() 缓冲尾部 10 字符防止标签跨 chunk 切断
  - thinkingStart 回调：检测到 <thinking> 时发一次 thinking_start 消息
  - 自动降级：300 字符后无标签 → 全走 answer 通道
  - flush()：流结束后清空缓冲

三个回调（构造时注入）：
  onThinking(token)      → WsMessage.thinkingToken(token)
  onAnswer(token)        → WsMessage.streamToken(token) + answerCollector
  onThinkingStart()      → WsMessage.thinkingStart()


3.3 ChatProcessor 中的意图驱动思考链
--------------------------------------------------------------------------------

isComplexIntent() 判定方法：

  if intent.category in {REASONING, CODE_GENERATION, KNOWLEDGE_QA, TASK_EXECUTION}
    → 启用思考链

流程：
  1. 意图识别 → isComplexIntent() 判断
  2. 若启用 → System Prompt 追加"用 <thinking> 标签包裹推理"
  3. 创建 ThinkingStreamParser，三个回调分别推送 thinking_token / stream_token / thinking_start
  4. LLM 流式调用中逐 token feed 给 parser
  5. answerCollector（纯回答）存入 DB，不含思考链内容


3.4 TreeHoleService 中的树洞思考链
--------------------------------------------------------------------------------

树洞始终启用思考链，不依赖意图判定：

  - System prompt："如果问题复杂需要分析，先把分析推理写在 <thinking>...</thinking> 标签中"
  - 同样使用 ThinkingStreamParser + answerCollector 分离纯回答


3.5 WebSocket 消息流
--------------------------------------------------------------------------------

  Client                    ChatProcessor                   LLM
    │                            │                            │
    │── stream_start ───────────►│                            │
    │                            │── prompt + system ────────►│
    │◄─ thinking_start ─────────│  (检测到<thinking>)        │
    │◄─ thinking_token("...")──│                            │
    │◄─ thinking_token("...")──│                            │
    │◄─ stream_token("答案")────│  (</thinking> 之后)       │
    │◄─ done ──────────────────│                            │

4.3 限流策略验证
--------------------------------------------------------------------------------

当前限流策略：
  - 用户级：20 次/分钟
  - IP 级：  600 次/分钟
  - 自动拉黑：1000 次/60 秒

单一 IP 1000 并发：
  → 前 495 成功（49.5%），后 505 全部 429 "您的IP已被临时封禁"
  → 限流在 ~495 次时触发，策略正常

随机 IP 验证：
  → 每个请求带随机 X-Forwarded-For / X-Real-IP
  → 1~5000 并发全部不受限流影响
  → 证明限流粒度在 IP 级别

五、502 瓶颈排查与性能优化
================================================================================

5.1 问题现象
--------------------------------------------------------------------------------

500 并发 AI 模式下出现 1 次 502 Bad Gateway，P50 高达 4.3s。


5.2 根因分析
--------------------------------------------------------------------------------

对逐层排查发现三个致命瓶颈：

  ┌───────────────────────────────────────────────────────────────┐
  │ 瓶颈 1 ★最关键★                                              │
  │ chat-web HikariCP maximum-pool-size = 5                       │
  │ 500 并发竞争 5 个 DB 连接 → 大量线程阻塞等待                   │
  ├───────────────────────────────────────────────────────────────┤
  │ 瓶颈 2                                                        │
  │ chat-web Tomcat threads.max = 50                              │
  │ 500 并发只有 50 线程，其余排队堆积                             │
  ├───────────────────────────────────────────────────────────────┤
  │ 瓶颈 3                                                        │
  │ Nginx 无 proxy_read_timeout（默认 60s）                       │
  │ 请求排队超过 60s 被 Nginx 强制断开 → 502                      │
  └───────────────────────────────────────────────────────────────┘

次要问题：
  - Nginx worker_connections = 1024（1000 并发时连接数不足）
  - Nginx upstream 无 keepalive（每次新建 TCP 连接）
  - chat-core HikariCP = 10 / threads.max = 100（偏小）


5.3 优化方案
--------------------------------------------------------------------------------

(1) chat-web/application-prod.yml

  server.tomcat.threads.max:           50  → 200
  server.tomcat.min-spare:             10  → 20
  server.tomcat.accept-count:          50  → 200
  server.tomcat.max-connections:       500 → 2000

6.2 后续建议

  (1) 1000+ AI 并发：chat-web 内存 256MB 可能不足，建议升至 512MB
  (2) DB 读写分离：消息表做读写分离，减轻主库写入压力
  (3) 缓存：用户信息、意图规则加本地缓存，减少 DB 查询
  (4) 监控：接入 Prometheus + Grafana，业务指标（意图分布 / 思考链占比）可视化
  (5) 意图 L2 增强：Milvus 中丰富 intent_examples 示例库，提升 L2 命中率
