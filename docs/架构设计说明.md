## 2. LLM 调用架构

### 2.1 策略模式

```
                    ┌──────────────────┐
                    │  LLMClient        │  ← Fluent Builder API
                    │  (场景化调用)       │
                    └───────┬──────────┘
                            │ 委托
                    ┌───────▼──────────┐
                    │  LLMInvoker       │  ← 熔断 / 自愈 / 链路追踪
                    └───────┬──────────┘
                            │ 策略选择
                    ┌───────▼──────────┐
                    │ LLMStrategyFactory│
                    └──┬──────────┬────┘
                       │          │
          ┌────────────▼──┐  ┌───▼─────────────┐
          │ OpenAICompat   │  │ DoubaoStrategy   │
          │ (qwen/deepseek)│  │ (豆包专用格式)     │
          └───────────────┘  └─────────────────┘
```

### 2.2 调用层次

| 组件 | 职责 | 使用者 |
|------|------|--------|
| `LLMClient` (NEW) | Fluent Builder、场景配置预设 | 业务层 |
| `LLMInvoker` | 熔断、链路追踪、自愈重试 | LLMClient |
| `LLMStrategyFactory` | 按 provider 名称分发策略 | LLMInvoker |
| `LLMStrategy` | HTTP 调用 + 响应解析 | Factory |

### 2.3 动态配置（Nacos）

`LLMClientConfig` 通过 `@RefreshScope` 支持运行时调整：
- 重试次数 / 退避间隔
- 超时时间
- 各场景的 temperature / max_tokens / top_p
- 修改 Nacos 配置后无需重启，刷新间隔内自动生效

## 3. 意图识别 — 三层漏斗

```
用户输入
  │
  ▼
┌─────────────────────────┐
│  IntentFunnelEngine     │ 编排器，串行降级
└───────────┬─────────────┘
            │
┌───────────▼─────────────┐  命中率 5-15%  ·  0-1ms
│ L1: RuleBasedMatcher    │  规则引擎
│   · Trie 关键词扫描      │  处理「明确的、固定的命令」
│   · Regex 预编译匹配     │  如: "翻译"→TRANSLATION
│   · 状态机 (多轮命令流)  │      "帮我写代码"→CODE
└───────────┬─────────────┘
            │ 未命中 ↓
┌───────────▼─────────────┐  命中率 70-85%  ·  30-80ms
│ L2: ContextMatcher      │  上下文语义匹配
│   · Embedding → k-NN    │  「接住九成常规意图」
│   · 对话历史消歧         │  语义匹配平衡速度和灵活
│   · 意图投票 + 阈值      │  Milvus intent_examples 集合
└───────────┬─────────────┘
            │ 未命中 ↓
┌───────────▼─────────────┐  命中率 < 10%  ·  200-1000ms
│ L3: ToolIntentMatcher   │  深度语义层
│   · LLM 分类 (qwen-turbo)│  「意图 → 执行」打通
│   · MCP 工具执行 (预留)  │  兜底 UNKNOWN
└─────────────────────────┘
```

### 3.1 设计要点

| 设计 | 说明 |
|------|------|
| 规则配置热加载 | `intent-rules.json` 支持运行时 `reload()` |
| 规则自动挖掘 | `IntentDataExtractor` TF-IDF 提取高频词 + LLM 标注意图 |
| 上下文消歧 | 最近 1-2 轮意图 → 加分递进 |
| 意图→参数路由 | `IntentRoutingHelper` 按意图动态调整 temperature |
| 三层容错 | 每层失败自动降级到下一层，不阻塞主流程 |

```

├── IntentResult.java            # 识别结果 (Record)
```

## 4. 无状态化设计

### 4.1 Session 管理

```
┌──────────────────────────────────────────────────────────┐
│  WebSocketSessionTracker                                  │
│                                                          │
│  移除: localSessions (ConcurrentHashMap)  ← 有状态      │

│  Redis Keys:                                             │

```

### 4.2 多实例就绪探针

`ReadinessHealthIndicator` 暴露 `/actuator/health/readiness`：
- 验证 Redis 读写能力
- 确认 Session 追踪器可正常工作
- Kubernetes / 负载均衡可根据此探针判断实例是否就绪

## 5. 思考链展示 (Thinking Chain Display)

### 5.1 架构位置

思考链位于 LLM 流式输出管道中，在 ChatProcessor / TreeHoleService 与 WebSocket 之间：

```
LLM (流式输出)
    │
    ▼
ThinkingStreamParser (状态机分离 <thinking> 标签)
    │
    ├── thinking_token  →  WebSocket → 前端灰色展示
    └── stream_token    →  WebSocket → 前端正常展示
    └── answerCollector →  DB 存储（纯回答，不含思考链）
```

### 5.2 ThinkingStreamParser 状态机

逐 token 解析的三态状态机，核心代码位于 `chat-core/.../intent/funnel/ThinkingStreamParser.java`：

| 状态 | 行为 |
|------|------|
| `NORMAL` | feed token → 缓冲并 emit answer token；遇到 `<thinking>` 切换 |
| `IN_TAG` | feed token → 缓冲并 emit thinking token；遇到 `</thinking>` 切换 |
| `TAG_CLOSED` | feed token → 直接 emit answer token |

**关键设计**：
- `emitSafe()` 只缓冲最后 11 个字符（`</thinking>` 长度），其余即时 flush → 零延迟
- 300 字符安全阈值：LLM 未输出 `<thinking>` 时自动切非思考模式
- `markAsNonThinking()` 手动降级接口

### 5.3 思考链启用策略

| 场景 | 策略 | 说明 |
|------|------|------|
| 个人对话（ChatProcessor） | 意图驱动 | REASONING / CODE_GENERATION / KNOWLEDGE_QA / TASK_EXECUTION → 开启 |
| 情绪树洞（TreeHoleService） | 始终开启 | 树洞的共情回复需要推理过程可视 |

### 5.4 消息类型

新增 WebSocket 消息类型（`chat-common/.../WsMessage.java`）：

- `TYPE_THINKING_START = "thinking_start"` — 检测到 `<thinking>` 标签时发送
- `TYPE_THINKING_TOKEN = "thinking_token"` — 每个 thinking 内容片段

## 6. LangGraph4j 辩论编排

### 6.1 概述

依赖 `org.bsc.langgraph4j:langgraph4j-core-jdk8:1.0-beta1` 实现 LLM 辩论的有向无环图编排，替代硬编码的循环逻辑。分两种辩论模式：

| 模式 | 实现 | 图类型 |
|------|------|--------|
| 标准辩论 | `DebateGraphService` + `DebateState` + `DebateNodes` | 单一 `StateGraph`，3 轮循环 |
| 树状辩论 | `TreePerspectiveGraphService` + `TreePerspectiveState` + `TreePerspectiveNodes` | **混合模式**：Java 上层并行 + 每视角一个 LangGraph 子图 |

### 6.2 标准辩论图

```
START → debate → shouldContinue ─┬─ "debate" (round < 3)
                                  └─ "summary" → END
```

- `DebateState`：topic、round、history、summary
- `DebateNodes`：debateNode (三方并行) / shouldContinue (条件路由) / summaryNode
- `DebateGraphService`：构建图 → `compile()` → `invoke()`

### 6.3 树状辩论混合图

树状辩论因视角数量由 LLM 运行时动态决定，无法用单一 `StateGraph` 表达。采用 **混合模式**：

```
DebateTreeProcessor.runTreeDebate()
  ├── decompose()                    ← Java: LLM 拆解 → 2-3 视角
  ├── 并行视角 (CompletableFuture):
  │   for each perspective:
  │     TreePerspectiveGraphService.execute()    ← LangGraph 子图
  │       ├── debateNode            ← 三方并行
  │       ├── shouldContinue        ← 条件路由
  │       └── summaryNode           ← 视角总结
  └── aggregate()                    ← Java: 各视角结论 → LLM 汇总
```

**为什么不全图**：LangGraph4j 的 `StateGraph` 节点编译时固化，但视角数量运行时决定，全图需要预定义 3 条并行分支 + 条件跳过，灵活性和可维护性不如混合模式。

### 6.4 代码位置

```
chat-core/src/main/java/com/example/chat/langgraph4j/
├── DebateState.java              # 标准辩论状态
├── DebateNodes.java              # 标准辩论节点
├── DebateGraphService.java       # 标准辩论图服务
├── TreePerspectiveState.java     # 树状单视角状态
├── TreePerspectiveNodes.java     # 树状单视角节点
└── TreePerspectiveGraphService.java  # 树状单视角图服务
```

## 7. 关键设计决策

| 决策 | 原因 |
|------|------|
| 意图三层漏斗 | 规则层 (0-1ms) → 语义层 (30-80ms) → LLM 层 (200-1000ms)，按命中概率分级 |
| LLM 策略模式 | 不同 Provider (豆包/千问/DeepSeek) 调用格式不同 |
| Nacos 动态配置 | 运行时调优 temperature/maxTokens，无需重启 |
| Redis Session 追踪 | 支持 chat-web 多实例部署 |
| 熔断器 (CircuitBreaker) | 防止 LLM 故障雪崩 |
| WebSocket + Redis Pub/Sub | 多实例消息广播 |
| ThinkingStreamParser 状态机 | 逐 token 分离 thinking/answer，零延迟，300 字符安全降级 |
| 思考链不存 DB | 保持历史记录干净，仅实时展示 |
| LangGraph 混合模式 | 树状辩论视角内用 `StateGraph` 做图式循环编排，上层用 Java 做动态并行和汇总 |
