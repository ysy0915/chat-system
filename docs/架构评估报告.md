## 一、架构一句话总结

**前后端分离 + 双服务器 + 6 模块微服务 + 双实例高可用的多 AI 群聊系统**：AI 能力（LLM/RAG/图谱）下沉独立服务 chat-llm，业务层（chat-core）聚焦编排，接入层（chat-web）双活，指标化运维闭环（Prometheus → 钉钉）。

### 2.3 核心设计决策（10 项）

| # | 决策 | 价值 |
|---|------|------|
| 1 | 双 core（9090 主 Xmx768m / 9092 从 Xmx512m） | 计算水平扩展；autoChat 仅主实例防重复；stop 广播全实例 |
| 2 | 双 web（8081/8082） | Nginx ip_hash 粘性 + keepalive 64；Session 无状态化 Redis 支撑多实例 |
| 3 | nodeId 固定 `node-{port}`（CrossNodeConfig） | 根治重启生成新队列 → RabbitMQ 168 万条堆积根除 |
| 4 | 会话历史修复 `buildFromRecent`（ChatHistoryBuilder） | 跨实例多轮不失忆，"回答完就断开"根除 |
| 5 | LLM/RAG/知识图谱运行时迁至 chat-llm | chat-core 业务解耦；两套 Embedding（1024/1536 维）隔离 |
| 6 | 意图三层漏斗 | 规则(0-1ms)→语义(30-80ms)→LLM(200-1000ms) 分级降级 + SeedPool 反馈自增强 |
| 7 | LangGraph 混合编排 | 树状辩论视角内 StateGraph 子图 + 上层 Java 并行，适配动态视角数 |
| 8 | AI 错误自愈 + Resilience4j | 频率/认证/网络/解析错误分类恢复，LLM 故障不雪崩 |
| 9 | Prometheus 指标化巡检 | 6 条告警（宕机/内存<8%/磁盘<15%/JVM堆/CPU/负载）→ 钉钉，替代手工 tail |
| 10 | Multi-Agent 并行工作流（2026-08-13） | 超长/跨域请求 TaskPlanner 拆解 ≤9 子任务 → RabbitMQ 分发 → 双实例 Worker×10 并行 → 收敛压缩 ≤1000 字；Redis Lua 全局限流 + manual ack 公平分发 + Reconciler 对账兜底 |

## 五、模型抽象与通用性专项评估

### 5.1 LLM 模型抽象（chat-llm 核心）

```
┌──────────────────────────────────────────────────────┐
│  LLMProviderFactory（SPI 扩展点，按 type 查字典）       │
│    ├─ RestProviderFactory    → OpenAICompatProvider  │
│    ├─ SdkProviderFactory     → OpenAISdkProvider     │
│    └─ 自定义 @Component 工厂   → Spring 自动收集       │
│    （LLMProviderStrategyFactory 组合/动态注册/回退rest）│
│              │ create(ProviderConfig)                 │
│  LLMProviderStrategy（接口）                           │
│    ├─ name() · invokeType() [rest/sdk/自定义]         │
│    ├─ supports(provider, model)                      │
│    ├─ invoke(req)            非流式                   │
│    └─ invokeStream(req, chunk, onComplete, onError)  │
│              ▲ 实现                                    │
│  ┌───────────┴───────────┐                           │
│  │ OpenAICompatProvider  │  OpenAISdkProvider        │
│  │ (REST / OpenAI兼容)   │  (OpenAI Java SDK)        │
│  └───────────────────────┴───────────────────────────┘
│              │ 注册 + 路由                              │
│  LLMProviderRegistry（注册中心）                        │
│    ├─ YAML 初始化（PostConstruct → 经策略工厂创建）    │
│    ├─ register()/unregister() 动态注入（DB 路由）      │
│    └─ resolve(provider, model) → RouteResult          │
│        精确匹配 provider → 精确匹配 model             │
│        → 未指定 model 用默认 → 未指定 provider 用全局   │
└──────────────────────────────────────────────────────┘
```

**抽象层次**：
| 层 | 类 | 职责 |
|----|----|------|
| SPI 工厂 | `LLMProviderFactory` + `LLMProviderStrategyFactory` | 按 `type` 查字典创建策略；Spring Bean 自动收集 + 动态注册；未知类型回退 rest（新增接入方式零改动注册中心） |
| 策略接口 | `LLMProviderStrategy` | 统一调用契约（rest/sdk 双模式、同步/流式） |
| 策略实现 | `OpenAICompatProvider` / `OpenAISdkProvider` | 厂商协议适配，新增厂商实现接口即可 |
| 注册路由 | `LLMProviderRegistry` / `ProviderRoute` / `ModelRoute` | YAML/DB 双数据源、优先级、默认模型、动态注册 |
| 调用链 | chat-core `LLMClient`(Fluent) → `LLMInvoker`(熔断追踪) → `LlmBundleClient` | 场景化预设 + 弹性包裹 + HTTP 转发 |
| 降级 | `DirectLLMClient` | chat-llm 不可用时直连兜底 |

**模型可扩展性验证**：新增一个厂商 = 实现 `LLMProviderFactory`（标注 `@Component`，Spring 自动收集）+ 实现 `LLMProviderStrategy` + 配置 baseUrl/apiKey/models（或 DB 注入），已有千问/DeepSeek/豆包三厂商实例验证了该路径；未知 `type` 配置自动回退 rest 不中断路由。

## 六、Multi-Agent 并行工作流专项评估（2026-08-13）

### 6.1 架构链路

```
请求 → TaskPlanner（意图→LLM 拆解 ≤9 子任务）
     → 子任务写 Redis meta + 入队 RabbitMQ（agent.task）
     → 双实例 SubAgentWorker ×10（prefetch=1 + manual ack）并行消费
     → 子结果写 Redis hash（幂等覆盖 + received 计数）
     → SubTaskResultCollector 轮询收敛 → LLM 汇总压缩 ≤1000 字
     → 全局并发闸门：Redis Lua 原子计数 agent:workflow:active ≤8
     → WorkflowReconciler 30s 对账兜底（结果齐但未收敛 → 重新触发收敛）
```

### 6.2 可靠性设计闭环

| 维度 | 方案 | 价值 |
|------|------|------|
| 限流 | Redis Lua 原子计数 `agent:workflow:active`（max-concurrent=8） | 双实例共享额度，100 并发 → 8 并行 + 92 降级（T03 验证）；根治 Semaphore 跨实例错配 |
| 分发 | Worker prefetch=1 + manual ack | 忙时不拉消息，按真实能力公平分发 |
| 丢失 | Worker 成功 ack / 失败 nack(requeue=false) 防重复计数；Collector 失败 requeue=true 依赖 Redis 幂等 | 子任务零丢失（T04 验证） |
| 去重 | Redis hash 幂等覆盖 + received INCR + SETNX 收敛锁 | 双实例只收敛一次 |
| 兜底 | WorkflowReconciler 30s 扫描"结果已齐但收敛未完成" → 重新触发收敛；converged 标记 + DB 状态 + SETNX 锁三层去重 | 服务器重启 / Worker 崩溃后自动恢复（方案 A 端到端验证×2） |
| 压缩 | converge-max-chars=1000 + qwen-turbo | 复杂任务输出 ≤1000 字（T02 验证） |

## 七、亮点

1. **意图漏斗自增强**：L1/L2/L3 分级 + SeedPool 反馈闭环，L3 高置信结果自动灌回 Milvus 与 Trie，L1+L2 目标 >95%

## 八、风险与路线图

| 等级 | 问题 | 影响 | 建议 |
|------|------|------|------|
| P0 | 服务器可用内存仅 ~500MB（已真实触发 HostMemoryPressure） | 双 core + Milvus + 监控栈共挤，系统最大约束 | 升内存或压缩 JVM 堆、评估迁移 Milvus |
| P0 | 主服务器 / Milvus 服务器均单点，无备份演练 | 硬件故障即全站不可用 | 第二台服务器 + 定期备份演练 |
| P1 | 密钥明文存 `.env`（600 权限但未加密） | 泄库即全凭据泄露 | 迁移 KMS / 加密 .env |
| P1 | 可观测性缺业务指标（漏斗命中率/LLM 成本/队列深度） | 告警覆盖以系统层为主 | 追加业务指标与仪表盘 |
| P1 | 模型接入非自助（需编码） | 运营无法自助加模型 | 动态注册 API + 管理界面 |
| P1 | 工作流状态依赖 Redis（plan meta/子结果/收敛标记） | Redis 故障则工作流中断，Reconciler 对账兜底也失效 | Redis 持久化（AOF）+ 高可用；Reconciler 增加 DB 源对账 |
| P1 | Worker 失败不重试（nack requeue=false 即终态） | 单个子任务失败导致整个 plan 无法收敛 | 失败子任务进死信队列 + 指数退避重试 |
| P2 | 无 HTTPS / CDN | 静态资源公网裸 HTTP | 上证书 + CDN |
| P2 | 缺 ADR 架构决策记录 | 决策依据难以追溯 | 建立 ADR 目录 |
