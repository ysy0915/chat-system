### 关键设计决策

| 决策 | 原因 |
|------|------|
| 前后端完全分离部署 | 前端 dist 独立部署 Nginx，后端 jar 不含静态资源，独立发布 |
| 双服务器架构 | 主服务器(低配)跑 Nginx+Redis+RabbitMQ，Milvus 服务器(高配)跑所有 Java + Nacos，资源优化 |
| 模块化微服务 | core/web/games/media 独立 jar，改了哪个只重启哪个 |
| 双 core 部署 | 主实例 9090 (Xmx768m) + 从实例 9092 (Xmx512m)，web 轮询；9091 被 milvus-standalone 占用不可用 |
| stop 广播 | 双 core 下停止请求经 `CoreClient.broadcast()` 广播到所有实例，任一成功即成功 |
| autoChat 仅主实例 | `ModelAutoChatService` 校验 `server.port == 9090`，避免双 core 重复广播自动问答 |
| nodeId 固定 | `CrossNodeConfig` 将节点 ID 固定为 `node-{port}`，杜绝重启生成带 UUID 队列导致 RabbitMQ 堆积 |
| 双 web 实例 | 8081 + 8082 双实例（Nginx ip_hash 粘性 + keepalive），无状态 WebSocket 天然水平扩展 |
| Prometheus 指标化监控 | 替代手工巡检：6 条告警规则（宕机/内存<8%/磁盘<15%/JVM堆/CPU/负载）推送钉钉 |
| Redis ZSet 按页面分组 | 精确统计每个页面的实时在线人数，支持监控页分页面曲线 |
| KeepAliveRoute 常驻 | 辩论场、树洞等页面切换时保留输入和对话状态，避免重新加载 |
| Nacos 服务注册 | 各模块向 Nacos 注册，chat-web 通过服务名发现 chat-core |

## 二、前端架构

### 2.1 入口与全局机制

**`main.jsx`** 是应用入口，承担三项全局职责：

1. **ErrorBoundary 包裹**：捕获任意子组件渲染异常，显示友好提示页 + 上报错误堆栈到后端 `/api/v1/frontend-error`，避免整树卸载导致白屏
2. **全局 axios 401 拦截器**：任意接口返回 401 时，自动清除 `localStorage` 中的 `auth_token` 和 `auth_user`，并派发 `auth-changed` 事件通知全局
3. **全局异常监听**：`window.error` 和 `unhandledrejection` 捕获 ErrorBoundary 抓不到的异步错误，同样上报

### 2.2 路由与页面保活

采用 `BrowserRouter`，基础路径 `/chat`。页面分为两类：

**常驻页面（KeepAliveShell）** —— 12 个页面同时挂载，通过 `display: none/flex` 切换显隐，切换时状态保留：

| 路径 | 页面 | 特点 |
|------|------|------|
| `/home` | 首页 Landing | 展示 1 小时内活跃人数、总用量 |
| `/` | AI伙伴群聊 Chat | 公开问答，多AI参与 |
| `/personal` | 个人对话空间 | 需登录，私密对话 |
| `/debate` | 观点辩论场 | 三AI并行辩论 |
| `/treehole` | 情绪树洞 | 需登录，情绪倾诉 |
| `/media` | 图片与视频生成 | 多模态AI生成 |
| `/games` | AI多人游戏入口 | — |
| `/history` | 问答列表 | 历史记录查询 |
| `/graph` | 知识脉络图 | 可视化知识图谱，支持权重筛选、双指缩放 |
| `/profile` | 个人信息 | 需登录 |
| `/admin/models` | 模型管理 | 静态展示 |
| `/sql` | SQL执行台 | 二次验证 |

**按需挂载页面（EPHEMERAL_ROUTES）** —— 4 个页面含全局 `keydown` 监听器（游戏控制），常驻会吞掉其他页面的键盘输入，因此离开即卸载：

- `/games/pingpong`、`/games/snakeking`、`/games/castlesiege`、`/monitor`

**登录拦截**：`/personal`、`/treehole`、`/profile` 三个页面未登录时拦截导航，弹出登录框，登录后自动跳转目标页面。

### 2.3 状态管理

前端采用 **事件驱动的轻量状态管理**，而非 Redux/Context：

```
localStorage ──读取──> useAuthUser Hook ──> 组件状态
      ▲                                         │
      │                                         │
window.dispatchEvent('auth-changed') <── axios 401 拦截器
      │                                   登录成功
      └── AuthModal 写入 token ──> 派发事件 ──> 全局更新
```

**localStorage 持久化的 Key**：

| Key | 用途 |
|-----|------|
| `auth_token` | JWT 令牌 |
| `auth_user` | 用户信息 JSON |
| `chat_user_id` | 群聊用户ID（未登录时生成） |
| `online_presence_guest_id` | 访客在线跟踪ID |
| `landing_visitor_id` | 首页访客ID |
| `announcement_ack_v1` | 公告已确认标记 |

### 2.4 WebSocket 在线跟踪

**OnlinePresenceTracker** 组件常驻 App 顶层，维护用户在线状态：

```
用户进入页面
    │
    ▼

    │
    ▼

    │
    ▼

    │
    ├─ 旧页面不同 → publish /app/online.unregister (旧页面)
    └─ publish /app/online.register (新页面)
                │

                │
                ▼

                │

[5分钟无操作] → deactivate() 断开 → 显示"已断开"横幅

```

### 2.5 核心页面调用流程

#### AI伙伴群聊 / 个人对话空间

```
1. 用户输入问题
2. POST /api/v1/messages { question, user_id, req_id, private, ai_answer }
3. 后端入库 + 发送 RabbitMQ 队列
4. ChatProcessor 消费 → 调用 AI 模型
5. STOMP 推送 /topic/user.{userId} (私聊) 或 /topic/public (群聊)
6. 前端 onMessage → setMessages → formatAnswer 渲染
```

#### 观点辩论场

```
1. 用户输入辩题，可选场次（rounds，默认 3 轮，范围 1~10）
2. POST /api/v1/debate { topic, rounds }
3. 后端并行调用 3 个 AI (千问/DeepSeek/豆包)
4. 每个 AI 完成后通过 WebSocket 推送观点
5. 前端逐条渲染，支持后续追问
```

#### 情绪树洞

```
1. 用户选择心情 + 输入倾诉内容 (可附图)
2. POST /api/v1/treehole/ask { mood, question } + Bearer JWT
3. 后端调 AI 生成温和回复
4. 返回回复 + 入库 treehole_messages
5. 前端加载历史 /api/v1/treehole/history
```

#### 监控页

```
1. POST /api/v1/monitor/login (独立密码验证)
2. GET /api/v1/monitor/online-history?date=YYYY-MM-DD
3. 返回 8 天各页面访问数据
4. Canvas 绘制：各页面访问曲线 + 总访问量白色虚线
5. 点击曲线显示页面详情
```

## 三、后端架构

### 3.1 安全防护层

```
请求进入
    │
    ▼
IpRateLimitInterceptor (滑动窗口限流)
    ├─ 同IP短时间内请求过多 → 自动拉黑
    └─ UA 过滤可疑爬虫
    │
    ▼
JwtAuthenticationFilter
    ├─ 提取 Authorization: Bearer xxx
    ├─ 验证 JWT 签名和有效期
    └─ 未通过 → 401 (前端拦截器清除登录态)
    │
    ▼
ContentSafetyService
    └─ 阿里云内容安全 detectSensitive() → 命中敏感词拒绝
    │
    ▼
业务 Controller
```

### 3.2 核心聊天流程（5步）

这是系统最核心的调用链，从用户发送问题到收到AI回复：

```
步骤1: MessageController.createMessage()
       ├─ rateLimitService.isAllowed(userId) 限流检查
       └─ 失败 → 返回 429
           │
           ▼
步骤2: contentSafetyService.detectSensitive(question)
       └─ 命中 → 返回 "内容包含敏感词"
           │
           ▼
步骤3: messageRepository.insert(message)  入库
       status = "queued"
           │
           ▼
步骤4: broadcastService.broadcast("/topic/public-questions", ...)
       实时广播问题到所有在线用户
           │
           ▼
步骤5: rabbitTemplate.convertAndSend("chat.exchange", "chat.request", payload)
       │   (若 RabbitMQ 不可用 → 直接 chatProcessor.process() 降级)
       │
       ▼
   ┌─── RabbitMQ 队列 chat.requests ───┐
   │                                    │
   ▼                                    ▼
ChatProcessor.process()            CrossNodeMessageListener
   │                                (跨节点消息转发)
   ├─ trySwitchModel() 检测"换豆包"等切换指令
   │
   ├─ 并发调用 3 个 AI 模型:
   │   ├─ CompletableFuture.supplyAsync(() -> callLLM(千问))
   │   ├─ CompletableFuture.supplyAsync(() -> callLLM(DeepSeek))
   │   └─ CompletableFuture.supplyAsync(() -> callLLM(豆包))
   │
   ├─ 每个完成时 .handle() 回调:
   │   ├─ AtomicInteger finishedCount++
   │   ├─ 立即推送该模型的回复到 WebSocket
   │   └─ 避免allOf竞态(所有完成才触发)
   │
   └─ completeWithAnswer()
       ├─ messageRepository.update() status="done"
       ├─ broadcastService.broadcast() 推送最终回复
       └─ Redis 缓存结果
```

**关键设计：用 `handle + AtomicInteger` 替代 `allOf`**

早期版本用 `CompletableFuture.allOf(...).thenAccept(...)` 等所有模型完成后统一推送，存在竞态条件——若某个模型快速失败，allOf 可能提前触发或漏触发。改为每个 future 独立 `.handle()` 回调，用 `AtomicInteger` 计数，任一完成立即推送，既快又稳。

### 3.3 AI 模型调用

支持 3 个模型提供商，统一通过 **OpenAI 兼容 API** 调用：

| 提供商 | 用途 | 特点 |
|--------|------|------|
| 千问 (Qwen) | 群聊、辩论、个人对话 | 支持搜索增强 |
| DeepSeek | 群聊、辩论 | 推理能力强 |
| 豆包 (Doubao) | 群聊、辩论 | 响应速度快 |

- 模型配置存储在 MySQL `model_configs` 表，支持运行时切换
- 支持多模态：`callLLMWithImage()` 处理图片，`callLLMWithHistory()` 携带上下文
- 观点辩论场**排除智谱**，仅用千问/DeepSeek/豆包

### 3.4 WebSocket 在线状态管理

chat-web 当前为**双实例部署（8081 + 8082）**，Session 状态已无状态化——在线会话与在线人数存 Redis：

```
前端 OnlinePresenceTracker
    │
    │ SockJS 连接 /ws/chat (Nginx ip_hash 粘性保证同会话命中同实例)
    │ STOMP publish/subscribe
    ▼
chat-web WebsocketController (任意实例)
    ├─ /app/online.register → 用户上线
    ├─ /app/online.unregister → 用户下线
    ├─ 写入 Redis (ws:session:page / ws:page:{page} / online:count:{page})
    └─ /topic/online-count/{page} → 广播在线人数
```

跨节点消息转发由 RabbitMQ 的 `CrossNodeMessageListener`（`cross-node-{nodeId}` 队列，nodeId 固定为 `node-{port}`）承载，双实例/双 core 间广播已实测可用。

### 3.5 在线人数统计

```
前端 OnlinePresenceTracker
    │
    │ STOMP publish /app/online.register {userId, page, name}
    ▼
MessageController.handleOnlineRegister()
    │
    ▼
WebSocketSessionTracker.registerUser()
    ├─ Redis ZSet: session:{page} → add(userId, timestamp)
    ├─ 扫描所有 page 清理残留 sessionId (兜底)
    └─ 更新 String: online:count:{page}
    │
    ▼
broadcastService.broadcast("/topic/online-count/{page}", count)
    │
    ▼
前端更新在线人数显示
```

**修复过的竞态问题**：
- `unregisterUser` 优先用传入的 `page` 参数，而非遍历所有 page
- `registerUser` 兜底扫描所有 page 清理残留 sessionId，防止"只增不减"
- 前端串行发送 unregister → register，避免乱序

### 3.6 首页活跃人数统计

首页展示的是**1 小时内活跃用户数**，而非实时 WebSocket 在线人数：

```
OnlineCountRedisService.getHourlyActiveCount()
    │
    ▼
Redis ZSet: monitor:active:1h
    ├─ ZREVRANGEBYSCORE 过滤最近 1 小时内的访问事件
    └─ 返回累计活跃用户数
    │
    ▼
MessageController.getOnlineCount() → Map.of("count", ..., "hourlyActive", ...)
    │
    ▼
前端 Landing.jsx → 展示 "{hourlyActive} 人 1 小时内在线"
```

- 数据来源：`OnlineCountRedisService` 定期向 Redis ZSet `monitor:active:1h` 写入访问事件
- API 返回同时包含 `count`（实时 WebSocket 人数）和 `hourlyActive`（1 小时累计），首页用后者
- 其他页面（Chat、PersonalChat 等）继续使用 `count` 实时数据

### 3.7 知识图谱（知识脉络图）

知识图谱基于 Neo4j 存储实体（Entity）和关系（Relation），在 AI 对话完成后自动抽取三元组并写入图数据库。

> **运行位置说明（2026-08）**：知识图谱运行时已迁移至 **chat-llm**——`KnowledgeGraphService` / `TripleExtractionService` / `GraphRepositoryService` / `BatchImportService` 四服务承载 Neo4j 直连（`app.knowledge-graph.enabled`，生产经 `KNOWLEDGE_GRAPH_ENABLED=true` 开启），`KnowledgeGraphController` 暴露 `/internal/graph/*`。chat-core 已删除本地实现并移除 Neo4j 依赖，经 `GraphClient`（Java 11 HttpClient）跨进程调用（地址 `app.llm-service.base-url`）：`ChatProcessor` / `DebateProcessor` 对话完成后异步触发三元组抽取，`InternalApiController` 代理图谱查询 / 搜索 / 统计 / 批量导入。chat-llm 不可用或服务未启用时 GraphClient 安全降级（返回空结构），不阻塞主流程。

```
AI 对话完成
    │
    ▼
ChatProcessor / DebateProcessor (chat-core)
    ├─ 异步调用 graphClient.extractAndSaveAsync()
    │      │  └─ HTTP → chat-llm /internal/graph/extract
    │      ▼
    │  (chat-llm) AI 提取三元组 (subject, relation, object)
    │      │
    │      ▼
    │  GraphRepositoryService.saveTriples()
    │      │
    │      ▼
    │  Neo4j Cypher:
    │      ├─ MERGE (s:Entity)-[r:RELATION {type}]->(o:Entity)
    │      ├─ ON CREATE SET r.count = 1    —— 首次出现计数为 1
    │      └─ ON MATCH SET r.count += 1    —— 再次出现累加计数
    │
    ▼
前端 KnowledgeGraph.jsx
    ├─ GET /api/v1/graph?limit=100&minEntityWeight=1&minRelationWeight=1
    ├─ 力导向布局渲染到 Canvas
    ├─ 支持节点拖拽、单指平移画布、双指缩放 (0.3x~3x)
    └─ 点击节点显示关联关系详情面板
```

**权重筛选机制**：

| 概念 | 含义 | 筛选逻辑 |
|------|------|----------|
| 实体权重 | 实体关联的边数 | 关系数 ≥ 阈值的实体才显示，值越大越核心 |
| 关系权重 | 同一条 RELATION 累计出现次数 | 累计次数 ≥ 阈值的关系线才显示 |

- API 参数：`minEntityWeight`（默认 1）、`minRelationWeight`（默认 1）
- 前端权重输入框留空默认不限制，可手动输入筛选
- `?` 帮助图标：点击弹出通俗解释弹窗，点击其他位置自动关闭

**高可用（2026-08 增强，chat-llm 内）**：
- `KnowledgeGraphService` 启动时建立 Neo4j Driver 并校验连接
- 启动竞态失败（Neo4j 与 llm 同时拉起）时自动降级，`kg-reconnect` 守护线程每 60s 重连直至成功，无需人工重启

**前端布局**：
- 和观点辩论场一致的中置卡片式布局（`max-width: 900px`）
- 顶部说明区域：标题 + 功能描述 + 统计徽章
- 画布 `550px` 高度（移动端 `420px`），支持 touch 手势
- 底部操作区：搜索框 + 权重筛选 + 按钮

### 3.8 数据存储

**MySQL（6 张核心表）**：

| 表 | 用途 |
|----|------|
| `messages` | 群聊/个人对话消息记录 |
| `users` | 用户账号信息 |
| `model_configs` | AI模型配置（provider/apiKey/baseUrl） |
| `online_count_records` | 在线人数历史快照（监控页数据源） |
| `treehole_messages` | 情绪树洞对话记录 |
| `debate_records` | 辩论场记录 |

**Redis 数据结构**：

| 结构 | Key 模式 | 用途 |
|------|---------|------|
| ZSet | `session:{page}` | 按页面分组的在线用户集合（score=时间戳） |
| String | `online:count:{page}` | 各页面实时在线人数 |
| ZSet | `monitor:active:1h` | 1 小时内活跃用户（首页在线人数数据源） |
| Hash | `model:cache:{reqId}` | AI回复结果缓存（避免重复调用） |

## 四、特殊功能模块

### 4.1 ModelAutoChatService（自动问答）

定时任务（1小时间隔），自动生成问题调用三个AI，模拟群聊活跃氛围，避免新用户进入看到空白聊天室。

### 4.2 FrontendErrorController（前端异常上报）

接收前端 `POST /api/v1/frontend-error`，记录到后端日志（WARN级别），便于定位用户反馈的白屏等问题。前端通过 `window.error`、`unhandledrejection` 和 `ErrorBoundary.componentDidCatch` 三路捕获。

### 4.3 5分钟无操作自动断开

前端 `OnlinePresenceTracker` 定时检测用户操作（mousemove/keydown/click/scroll/touchstart），5分钟无操作主动 `deactivate()` STOMP 连接并显示提示横幅，用户恢复操作时自动重连。

### 4.4 防爬虫五层防护

1. Nginx 层 IP 限流（滑动窗口）
2. 自动拉黑异常IP
3. UA 过滤可疑爬虫
4. JWT 鉴权保护核心接口（弱密钥启动校验 + DTO 参数校验）
5. 内容安全检测拦截恶意输入

**业务级限流（2026-08 扩展）**：在网关 IP 限流之上，针对高风险接口增加业务级限流 —— SQL 执行台（登录失败锁定 + 执行频率）、媒体生成（用户级 429 + `retry_after`），详见 [安全配置说明.md](安全配置说明.md) 第四章。
