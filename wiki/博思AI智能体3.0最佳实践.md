第一章  引言：AI应用产品面临的真实挑战
================================================================================

在构建AI应用产品的过程中，开发团队和用户共同面对八大根本性问题：

  1. 单一模型偏见：一个模型一种观点，用户只能听到单方说辞
  2. 黑盒推理：AI给出答案但不展示思考过程，用户无法判断可靠性
  3. 意图识别粗暴：所有问题用同一套参数处理，响应慢、体验差
  4. 能力孤岛：聊天、绘画、视频、游戏分散在不同平台，切换成本高
  5. 稳定性焦虑：LLM调用经常报错超时，用户被晾着等，没有自愈机制
  6. 安全与体验矛盾：不防刷被滥用，防太死影响正常使用
  7. 记忆缺失：AI记不住用户偏好与情绪，每次都要重新说明背景
  8. 知识断层：通用模型无法理解企业私有知识，回答缺乏专业性

博思（BoSi）AI智能体系统是一个多模型智能协作平台，核心理念是「不只一个
AI回答你，而是一群AI一起帮你」。系统融合千问、DeepSeek、豆包三大模型，
覆盖群聊、辩论、树洞、多模态生成、AI游戏、知识图谱等核心场景。

本文基于博思系统的完整研发实践，总结AI应用产品在架构设计、模型调用、
智能路由、Agent编排、安全合规等方面的最佳实践，供同行参考。

第二章  系统架构设计最佳实践
================================================================================

2.1 分层解耦，职责清晰
------------------------

博思系统采用九层分层架构，每一层职责明确、可独立演进：

  前端层 → 负载均衡层 → 网关层 → 安全层 → 应用核心 → AI服务层
  → 中间件层 → 大数据层 → 存储层

关键原则：

  - 前后端完全分离：前端dist独立部署Nginx，后端jar轻量化，独立发布
  - AI能力独立服务化：chat-llm独立承载多Provider调用/图执行/RAG，与业务解耦
  - 模块化微服务：6个独立jar（common/web/core/llm/games/media），改哪个重启哪个

2.2 无状态化设计，水平可扩展
------------------------

所有服务均按无状态原则设计：

  - Session存Redis（Hash结构），不存本地内存
  - WebSocket会话追踪存Redis，支持多实例部署
  - 游戏状态存Redis，支持水平扩展
  - nodeId固定为node-{port}，重启不生成新UUID，杜绝消息队列堆积

生产环境双实例部署：
  - chat-web双实例（8081/8082），Nginx ip_hash粘性负载均衡
  - chat-core双实例（9090主/9092从），web轮询调用，autoChat仅主实例执行

2.3 双服务器资源最优分配
------------------------

  - 主服务器（低配）：流量入口，跑Nginx/Redis/RabbitMQ
  - Milvus服务器（高配）：全部Java服务+中间件+监控栈

这种拓扑将IO密集型与计算密集型负载物理隔离，资源利用率最大化。

第三章  多模型协同与LLM调用最佳实践
================================================================================

3.1 多Provider策略模式
------------------------

核心设计：LLMProviderStrategy接口 + 策略工厂自动收集

  - OpenAICompatProvider：REST方式接入千问/DeepSeek/豆包
  - OpenAISdkProvider：SDK方式接入OpenAI/Azure
  - 新增厂商只需实现接口并标注@Component，零改动注册中心

关键经验：
  - 不设Accept-Encoding: gzip，java.net.http的BodyHandlers.ofString()
    不会自动解压，会导致乱码
  - JSON响应需清洗控制字符（ASCII 0x00-0x1F），否则Jackson解析失败
  - 线程池拒绝策略用CallerRunsPolicy替代DiscardPolicy，防止任务静默丢失

3.2 统一调用层次
------------------------

  LLMClient（Fluent Builder，场景化调用）
    → LLMInvoker（熔断/自愈/链路追踪）
      → LlmBundleClient（统一多模型入口，对接chat-llm）
      → DirectLLMClient（降级直连兜底）

Fluent API风格统一：
  llmClient.forConfig(model).scene("chat").stream().execute()

降级、重试、熔断全部内聚，业务层无需关心底层细节。

3.3 动态配置热更新
------------------------

通过Nacos @RefreshScope支持运行时调整：
  - 重试次数/退避间隔
  - 超时时间
  - 各场景的temperature/max_tokens/top_p
  - 修改配置无需重启，刷新间隔内自动生效

3.4 模型管理运营面
------------------------

零代码接入新模型厂商：
  管理页新增提供商 → 填baseUrl + apiKey + 模型列表 → 保存即时生效

技术实现：
  - YAML兜底 + DB覆盖，ApplicationReadyEvent自动加载
  - apiKey存数据库SECRET字段，列表仅回脱敏值
  - /reload接口全量重载，无需重启服务

第四章  意图识别与智能路由最佳实践
================================================================================

4.1 三层漏斗架构
------------------------

意图识别不是简单的LLM分类，而是按命中概率分级的三层漏斗：

  L1 规则匹配（0-1ms）
    - 33条规则覆盖10类意图
    - Trie关键词扫描 + Regex预编译匹配 + 状态机
    - 命中率15-25%

  L2 语义匹配（30-80ms）
    - ~420条种子预加载，解决冷启动
    - Embedding + Milvus k-NN向量检索
    - 动态阈值滑动窗口（1000条±0.02自适应）
    - 命中率80-90%

  L3 LLM分类（200-1000ms）
    - qwen-turbo轻量模型分类
    - 兜底返回UNKNOWN
    - 命中率<10%

设计精髓：
  - 越上层越快、越下层越聪明
  - 每层失败自动降级下一层，不阻塞主流程
  - L1+L2综合命中率>95%，仅<10%走LLM兜底

4.2 自增强闭环
------------------------

  L3高置信结果（≥0.80）
    → SeedPool（积累100条/每10分钟）
    → 灌入Milvus（强化L2）+ Trie（强化L1）

系统越用越聪明，人工标注成本持续降低。

4.3 意图驱动参数路由
------------------------

识别出意图后，自动调整LLM参数：

  意图              Temperature    原因
  CODE_GENERATION   0.2           代码需稳定输出
  REASONING         0.2           逻辑推理需一致性
  TRANSLATION       0.1           翻译需精确
  GENERAL_CHAT      0.7           闲聊自然
  CREATIVE_WRITING  0.95          创作需想象力

同一套系统，不同场景自动匹配最优参数。

第五章  Agent编排与Multi-Agent工作流最佳实践
================================================================================

5.1 标准辩论：LangGraph状态图编排
------------------------

  START → debate(N 方并行) → reflect(N 方批判性反思)
    → shouldContinue → debate/summary → END

关键设计：
  - 模型数由参数透传（默认3个，可选3-6个，从已配置 chat 模型随机组队）
  - 轮数由参数透传（默认3轮，可选1-10轮）
  - Reflection反思：每轮辩论后 N 方批判性审视，修正立场
  - 裁决式汇总：基于反思后的最终立场输出，替代机械归纳

5.2 树状辩论：Plan-and-Execute混合模式
------------------------

为什么不全图：LangGraph节点编译时固化，视角数量运行时决定，全图不灵活。

混合方案：
  Plan：LLM拆解2-3个分析视角（运行时动态）
  Execute：Java CompletableFuture并行执行各视角
    每视角 = LangGraph子图（debate → reflect → shouldContinue → summary）
  Aggregate：LLM综合各视角结论

容错设计：单视角失败不影响其他视角，汇总LLM失败自动本地拼接。

5.3 Multi-Agent并行工作流
------------------------

超长/跨域请求升级为TaskPlanner拆解 + RabbitMQ并行：

  TaskPlanner.shouldDecompose
    → Redis Lua原子限流（max-concurrent=8，超限降级）
    → LLM拆解≤9子任务
    → RabbitMQ分发
    → 双实例Worker×10并发（manual ack + prefetch=1）
    → SubTaskResultCollector结果聚合
    → AgentWorkflowOrchestrator.converge（轻量模型压缩≤1000字）

可靠性三板斧：
  1. Redis Lua原子限流：双实例共享计数，防跨实例错配
  2. manual ack + prefetch=1：按真实能力公平分发，实例挂掉requeue零丢失
  3. WorkflowReconciler对账：每30s兜底卡住的plan，重启后自动恢复

压测验证：20并发=8并行+12降级，全量测试PASS=12/FAIL=0。

5.4 ReAct工具调用
------------------------

Agent工具链：Calculator / Weather / Time / KnowledgeSearch
  → ToolDispatcher ReAct循环（思考→行动→观察→再思考）
  → 工具调用下沉chat-common（LlmToolInvoker + LlmToolExecutor）
  → ToolDispatcher与SubAgentWorker共享实现，零重复

第六章  RAG检索增强生成最佳实践
================================================================================

6.1 文档处理流水线
------------------------

  文档上传（POST /api/v1/rag/documents → 202异步）
    → DocumentParser解析
    → TextChunker分块
    → Embedding向量化（1536维新版 / 1024维legacy）
    → Milvus写入

关键经验：
  - 文档上传异步化（202 + processing状态），不阻塞主线程
  - 两套Embedding并存（维度不兼容故独立实现）
  - RAG运行时从chat-core迁至chat-llm，业务与检索解耦

6.2 对话自动RAG：意图驱动的知识库增强
------------------------

  知识/事实类问题（KNOWLEDGE_QA / TASK_EXECUTION）
    → shouldAutoRag三层判定：
      ① 开关配置 + kbId>0
      ② 意图判定
      ③ 排除实时/个人数据查询（天气、时间、新闻等）
    → RagClient.search(kbId, q, topK=3)
    → score≥0.3片段（≤2000字符）注入system prompt
    → 知识库为空/未命中/失败 → 自动降级普通回答

设计精髓：可查性三层判定避免无效Embedding检索，与weather等实时工具互补。

6.3 多数据源路由
------------------------

RagService支持多数据源路由（Milvus/Pinecone适配），按配置自动选择向量存储。
legacy kbId模型与新版多数据源并存，平滑迁移。

第七章  记忆系统与用户画像最佳实践
================================================================================

7.1 三层记忆架构
------------------------

  Redis短期记忆（最近5轮原文）
    → Milvus长期记忆（向量检索top-3）
    → 用户画像（LLM结构化提炼：情景/情绪/偏好）

7.2 用户画像提炼
------------------------

  每次倾诉 → LLM提炼画像（scene/emotions/preferences/context）
    → Redis user_profile:{scene}:{userId}（TTL 30天）
    → 偏好增量合并
    → 注入记忆上下文 → 回答贴合偏好

关键设计：
  - 异步无侵入：画像提炼在chat-llm线程池执行，失败仅告警不影响主流程
  - TTL 30天自动过期，避免陈旧数据干扰
  - 增量合并策略，偏好逐步累积而非覆盖

7.3 会话历史上下文恢复
------------------------

问题：双core轮询下多轮会话"失忆"（"回答完就断开"）
根因：ChatHistoryBuilder.buildGroup不加载历史对话
修复：复用buildFromRecent加载近期消息，跨实例上下文完整恢复

第八章  安全体系与内容合规最佳实践
================================================================================

8.1 纵深防御体系
------------------------

  网络层：Nginx IP限流 + 自动拉黑 + UA爬虫过滤 + CORS白名单 + 安全响应头
  认证层：JWT（≥32字节弱密钥启动拒绝）+ DTO @Valid校验
  应用层：用户级限流20次/分 · IP 600次/分 · 敏感接口限流10次/分
  内容层：阿里云内容安全detectSensitive + AI生成标识
  运维层：.env 600权限 · 告警webhook · logrotate

8.2 多层限流策略
------------------------

  IP全局限流 600次/分钟
    └── 用户级限流 20次/分钟 / 200次/小时
          └── 敏感接口限流 10次/分钟
                └── 自动拉黑 1000次/60s → 封禁10min

Fail-open容错：Redis异常时放行请求，不因安全组件故障阻断业务。

8.3 构建时安全扫描
------------------------

  Checkstyle：代码风格（CI push阻断）
  PMD：代码质量（CI push阻断）
  SpotBugs + FindSecBugs：Java缺陷+安全漏洞
  Gitleaks：提交历史密钥扫描
  OWASP Dep-Check：依赖CVE数据库
  npm audit：前端依赖CVE扫描

8.4 Nginx安全响应头
------------------------

  X-Content-Type-Options: nosniff        防MIME嗅探
  X-Frame-Options: DENY                  防Clickjacking
  X-XSS-Protection: 1; mode=block       防XSS
  Content-Security-Policy: default-src 'self'  内容安全策略
  Permissions-Policy: camera=(), microphone=()  权限控制
  server_tokens: off                     隐藏版本信息

8.5 密钥管理
------------------------

  - 密钥全部通过环境变量/Nacos注入，禁止硬编码
  - JWT弱密钥启动校验（≥32字节），不合规直接拒绝启动
  - apiKey存数据库SECRET字段，列表仅回脱敏值
  - 泄露应急预案：立即轮换 → 审计日志 → Git清理 → 同步更新

第九章  高可用与弹性设计最佳实践
================================================================================

9.1 熔断与自愈
------------------------

Resilience4j熔断器：
  - 50%失败率 → 30s熔断
  - 重试3次 + 超时30s
  - 按Provider维度隔离

AI错误自愈策略：

  错误类型          自愈策略
  频率限制/超时     换同Provider其他模型重试
  认证失败          跳过失败模型，用默认模型重试
  网络错误          等待1s后重试
  解析错误          降temperature到0.3重试
  模型不存在        不重试，直接报错

降级链：
  llm不可用 → DirectLLMClient直连
  RabbitMQ不可用 → 直调处理
  chat-llm不可用 → chat-core内DirectLLMClient兜底

9.2 双实例高可用
------------------------

  core主（9090，Xmx768m）+ core从（9092，Xmx512m）
  web双实例（8081/8082，各Xmx256m）

  - stop请求CoreClient.broadcast()广播到所有实例
  - 按端口精确pkill，restart-core.sh [9090|9092|all]
  - autoChat定时任务仅主实例执行，避免重复

9.3 跨节点通信
------------------------

基于RabbitMQ TopicExchange('cross-node')实现消息广播：
  - BroadcastService统一入口
  - Base64编码 + _nodeId防回环机制
  - 新节点启动自动创建独立队列并绑定交换机
  - 缩容时队列自动清理，即插即用

9.4 思考链展示
------------------------

ThinkingStreamParser状态机逐token分离<thinking>标签：
  - 三态状态机：NORMAL → IN_TAG → TAG_CLOSED
  - 零延迟emit：仅缓冲最后11字符用于模式匹配
  - 300字符无标签自动切非思考模式，避免误判
  - 意图驱动触发：复杂意图开启，简单对话跳过
  - 仅实时展示不存库，保持历史记录干净

WebSocket消息类型：
  thinking_start → thinking_token → stream_token → done

第十章  可观测性与运维最佳实践
================================================================================

10.1 Prometheus全链路监控
------------------------

  各服务 /actuator/prometheus（micrometer 1.11.6）
    → Prometheus :9094（host网络容器）
    → 12条告警规则 → Alertmanager :9093
    → alert-webhook.py :9950 → 钉钉

告警规则覆盖：
  系统级（8条）：
  - ServiceDown：服务宕机
  - HostMemoryPressure：可用内存<8%
  - DiskWillFill：磁盘<15%将满
  - JvmHeapHigh：JVM堆>85%
  - HighCpu / HighLoad
  - 延迟/5xx异常
  业务级（4条，2026-08-13 上线，数据源由 AOP 切面采集）：
  - IntentFunnelHitRateLow：意图漏斗 L1+L2 命中率<85%
  - AgentWorkflowDegradeHigh：并行工作流降级率>50%
  - AgentWorkflowConvergeFail：收敛失败
  - LLMTokenSurge：LLM token 激增（成本异常）

业务指标采集方式：chat-core 的 `CoreBusinessMetricsAspect`（AOP 切面，
spring-boot-starter-aop）从返回值/异常横切埋点（@Around 三个切点），
`IntentFunnelEngine` / `AgentWorkflowOrchestrator` 业务类零侵入。

10.2 指标化巡检替代手工
------------------------

  - Prometheus 6条告警规则替代手工tail日志
  - 异常秒级推送钉钉
  - 每60s守护线程健康检查（Neo4j自动重连等）

10.3 一键部署
------------------------

  bash deploy.sh install          安装环境（幂等）
  bash deploy.sh install-all      全新上线
  bash deploy.sh all              日常全量部署
  bash deploy.sh core|web|llm     单模块部署

启动顺序：
  llm → core（双实例）→ web（双实例）→ games → media

10.4 前端异常上报
------------------------

POST /api/v1/frontend-error 收集三路异常：
  - ErrorBoundary捕获
  - window.onerror
  - unhandledrejection

前后端异常统一监控。

第十二章  总结与展望
================================================================================

12.1 核心经验总结
------------------------

1. 分层解耦是基础：九层架构让每一层可独立演进，AI能力独立服务化是关键决策
2. 多模型不是堆砌而是编排：策略模式+统一调用层次+动态路由，让多模型协同有序
3. 意图识别要分级：三层漏斗按命中概率分配计算资源，95%请求毫秒级响应
4. 弹性不是可选项而是必须：熔断/自愈/降级/对账，每一层都有容错方案
5. 安全要纵深防御：从网络到认证到内容到运维，层层设防，Fail-open容错
6. 记忆让AI有温度：三层记忆+用户画像，回答逐步贴合个人偏好
7. 可观测替代手工巡检：Prometheus+钉钉告警，异常秒级发现

12.2 技术债务与演进方向
------------------------

  - 服务器内存扩容（已真实触发HostMemoryPressure告警）
  - 双服务器高可用（消除单点）
  - 密钥迁移KMS（替代.env明文）
  - 静态资源上CDN + HTTPS证书
  - 目标1000并发压测（当前500并发P50 154ms零失败）

12.3 可复用的架构资产
------------------------

  - 三层意图漏斗：可独立部署为轻量意图网关
  - LangGraph混合模式：编译时静态+运行时动态的编排范式
  - Fluent Builder API：统一降级/重试/熔断内聚
  - Multi-Agent并行工作流：Plan-and-Execute规模化方案
  - Provider策略模式：新增LLM厂商零改动接入
  - 前后端完全分离：可作为同类项目脚手架
