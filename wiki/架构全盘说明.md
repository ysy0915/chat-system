## 一、系统定位与能力

多 AI 模型群聊系统，核心能力：

| 能力域 | 说明 |
|--------|------|
| 公开群聊 | 千问 / DeepSeek / 豆包三方并发回答，流式输出 |
| 个人对话 | JWT 私密会话，历史持久化，多轮记忆（跨实例共享） |
| 观点辩论场 | 标准辩论（已配置 chat 模型随机组队 3~6 个）+ 树状辩论（LLM 动态拆解多视角） |
| 情绪树洞 | 匿名倾诉，AI 共情回复，内容安全过滤，Memory 记忆增强（用户画像：情景+情绪+偏好） |
| 多模态生成 | 文生图 / 文生视频 / 图生 3D |
| AI 多人游戏 | 城堡围攻 / 乒乓 / 贪吃蛇（WebSocket 对战） |
| 知识库 RAG | 文档上传 → 解析分块 → 向量化 → 检索增强回答 |
| 知识图谱 | 对话后自动抽取三元组入 Neo4j，前端可视化 |
| Agent 工具 | Calculator / Weather / Time / KnowledgeSearch，ReAct 循环（思考→行动→观察）|
| 意图识别 | 三层漏斗（规则→语义→LLM），自动路由模型参数 |
| 思考链 | LLM 推理过程灰色斜体实时展示 |
| 监控告警 | Prometheus 全链路指标 + 钉钉告警 |

## 二、整体架构总览

### 2.1 服务器拓扑（生产）

```
用户浏览器 (React SPA)
    │  HTTPS(80) / WebSocket
    ▼

    ├─ Nginx :80                静态资源 /opt/app/static/chat/ · 反代 /api/ /ws/

    ├─ chat-core :9090 / :9092   核心 AI 引擎（双实例，主从）
    ├─ chat-web  :8081 / :8082   Web 接入层（双实例）

    ├─ Neo4j :7687               知识图谱库
    ├─ Milvus :19530             向量库（9091 为其 metrics，勿占用）

        Prometheus:9094 · Alertmanager:9093 · node-exporter:9100
        · blackbox:9115 · alert-webhook.py:9950 → 钉钉
```

### 2.3 关键架构决策

| 决策 | 原因 |
|------|------|
| 前后端完全分离 | 前端 dist 独立部署 Nginx，后端 jar 轻量化，独立发布 |
| 双服务器 | 主服务器低配只跑入口，Milvus 高配跑计算，资源最优 |
| 模块化微服务 | 6 个独立 jar（common/web/core/llm/games/media），改哪个重启哪个 |
| **双 core (9090/9092)** | 主实例 Xmx768m + 从实例 Xmx512m；web 轮询；autoChat 仅主实例执行 |
| **web 弹性伸缩 (8081 + 按需)** | Nacos 服务发现 + 动态 upstream（least_conn）；Session 无状态化存 Redis；`web-scale.sh` 一键扩缩容 |
| **stop 广播** | 双 core 下停止请求 `CoreClient.broadcast()` 广播到所有实例，任一成功即成功 |
| **nodeId 固定** | `CrossNodeConfig.nodeId()` 固定为 `node-{port}`，根治 RabbitMQ 队列堆积 |
| LLM 独立服务 | chat-llm 承载 Provider 协议适配/图引擎/RAG/图谱，chat-core 业务解耦 |
| 意图三层漏斗 | 规则(0-1ms)→语义(30-80ms)→LLM(200-1000ms)，按命中概率分级，自动降级 |
| 思考链不存库 | 仅实时展示，历史记录保持干净 |
| 指标化巡检 | Prometheus 12 条告警规则（系统 8 + 业务 4：漏斗命中率/工作流降级率/收敛失败/LLM token 激增）替代手工 tail，异常秒级推送钉钉 |

├── dto/          WsMessage(思考链消息类型) · SubAgentTask/SubAgentResult/SubAgentPlan(子任务协议)

### 4.2 chat-web（Web 接入层，弹性伸缩 8081 默认 + Nacos 动态 upstream）

```
controller/  MessageController · AuthController · DebateController · TreeHoleController
             MonitorController · ProfileController · KnowledgeBaseController(代理)
             GraphController · ModelConfigController · IpAdminController
             FrontendErrorController(前端异常上报) · AttachmentController
client/      CoreClient(轮询 coreUrls + broadcast 广播)
```

**核心职责**：
- REST API 暴露 + STOMP WebSocket（在线跟踪 / 消息推送）

- **代理层**：`CoreClient` 转发聊天/辩论/树洞/图谱/知识库请求到 chat-core 或 chat-llm

## 五、核心业务流程

### 5.1 群聊消息（5 步链路）

```
1. MessageController.createMessage()      POST /api/v1/messages
   ├─ rateLimitService.isAllowed(userId)  限流 → 429
   └─ contentSafetyService.detectSensitive 敏感词 → 拒绝
2. messageRepository.insert()              status=queued 入库
3. broadcastService.broadcast()            实时广播问题到在线用户
4. rabbitTemplate.send("chat.exchange","chat.request")
   └─ RabbitMQ 不可用 → chatProcessor.process() 直调降级
5. ChatRequestConsumer 消费（任一 core 实例）
   ├─ ChatProcessor：trySwitchModel 检测换模型指令
   ├─ 并行调 3 个 AI（handle+AtomicInteger 逐完成即推送，避免 allOf 竞态）
   ├─ 思考链：ThinkingStreamParser 分离 thinking_token / stream_token
   └─ completeWithAnswer：status=done + 广播回复 + Redis 缓存
```

### 5.2 个人对话 / 树洞（含思考链）

```
POST /api/v1/messages {private:true} / /api/v1/treehole/ask
  → web 入库 + CoreClient → core(轮询任一实例)
  → ChatProcessor.doPersonalStream / TreeHoleService.executeStreamCall
  → 意图判定 isComplexIntent() → 决定是否开启思考链
  → ChatHistoryBuilder.buildFromRecent 加载历史（跨实例上下文完整）
  → LLM 流式 → ThinkingStreamParser 状态机 → WS 推送
```

**关键**：`buildGroup` 已修复为加载近期历史 —— 双 core 轮询下多轮会话不失忆（"回答完就断开"根除）。

### 5.3 辩论

**标准辩论**（多模型随机组队 3~6 个，轮数可选，含 Reflection 反思）：
```
LangGraph4j StateGraph: START → debate(多方并行) → reflect(多方反思) → shouldContinue ─┬→ debate(round<maxRounds)
                                                                                       └→ summary(裁决式) → END
```
- 模型数由 `model_count` 参数透传（默认 3，限 3~6），后端从已配置 chat 模型随机抽取 N 个（`resolveDebateModels`），动态分配参与者 id 0..N-1，整合模型 id=N，名称经 `ModelRouter.modelDisplayName` 中文展示
- 轮数由 `rounds` 参数透传（默认 3，限 1~10），`DebateGraphService.execute(reqId, userId, topic, rounds)` 动态化 `maxSteps` 与 `state.maxRounds`
- Reflection：每轮辩论后多方批判性审视对方观点并修正立场，汇总基于反思后的最终立场裁决输出
- 提示词增强 + 外存记忆（2026-08-15）：debate 分支注入对方上一轮反思立场 `{{state.conReflections[-1]}}` 与跨会话 `historySummary`（Redis `debate:memory:{userId}:{topicHash}`，TTL 7 天，无 Redis 静默降级）；reflect 节点广播 `reflecting` WS 事件，前端显示反思提示，消除第二轮静默期

**树状辩论**（Plan-and-Execute 混合：先规划再执行，视角内含 Reflection）：
```
DebateTreeProcessor.runTreeDebate
  ├─ decompose()      Plan：LLM 拆解 2-3 视角（异常回退默认三视角）
  ├─ 视角并行 (CompletableFuture)  ← Execute：并行执行各子任务
  │   每视角 = LangGraph 子图（debate → reflect → shouldContinue → summary）
  └─ aggregate()      汇总：各视角结论 → LLM 非流式汇总（异常本地拼接）
```

混合模式原因：视角数运行时决定，单一 StateGraph 需预定义分支，不灵活；Plan-and-Execute（LLM 规划 + Java/子图执行）恰好契合"动态计划 + 并行执行"。

### 5.3.1 Multi-Agent 并行工作流（2026-08）

普通对话走 5.4 的三层漏斗 + 单 Agent 串行回答；**超长/跨域请求**则升级为 TaskPlanner 拆解 + RabbitMQ 并行工作流（与辩论的"视角并行"不同，这里是"独立子任务并行"）：

```
TaskPlanner.shouldDecompose  →  Redis Lua 原子限流(max-concurrent=8，超限降级普通流程)
  → LLM 拆解 ≤9 子任务 → RabbitMQ 分发 (agent.subtask.exchange)
  → 双实例 Worker ×10 并发 (manual ack + prefetch=1，按真实能力公平分发)
  → SubTaskResultCollector 结果 hash 聚合 + received INCR + 收敛锁(SETNX)
  → AgentWorkflowOrchestrator.converge 轻量模型压缩汇总 ≤1000 字 → 完整收尾
```

可靠性三板斧：**Redis Lua 原子限流**（双实例共享计数，防跨实例错配）、**manual ack + prefetch=1**（忙时不拉新消息，实例挂掉 requeue 重投零丢失）、**WorkflowReconciler 对账**（每 30s 兜底"结果已齐但收敛未完成"的卡住 plan，挂掉重启后自动恢复）。压测：20 并发 = 8 并行 + 12 降级，全量测试 PASS=12/FAIL=0。详见《架构设计说明》第 7 章。

### 5.4 意图识别三层漏斗

```
用户输入
  → L1 RuleBasedMatcher   33 条规则 / Trie+Regex / 0-1ms / 命中率 15-25%
  → L2 ContextMatcher     种子420条预载 Milvus / k-NN / 30-80ms / 80-90%
  │   动态阈值(滑动窗口1000条±0.02) · 上下文消歧 · nprobe 自适应
  → L3 ToolIntentMatcher  LLM(qwen-turbo) 分类 / 200-1000ms / <10%
  → 高置信(≥0.80) 结果 → SeedPool(100条/10min) → 灌入 Milvus(L2)+Trie(L1)
每层失败自动降级下一层，不阻塞主流程
```

### 5.5 RAG 检索增强（运行时在 chat-llm）

```
文档上传 POST /api/v1/rag/documents → 202 异步(ragExecutor)
  → DocumentParser 解析 → TextChunker 分块 → Embedding 向量化
  → Milvus 写入(1536维 新版 / 1024维 legacy)
对话时 chat-core RagClient → chat-llm /internal/rag/search
  → 向量检索 + 对话记忆融合 → /internal/rag/invoke-stream 生成 RAG 回答

对话自动 RAG（2026-08）：个人/群聊 → ChatProcessor.shouldAutoRag 三层判定
  （开关配置 → 意图 KNOWLEDGE_QA/TASK_EXECUTION → 排除实时/个人数据查询）
  → RagClient.search(kbId, q, topK=3) → score≥0.3 片段(≤2000字符) 注入 system prompt
  → 知识库为空/未命中/失败 自动降级普通回答
```

### 5.6 知识图谱抽取（运行时在 chat-llm）

```
对话完成 → chat-core GraphClient(异步) → chat-llm /internal/graph/extract
  → LLM 抽取三元组 (subject, relation, object)
  → Neo4j: MERGE (s)-[r:RELATION{type}]->(o)  ON MATCH SET r.count += 1
前端 /api/v1/graph?limit&minEntityWeight&minRelationWeight → 力导向 Canvas 渲染
高可用：kg-reconnect 守护线程每 60s 重连，启动竞态自动恢复
```

### 5.7 多模态生成 / 游戏对战

```
文生图/视频/3D：MediaGenController → 三方平台 API → 文件落盘 → 返回 URL
  （用户级限流 RateLimitService，429 + retry_after）
游戏对战：WebSocket /ws/games → chat-games（游戏状态 Redis）
```

## 七、高可用与可观测性

### 7.1 双实例架构

| 实例 | 端口 | 内存 | 职责 |
|------|------|------|------|
| core 主 | 9090 | Xmx768m | 全量业务 + autoChat 定时任务 |
| core 从 | 9092 | Xmx512m | 全量业务（autoChat 跳过） |
| web 1 | 8081 | Xmx256m | REST/WS，Nginx ip_hash |
| web 2 | 8082 | Xmx256m | REST/WS，Nginx ip_hash |

- web 启动：`--app.core.base-urls=http://127.0.0.1:9090,http://127.0.0.1:9092`
- stop 请求：`CoreClient.broadcast()` 全实例广播
- 重启：`restart-core.sh [9090|9092|all]`、`restart-web.sh [8081|8082|all]` 按端口精确 pkill

### 7.2 Prometheus 监控栈（已上线）

```
各服务 /actuator/prometheus (micrometer 1.11.6)
   → Prometheus :9094 (host 网络容器，--web.listen-address=:9094)
   → 12 条告警规则（系统 8 + 业务 4）→ Alertmanager :9093 (--cluster.listen-address=)
   → alert-webhook.py :9950 (health-check 每分钟守护) → 钉钉
```

规则：ServiceDown / HostMemoryPressure(<8%) / DiskWillFill(<15%) / JvmHeapHigh(>85%) / HighCpu / HighLoad + 延迟/5xx + 业务 4 条（漏斗命中率<85% / 工作流降级率>50% / 收敛失败 / LLM token 激增）；业务指标由 `CoreBusinessMetricsAspect` AOP 切面横切采集（`core.intent.funnel.*` / `core.agent.workflow.*`，业务类零侵入）。

### 7.3 弹性设计

- Resilience4j 熔断（滑动窗口：10 次 / 最少 5 次 / 失败率 ≥50% → OPEN，冷却 30s → HALF_OPEN 放行 3 次）+ 重试（3 次）+ 超时（30s）
- AI 错误自愈：频率限制/认证失败/网络/解析错误分类型恢复
- 降级链：llm 不可用 → DirectLLMClient 直连；RabbitMQ 不可用 → 直调处理
