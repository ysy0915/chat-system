## 一、架构概览

### 服务器拓扑

```
用户浏览器
    │
    ▼
主服务器 your-nginx-ip (Nginx + Redis + RabbitMQ)
    │  ├─ 前端静态资源: /opt/app/static/chat/
    │  ├─ Nginx 反代 /api/ /ws/ → 内网 your-intra-ip:8081/8082 (双 web，ip_hash)
    │  └─ Redis + RabbitMQ 本地
    │
    ▼ 内网
Milvus 服务器 your-milvus-ip (所有 Java 服务 + Prometheus 监控栈)
    ├─ chat-core  :9090 (主实例, Xmx768m, autoChat 定时任务仅此执行)
    ├─ chat-core  :9092 (从实例, Xmx512m)
    ├─ chat-web   :8081 / 8082 (Web接入层双实例, --app.core.base-urls 轮询 core)
    ├─ chat-llm   :9095/9096 (LLM独立服务 + RAG 运行时, gRPC :9195/9196)
    ├─ chat-games :8083 (游戏服务)
    ├─ chat-media :8084 (多模态服务)
    ├─ Nacos :8848 (注册中心容器 nacos/nacos-server:v2.2.3, 配额 768m, RSS ~580MB)
    ├─ Neo4j :7687 (知识图谱) · Milvus :19530 (向量库)
    └─ Prometheus 栈 (host 网络容器): Prometheus:9094 · Alertmanager:9093
       · node-exporter:9100 · blackbox-exporter:9115 · alert-webhook:9950
```

> **端口说明**：9091 被 milvus-standalone 容器占用，core 从实例只能用 9092；Prometheus UI 用 9094（9090 被主 core 占用）。

> **2026-08-12 减重瘦身**：jar 包瘦身（5 模块 432M → 393M，-9%）：chat-core 删除 4 个零引用依赖（pdfbox / aliyun-oss / reactor-netty / green，-24M）；全部模块排除 `org.webjars:swagger-ui` webjars（-4M×5，保留 `/v3/api-docs` JSON，`/swagger-ui.html` 页面 404）。Nacos 容器内存配额 1G → 768m。全量测试通过；1000 并发纯写入压测 100% 成功（P50 72ms / P99 276ms）。

### 生产高可用设计（2026-08 上线）

| 设计 | 说明 |
|------|------|
| **双 core (9090/9092)** | 主实例 Xmx768m，从实例 Xmx512m；web 经 `--app.core.base-urls=http://127.0.0.1:9090,http://127.0.0.1:9092` 轮询 |
| **stop 请求广播** | 双 core 下 stop 必须打到承载实例，`CoreClient.broadcast()` 广播到所有实例，任一成功即成功 |
| **autoChat 仅主实例** | `ModelAutoChatService` 校验 `server.port == 9090` 才执行，避免双实例重复广播自动问答 |
| **RabbitMQ 队列防堆积** | nodeId 固定为 `node-{port}`（`CrossNodeConfig`），重启不再生成带 UUID 的新队列导致堆积 |
| **双 web (8081/8082)** | Nginx upstream 双节点 + ip_hash（WebSocket 会话粘性），`restart-web.sh` 同时拉起两个实例 |
| **Prometheus 指标化巡检** | 替代手工 `tail` 巡检，12 条告警规则（系统 8 条：服务宕机/JVM 堆/CPU/负载/磁盘/内存/延迟/错误率 + 业务 4 条：漏斗命中率/工作流降级率/收敛失败/LLM token 激增）推送钉钉；业务指标由 `CoreBusinessMetricsAspect` AOP 切面横切采集（业务类零侵入） |

### 3.3.1 chat-llm 启动耗时说明（2026-08-13）

**实测数据**（本次全量重启，Spring `Started` 日志时间）：

| 服务 | 启动耗时 | 备注 |
|------|---------|------|
| chat-llm :9095 | **8.5s** | 含 gRPC :9195 |
| chat-core :9090 | 11.5s | 含 autoChat/意图识别初始化 |
| chat-web :8081 | 7.0s | 纯 Web 接入层 |
| chat-games :8083 | 11.8s | 含 Nacos 注册 |
| chat-media :8084 | 11.1s | 含 OSS/多模态初始化 |

**结论：llm 的绝对启动时间不是最慢的**（比 core/games/media 快 ~3s）。部署时"感觉 llm 慢"主要来自**双实例串行重启 + 健康检查轮询**：`restart-llm.sh` 依次重启 9095 → 9096，每实例 = 启动 8.5s + 健康检查 3s/次 轮询（通常 4~5 次命中），`all` 总耗时约 40~60s，且 llm 是部署顺序中最后一个模块，容易成为整体耗时尾部。

**llm 启动路径上的额外环节**（相对纯 Web 服务）：

| 环节 | 耗时 | 说明 |
|------|------|------|
| Nacos 配置订阅 | ~0.5s | 启动早期即拉取 `chat-common-prod.yml` + `chat-llm-prod.yml` 并挂监听 |
| Milvus 同步连接 | ~1.3s | 启动时同步建连 `your-intra-ip-2:19530` 并校验 Collection，随后注册 VectorStore/DataSource |
| gRPC Server | ~1s | 6 个 gRPC 服务注册（graph/admin/langchain/rag/health/reflection）+ 反射服务，端口 9195/9196 |
| LLM 提供商注册 | ~0.5s | `LLMProviderStrategyFactory` + `LLMProviderRegistry` 动态注册（YAML 兜底 + DB 覆盖） |
| Nacos 服务注册 | ~0.6s | `[REGISTER-SERVICE]` 上报实例 |

**无害噪音**：启动早期 2 条 `Load Logback Configuration of Nacos fail` WARN —— Nacos 客户端类路径无内置 `nacos-logback.xml`，回退默认日志，不阻塞启动，可忽略。

**优化建议（待落地）**：
1. `restart-llm.sh` 双实例改**并行**启动（`restart_one 9095 & restart_one 9096 & wait`），总耗时减半；
2. Milvus 连接改惰性初始化（首个检索请求时建连），可再省 ~1.3s；
3. 健康检查轮询间隔 3s → 1.5s 且首检成功即返回。

### 3.5 意图识别配置

#### 环境变量

| 环境变量 | 默认值 | 说明 |
|---------|-------|------|
| `INTENT_ENABLED` | `true` | 是否启用意图识别 |
| `INTENT_MODEL` | `qwen-turbo` | L3 分类用 LLM 模型 |

> L2 阈值已改为**动态自适应**（无需手动配置），详见下节。

#### 三层漏斗结构

| 层 | 引擎 | 命中率 | 延迟 | 关键特征 |
|----|------|--------|------|---------|
| L1 | `RuleBasedMatcher` | 15-25% | 0-1ms | 33 条规则覆盖 10 类意图 |
| L2 | `ContextMatcher` | 80-90% | 30-80ms | Milvus k-NN + 动态阈值 + 种子预加载 |
| L3 | `ToolIntentMatcher` | <10% | 200-1000ms | LLM 分类兜底 + 反馈闭环 |

#### v3.0 新增优化

**L1 规则层**：
- 规则从 10 条扩展到 33 条，覆盖全部 10 种意图
- 额外支持 `CREATIVE_WRITING`、`KNOWLEDGE_QA`、`TASK_EXECUTION`、`EMOTIONAL_SUPPORT` 等

**L2 语义层**：
- 启动时从 `intent-seeds.json` 自动加载 ~420 条种子示例到 Milvus
- **滑动窗口动态阈值**：每意图最近 1000 次命中率 → 自动 ±0.02 调节阈值
- **增强上下文消歧**：多轮同主题加分 / 代码场景降权 / 情绪连续性加分
- **nprobe 自适应**：集合大小 <1000→32、<5000→16、≥5000→8

**反馈闭环**：
- L3 高置信 (>0.80) 分类结果 → 异步推入 SeedPool
- 积累 100 条 或 每 10 分钟 → 自动写入 Milvus (L2) + 提取关键词 (L1)
- 持续自增强，L1+L2 命中率目标 >95%

**多级 TF-IDF**：
- 自动规则挖掘阈值从 tf>0.2 降为三级 (0.05/0.08/0.15)，关键词发现量提升 5×

| 告警 | 表达式要点 | 触发条件 |

### 7.2 AI 回答（ai_answer=true，消息入队 + 异步 LLM）

> 优化配置：HikariCP 5→30, Tomcat threads 50→200, Nginx worker_connections 1024→4096

| 并发数 | 成功率 | P50 | P90 | P99 | Max | 平均 | 备注 |
|--------|--------|-----|-----|-----|-----|------|------|
| 10 | 100% | 83ms | 140ms | 140ms | 140ms | 91ms | -- |
| 50 | 100% | 82ms | 112ms | 193ms | 193ms | 89ms | -- |
| 200 | 100% | 78ms | 117ms | 2.6s | 2.7s | 179ms | -- |
| 500 (优化前) | 99.8% | 4.3s | 8.1s | 9.7s | 11.7s | 4.1s | 1 次 502 |
| **500 (优化后)** | **100%** | **154ms** | **4.4s** | **5.6s** | **6.3s** | **1.6s** | ✅ 零失败 |

**结论**：AI 模式下 HTTP 同步部分（消息入库 + 入队）响应快速；500 并发优化后 P50 从 4.3s 降至 154ms，零 502。

### 7.3 限流验证

| 场景 | 结果 |
|------|------|
| 1000 并发（同一 IP） | 前 495 成功，后 505 全部 429 限流 |
| 自动拉黑 | 超频后 IP 被临时封禁，返回 `"您的IP已被临时封禁"` |
| 随机 IP 模拟 | 1~5000 并发均不受限流影响 |

限流策略：用户级 20次/分钟，IP 级 600次/分钟，自动拉黑 1000次/60秒。

### 7.4 1000 并发优化指南

> 500 并发 AI 模式下出现 502 的根因及修复方案，已验证可支撑 500 并发零失败。

#### 瓶颈分析

| 组件 | 优化前 | 优化后 | 说明 |
|------|--------|--------|------|
| **chat-web HikariCP** | `maximum-pool-size: 5` | `30` | 500 并发竞争 5 个 DB 连接 → 大量等待 |
| **chat-web Tomcat** | `threads.max: 50` | `200` | 500 并发只有 50 线程 → 排队堆积 |
| chat-web Tomcat | `max-connections: 500` | `2000` | 连接上限不够 |
| chat-web Tomcat | `accept-count: 50` | `200` | OS 层等待队列不够 |
| chat-core HikariCP | `maximum-pool-size: 10` | `30` | web 转发到 core 也会消耗连接 |
| chat-core Tomcat | `threads.max: 100` | `200` | 对齐 web 层 |
| **Nginx** | `worker_connections: 1024` | `4096` | 1000 并发时连接数不足 |
| **Nginx API** | 无 `proxy_read_timeout` | `120s` | 默认 60s，长请求被 Nginx 切断 |
| Nginx upstream | 无 `keepalive` | `64` | 每次请求新建 TCP 连接 |

#### 1. chat-web (application-prod.yml)

```yaml
server:
  tomcat:
    threads:
      max: 50 → 200          # 线程池
      min-spare: 10 → 20
    accept-count: 50 → 200   # 等待队列
    max-connections: 500 → 2000  # 最大连接

spring:
  datasource:
    hikari:
      maximum-pool-size: 5 → 30   # 数据库连接池（最关键）
      minimum-idle: 1 → 5
```

#### 2. chat-core (application-prod.yml)

```yaml
server:
  tomcat:
    threads:
      max: 100 → 200
    accept-count: 100 → 200
    max-connections: 1000 → 2000

spring:
  datasource:
    hikari:
```

## 八、树状辩论模式

### 8.1 功能概述

树状辩论是标准辩论模式的升级版，通过 LLM 语义拆解将问题分解为 2-3 个独立分析视角，每个视角由 3 个快模型（随机组队，排除本地 Ollama 慢模型提速）进行 3 轮辩论，最后汇总为一份综合分析结论。整体遵循 **Plan-and-Execute** 范式（LLM 生成计划 → 并行执行 → 汇总结果）。

### 8.2 架构流程

树状辩论采用 **Plan-and-Execute + LangGraph 混合模式**：顶层"规划"（decompose）与"汇总"（aggregate）由 Java 方法完成，单个视角内的 3 轮辩论由 LangGraph 子图驱动（"执行"阶段的子任务）。

```
用户提问
   │
   ▼
┌──────────────────────────────────────┐
│ 1. 语义拆解 (decompose)              │
│    LLM 拆解 → 2-3 个分析视角          │
│    异常回退 → 理性分析/批判观点/综合考量 │
│    (Java 方法)                        │
└──────────┬───────────────────────────┘
           │
     ┌─────┴─────┬─────────┐
     ▼           ▼         ▼
┌─ 视角1 ─┐ ┌─ 视角2 ─┐ ┌─ 视角3 ─┐   ← 上层 batchPool 并行
│         │ │         │ │         │
│  ┌──────┴─┴─ LangGraph 子图 ─┴─┴──────┐
│  │  START → debate → reflect →       │
│  │           shouldContinue          │
│  │              ↑         ↓          │
│  │              └─── (round < 3)     │
│  │                        (round≥3)→ │
│  │              summary → END        │
│  │  (reflect: N 方批判性反思修正立场)  │
│  └───────────────────────────────────┘
│         │ │         │ │         │
│  视角结论  │ │ 视角结论  │ │ 视角结论   │
└──────┬────┘ └──────┬────┘ └──────┬────┘
       └──────────────┼──────────────┘
                      ▼
          ┌───────────────────────┐
          │ 2. 最终汇总 (aggregate)│
          │    各视角结论 → LLM    │
          │    非流式，直接返回    │
          │    异常 → 本地拼接     │
          │    (Java 方法)         │
          └───────────────────────┘
```

**关键模块**：

| 模块 | 文件 | 说明 |
|------|------|------|
| 顶层编排 | `chat-core/.../DebateTreeProcessor.java` | 拆解 + 并行调度视角 + 汇总 |
| LangGraph 子图服务 | `chat-core/.../langgraph4j/TreePerspectiveGraphService.java` | 构建单视角 LangGraph 图并执行 |
| LangGraph 子图节点 | 内联于 `chat-core/.../langgraph4j/TreePerspectiveGraphService.java` | debate / reflect / shouldContinue / summary 四节点 |
| LangGraph 状态 | `chat-core/.../langgraph4j/TreePerspectiveState.java` | 轮次历史、各方答案、结论 |
| 前端展示 | `frontend/src/components/DebateTreeView.jsx` | 拖拽画布 + 节点树 + 缩放 |
| 前端页面 | `frontend/src/pages/Debate.jsx` | 树状模式入口 + WS 事件路由 |
| 后端测试 | `chat-core/.../DebateTreeProcessorTest.java` | 顶层单元测试 |
| LangGraph 测试 | `chat-core/.../langgraph4j/TreePerspectiveStateTest.java` | 状态结构验证 |

### 8.3 WebSocket 事件流

| 事件类型 | 方向 | 说明 |
|----------|------|------|
| `start` | 服务端→前端 | 模型信息 (model_id→model_name) |
| `tree_decompose_start/result` | 服务端→前端 | 语义拆解结果 |

### 8.4 容错设计

| 场景 | 处理策略 |
|------|---------|
| 语义拆解 LLM 失败 | 回退到默认 3 视角 (理性分析/批判观点/综合考量) |
| 语义拆解返回空/>4 个 | 回退到默认 3 视角 |
| 单个视角辩论异常 | 标记 `[xxx 辩论中断]`，其他视角继续 |
| 汇总 LLM 超时/失败 | 本地拼接各视角结论，不触发全局异常 |
| 全部异常 | 仍发送 `done` 消息，前端可解除 loading 状态 |

### 8.5 排障

```bash
# 查看树状辩论相关日志
ssh -i "/Users/apple/Downloads/Milvus.pem" root@your-milvus-ip \
  "grep '\[TreeDebate\]' /opt/app/logs/core-9090.log | tail -50"
```

| 现象 | 可能原因 | 排查 |
|------|---------|------|
| 拆解后无视角 | LLM 返回非法 JSON | 查看 `tree_decompose_result` 中 perspectives 是否为空 |
| 某个视角卡住 | 3 个 LLM 模型中有模型超时 | `grep "error:" /opt/app/logs/core-9090.log` |
| 最终结论不显示 | `done` 消息未到达前端 / 前端组件提前卸载 | 检查 WS 消息中 `done` 是否在 `tree_aggregate_result` 之后 |
| 汇总卡死 | `aggregate()` prompt 过大 + 流式输出 | 已改为 `invoke()` 非流式，若仍卡死检查 LLM API 限制 |
| 移动端缩放/拖拽无效 | CSS `touch-action` 冲突或 JS 事件被拦截 | 确认 `debate-tree-wrapper` 有 `touch-action: none` |

### 8.6 LangGraph 混合模式设计

树状辩论中，**视角内的辩论循环**使用 LangGraph 的 `StateGraph` 做有向无环图编排：

| 设计 | 说明 |
|------|------|
| 图结构 | `debate → reflect → shouldContinue → (debate 或 summary → END)` |
| 节点 | 4 个节点：debateNode、reflectNode、shouldContinue、summaryNode（`debate`/`reflect` 为 N 方并行分支） |
| 条件路由 | `shouldContinue` 根据 `round < maxRounds` 决定下一跳 |
| Reflection | `reflect` 节点 N 方各自审视「自己+对方观点」后输出修正立场（50 字内），写 `model*Reflections` |
| 并发策略 | 视角间在上层 `CompletableFuture` 并行，视角内 LangGraph 单线程串行 |
| 编译缓存 | 每个视角重新编译图（beta API 限制），每次执行约 10-20ms 开销 |

**为什么只做视角内子图而非全图**：

LangGraph4j 的 `StateGraph` 节点是编译时固化的，但树状辩论的视角数量由 LLM 运行时动态决定（2-3 个）。若用单一全图实现，需要预定义 3 条并行分支并用条件跳过未使用的分支，图会变得复杂且不灵活。混合模式 — 上层 Java 动态并行 + 视角内 LangGraph 子图 — 兼顾了灵活性和结构化编排。

### 8.7 与标准辩论的对比

| 特性 | 标准辩论 (DebateProcessor) | 树状辩论 (DebateTreeProcessor) |
|------|---------------------------|-------------------------------|
| 视角数量 | 动态 N 个 (模型数 3~6 可自选，随机组队) | 动态 2-3 个 (LLM 按问题拆解) |
| 辩论轮次 | 用户可选 1~10 轮（默认 3，前端 1~5） | 每个视角固定 3 轮 |
| LLM 调用 | 每轮 3 次 (流式) | 每视角每轮 3 次 (流式) + 汇总 1 次 (非流式) |
| 总 LLM 调用 | ~9 次 | 视角数 × 9 + 1 次汇总 |
| 前端展示 | 固定布局 | 可拖拽 DAG 画布 + 缩放 |
| 汇总方式 | 逐轮逐步 | 所有视角完成后一次性汇总 |
| 辩论编排 | LangGraph4j `StateGraph` | 上层 Java + 视角内 LangGraph4j 子图 (混合) |
| 异常隔离 | 全局失败 | 单视角失败不影响其他视角 |
